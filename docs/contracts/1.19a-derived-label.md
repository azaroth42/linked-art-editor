# Contract: Step 1.19a — Derived root `_label`

**Step:** follow-up to Phase 1 Step 1.19 (found in PR #155; no guide step) · **Owner decision:** 2026-11-23 (`docs/questions.md`, "Owner decision, 2026-11-23 (derived `_label`)") · **Contract by:** Claude Fable 5.2 · **Date:** 2026-11-23

Read with: rule R17 of `docs/spikes/S3-projection.md` (ADR-0018); ADR-0027 (item 5 and "Consequences"); ADR-0030; contracts `1.10-publish.md` and `1.14-revisions.md` (§3 items 5, 12, 16, 17); the module docstrings of `lae.labels.extract`, `lae.labels.langtags`, `lae.crdt.rooms`, `lae.projection.ops`, `frontend/src/crdt/paths.ts`, `frontend/src/editor/validation/schemaCheck.ts`; `docs/questions.md` Step 1.17 item 2.

**The decision.** A record's root `_label` is derived from its primary name, the preferred language first. It follows every title edit, users cannot edit it, and a stub gets it from the name typed in the dialog.

**The design: derive on read, never write into the CRDT.** `_label` is a pure function of the draft's names, applied wherever a draft becomes JSON-LD: in `Room.snapshot()` on the server (the one place every server-side reader of a draft goes through: draft validation, publish, `draft/diff`) and in one `projectDraft` helper in the browser. The server never writes a Yjs update for it. Reasons, which the implementer must not trade away:

- A server-written `_label` needs a second update after every title keystroke (persist-before-apply through a private replica, ADR-0027), changes `last_update_id` behind the client (spurious `LAE-PUB-004`), and a snapshot taken between the two updates would still be stale, so the snapshot would have to derive anyway.
- A pure function of converged state converges by construction; it creates no undo entry and cannot loop.
- Drafts and stubs that already exist without `_label` are correct on their next read; no migration.

"Always follows title edits" therefore means: after any draft write, every reading of the draft (snapshot, validation, publish, diff, the browser's own projection, also offline) carries the label derived from the names as they are then. Collaborators see it change because each browser computes it from the same converged document. The published JSON-LD stores the derived value, because publish stores the snapshot.

## 2. Interfaces

### 2.1 `lae.labels.derive`

```python
LABEL_LANGUAGE: Final = "en"          # the instance's preferred label language
LABEL_KEY: Final = "_label"

def normalize_label(text: str) -> str
def derive_label(jsonld: Mapping[str, Any]) -> str | None
def with_derived_label(jsonld: dict[str, Any]) -> dict[str, Any]
```

All three are pure (no database, settings, clock or randomness), never raise for any JSON object, and never modify their argument.

**Usable name.** An item of the root `identified_by` (a single object counts as a one-item array) that is an object with `type == "Name"` and a string `content` holding at least one non-whitespace character: exactly what `lae.labels.extract.iter_names` yields, in projected array order. Identifiers and names of embedded nodes never count.

**Selection** (`lae.labels.extract.primary_name(names) -> NameLabel | None`; the order `_default_label` already uses):

1. the first usable name classified as Primary Name (`is_primary_name`: `aat:300404670` in any AAT spelling) whose language is `LABEL_LANGUAGE` (`primary_language(name.language) == "en"`, the language being `language_tag` of the name's first `language` entry);
2. else the first usable name classified as Primary Name, in any language or none;
3. else the first usable name;
4. else none.

**`derive_label`** returns `normalize_label(content)` of the selected name, or `None` when there is none. It never reads the root `_label`, and never returns `""`.

**`normalize_label`**: leading and trailing whitespace removed, every run of whitespace replaced by one U+0020. Whitespace is exactly the 29 code points of Python's `str.isspace`: U+0009–000D, U+001C–001F, U+0020, U+0085, U+00A0, U+1680, U+2000–200A, U+2028, U+2029, U+202F, U+205F, U+3000 (Python: `" ".join(text.split())`). U+FEFF and U+200B are not whitespace. Nothing else is changed: no Unicode normalization, no case folding, **no maximum length and no truncation** (the schema sets none, and a truncated label would no longer equal the name it comes from).

**`with_derived_label(jsonld)`**: with `label = derive_label(jsonld)`: if `label is None` or `jsonld.get("_label") == label` (same string), the result is `jsonld` unchanged (it may be the same object); otherwise a shallow copy with `_label` set to `label`. So when there is no usable name the document's own `_label` is kept, and an absent one stays absent.

**Where the language preference comes from.** A module constant, `en`: the value `_default_label` and `lae.api.deps.FALLBACK_LOCALE` already use. It is not a setting in this step, because the browser must apply the same value and there is no channel that carries settings to it. It is not the caller's locale: the label is stored in the record.

A bulk-loaded record gets the derived label when it is first published through the editor.

### 2.3 Browser (`frontend/src/crdt/derivedLabel.ts`)

```ts
export const LABEL_LANGUAGE = "en";
export function normalizeLabel(text: string): string;
export function deriveLabel(jsonld: JsonObject): string | null;
export function withDerivedLabel(jsonld: JsonObject): JsonObject;
export function projectDraft(doc: Y.Doc): JsonObject;   // withDerivedLabel(project(doc))
```

Mirrors 2.1 exactly, including `is_primary_name`, `language_tag` (a well-formed `notation` decides alone, `eng` counts as `en`; otherwise the AAT id `300388277` in the three AAT spellings) and the whitespace set, written as an explicit character class (never `\s`, `trim()` or `split(/\s+/)`: JavaScript's set differs). `project` stays the R-rule mirror and is not changed. Every production reading of the live draft as JSON-LD uses `projectDraft`. `checkSchema` and `schemaCheck.ts` are not changed: the drawer passes it `projectDraft(doc)`, the server's schema stage gets `Snapshot.jsonld`, so both see the same document and the Step 1.19 fixture (`schema_browser_cases.json`, which must not change in the PR) still proves the two checks equal.

### 2.4 Write paths: the TS / Python mismatch is settled here

`lae.projection.rules.WRITE_FORBIDDEN_KEYS = frozenset({"id", "type", "_label"})`. `_write_path` checks, before parsing, each `.`-separated part of the path up to its first `[` against it and raises `ProjectionError(PROJ_BAD_PATH)` (`LAE-PROJ-007`), as `paths.ts` `writePath` does. Python no longer answers `PathSyntaxError` for `_label`. `IDENTITY_KEYS` keeps its meaning for its other users. `add_reference(label=…)` still stores a reference's `_label`: that is not a path. Closes `docs/questions.md` Step 1.17 item 2.

### 2.5 Error codes (no new codes)

| Code | When |
| :-- | :-- |
| `LAE-SCHEMA-required`, path `""`, `missing` containing `_label` | a draft with no usable name and no `_label` of its own; from draft validation and, identically, from the browser check |

Scaffolding: for `LAE-SCHEMA-required` at `""` with `missing == ["_label"]` the drawer shows "Give the record a name; its label is taken from the name." and jumps to the first slot whose path is `identified_by[Name]`. Code, path and params are unchanged.

## 3. Invariants

1. **Function of the names only.** `derive_label(d)` depends on nothing but the root `identified_by` of `d`; two documents that differ only in `_label` give the same result.
2. **Idempotent and non-mutating.** `with_derived_label(with_derived_label(d))` is `same_json` to `with_derived_label(d)`; `d` is unchanged afterwards.
3. **Agreement with `entity_labels`.** For every document with a usable name, `derive_label(d) == normalize_label(labels_from_record(d)[1])`. `labels_from_record` returns for every corpus record exactly what it returned before this step.
4. **Never empty.** No code path writes `_label: ""` or `null`. Without a usable name the document is left as it is.
5. **Every server reading of a draft is derived.** For any room, `room.snapshot().jsonld` is `same_json` to `with_derived_label(project(room.ydoc))`. Hence draft validation, publish and `draft/diff` see the same `_label`, and what publish stores (`records.data`, the revision's JSON-LD and N-Triples, `entity_labels.default_label` up to normalization) carries it.
6. **The server writes nothing for it.** Deriving appends no `crdt_updates` row, does not change `last_update_id`, `contributors` or the `Doc`'s state vector, and broadcasts nothing. After *n* client updates a draft has had exactly *n* appended.
7. **Convergence.** Two replicas that have exchanged all updates give `same_json` `projectDraft` results, equal to the server's snapshot, whatever the order in which concurrent edits to the names arrived.
8. **No undo entry, no loop.** `projectDraft` does not transact on the `Doc` (no `update` event fires); after one title edit the editor's `Y.UndoManager` holds one item.
9. **Python and TypeScript agree** on `derive_label`, `with_derived_label` and the schema verdict of the derived document, for every case and every corpus record of `derived_label_cases.json`.
10. **Clients cannot write it through the write path.** A write path naming `_label` at any depth is `LAE-PROJ-007` in both languages and leaves the document unchanged. (A client speaking raw Yjs can still set the root `_label` key, ADR-0027 "Consequences"; it shows only while the record has no usable name. Not checked in this step.)
11. **A new record's row is derived.** After `POST /api/records` with a template that has a usable name, `records.data["_label"]` is the derived label, and so is the first snapshot's.
12. **Diff.** A changed derived label appears in `semantic_diff` as one `update_literal` with `parent == []`, `property == "_label"` (`op` `set` or `change`). That is correct and must not be filtered on the server: contract 1.14 §3 items 5 and 12 need it, and it is a true statement about what the publish will store. The diff view may caption it as derived from the name.
13. **Amendment to contract 1.14 §3 item 17.** After a revert the snapshot is `same_json` to `with_derived_label(revision n)`, and `draft/diff` equals `revisions/{current}/diff/{n}` except for at most that one root `_label` change. The two are identical for every revision published after this step; they differ only for a bulk-loaded revision whose source `_label` is not the derived one.

## 4. Failure modes

| Situation | Result |
| :-- | :-- |
| No usable name, the document has a `_label` (most bulk-loaded records without names; a template with only `_label`) | label kept; validation and publish as before |
| No usable name and no `_label` | `LAE-SCHEMA-required` naming `_label`; publish 422 `LAE-PUB-003`; nothing written |
| All names removed from a record that had one | the `_label` the document holds (the last stored one) is kept: there is no name to follow |
| `identified_by` or a name is malformed (a string, `null`, `content` not a string, blank) | that item is not usable; no exception; the schema and `LAE-RULE-003` report it as today |
| Draft cannot be projected | 422 `LAE-CRDT-008` as before (deriving comes after projecting) |
| Stub created before this step, without `_label` | derived on the next snapshot; its parent publishes |
| Bulk-loaded record whose `_label` differs from its name | the first `draft/diff` shows the `_label` change without any user edit; publish stores the derived label; the sync worker's ordinary diff updates the label triple |
| Two primary names in the preferred language (concurrent adds) | the first in projected order on every replica (R12 order is deterministic) |
| Write path naming `_label` | `LAE-PROJ-007`, document unchanged |
