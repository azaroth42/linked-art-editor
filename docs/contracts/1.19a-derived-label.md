# Contract: Step 1.19a — Derived root `_label`

**Step:** follow-up to Phase 1 Step 1.19 (found in PR #155; no guide step) · **Owner decision:** 2026-11-23 (`docs/questions.md`, "Owner decision, 2026-11-23 (derived `_label`)") · **Contract by:** Claude Fable 5.2 · **Date:** 2026-11-23 · **Amended:** 2026-11-23 (the label language is a setting; owner decisions (a)–(c) in the same `docs/questions.md` entry)

Read with: rule R17 of `docs/spikes/S3-projection.md` (ADR-0018); ADR-0027 (item 5 and "Consequences"); ADR-0030; contracts `1.10-publish.md` and `1.14-revisions.md` (§3 items 5, 12, 16, 17); the module docstrings of `lae.labels.extract`, `lae.labels.langtags`, `lae.settings`, `lae.crdt.rooms`, `lae.projection.ops`, `frontend/src/crdt/paths.ts`, `frontend/src/editor/validation/schemaCheck.ts`; `docs/questions.md` Step 1.17 item 2.

**The decision.** A record's root `_label` is derived from its primary name, the preferred language first. It follows every title edit, users cannot edit it, and a stub gets it from the name typed in the dialog. The preferred language is a setting of the installation (`LAE_LABEL_LANGUAGE`, default `en`; §2.6), not a constant.

**The design: derive on read, never write into the CRDT** (accepted by the owner as a reading of "set on every draft write"). `_label` is a pure function of the draft's names and the label language, applied wherever a draft becomes JSON-LD: in `Room.snapshot()` on the server (the one place every server-side reader of a draft goes through: draft validation, publish, `draft/diff`) and in one `projectDraft` helper in the browser. The server never writes a Yjs update for it. Reasons, which the implementer must not trade away:

- A server-written `_label` needs a second update after every title keystroke (persist-before-apply through a private replica, ADR-0027), changes `last_update_id` behind the client (spurious `LAE-PUB-004`), and a snapshot taken between the two updates would still be stale, so the snapshot would have to derive anyway.
- A pure function of converged state converges by construction; it creates no undo entry and cannot loop.
- Drafts and stubs that already exist without `_label` are correct on their next read; no migration.

"Always follows title edits" therefore means: after any draft write, every reading of the draft (snapshot, validation, publish, diff, the browser's own projection, also offline) carries the label derived from the names as they are then. Collaborators see it change because each browser computes it from the same converged document. The published JSON-LD stores the derived value, because publish stores the snapshot.

## 2. Interfaces

### 2.1 `lae.labels.derive`

```python
LABEL_KEY: Final = "_label"
DEFAULT_LABEL_LANGUAGE: Final = "en"   # the default of Settings.label_language; see below

def normalize_label(text: str) -> str
def derive_label(jsonld: Mapping[str, Any], label_language: str) -> str | None
def with_derived_label(jsonld: dict[str, Any], label_language: str) -> dict[str, Any]
```

All three are pure (no database, settings, clock or randomness), never raise for any JSON object and any string `label_language`, and never modify their argument. `label_language` is a required positional parameter with **no default**, here and in `primary_name` and `labels_from_record`: a call site that forgets it does not type-check. None of these functions reads `Settings` or `get_settings()`; the call sites of §2.2 do. There is no module constant holding "the" language: `DEFAULT_LABEL_LANGUAGE` is only the default of the settings field and of the two constructors named in §2.2, and `lae.labels.extract.ENGLISH` is removed.

**`label_language`** is a value `Settings.label_language` accepts (§2.6): a lower-case primary language subtag such as `en`, `fr`, `de`. The functions compare it as given, without normalizing it; a string that is not such a value (`"EN"`, `"en-GB"`, `""`) matches no name in step 1 below and is otherwise harmless.

**Usable name.** An item of the root `identified_by` (a single object counts as a one-item array) that is an object with `type == "Name"` and a string `content` holding at least one non-whitespace character: exactly what `lae.labels.extract.iter_names` yields, in projected array order. Identifiers and names of embedded nodes never count.

**Selection** (`lae.labels.extract.primary_name(names, label_language) -> NameLabel | None`; the order `_default_label` already uses, with the language as a parameter):

1. the first usable name classified as Primary Name (`is_primary_name`: `aat:300404670` in any AAT spelling) whose language is the label language (`primary_language(name.language) == label_language`, the language being `language_tag` of the name's first `language` entry; "Language matching" below);
2. else the first usable name classified as Primary Name, in any language or none;
3. else the first usable name;
4. else none.

**Language matching** is `lae.labels.langtags` as it is; this step changes nothing in that module. A name is in the label language exactly when `primary_language(language_tag(e)) == label_language`, `e` being the first entry of its `language` (a single object counts as a one-item array; later entries are never read). Spelled out:

- If `e.notation` is a string that is a well-formed tag after `str.strip()` (the 29 whitespace code points below; `[A-Za-z]{2,8}(-[A-Za-z0-9]{1,8})*`), it decides alone: its first subtag, lower-cased and shortened through `ISO_639_2_TO_1` (`fra` and `fre` to `fr`, `deu` and `ger` to `de`, `eng` to `en`), is compared. So `fr`, `FR`, `fr-CA`, `fra` and `" fre "` are French; a notation `en` on a name whose `id` is the French concept is English, not French; a well-formed notation that is no language (`english`) matches nothing, and the `id` is not consulted.
- Otherwise, if `e.id` is a string naming a concept of `AAT_LANGUAGE_TAGS` in one of the three AAT spellings (`http://vocab.getty.edu/aat/`, `https://vocab.getty.edu/aat/`, `aat:`, followed by ASCII digits only), that table's tag is compared. **A name that carries only an AAT language id therefore matches a configured `fr` or `de`** (`300388306`, `300388344`), as it matches `en` today (`300388277`): the table maps 57 AAT languages, and `Settings.label_language` accepts exactly its 57 tags, so every accepted value can be matched by an id alone and can be written by the editor's language widget, which writes the concept without a notation.
- Otherwise (no `language`, an entry that is not an object, a malformed notation and an unknown or non-AAT `id`) the name's language is `und` and matches no label language.

**`derive_label`** returns `normalize_label(content)` of the selected name, or `None` when there is none. It never reads the root `_label`, and never returns `""`. Whether it returns `None` does not depend on `label_language` (steps 2–4 do not read it).

**`normalize_label`**: leading and trailing whitespace removed, every run of whitespace replaced by one U+0020. Whitespace is exactly the 29 code points of Python's `str.isspace`: U+0009–000D, U+001C–001F, U+0020, U+0085, U+00A0, U+1680, U+2000–200A, U+2028, U+2029, U+202F, U+205F, U+3000 (Python: `" ".join(text.split())`). U+FEFF and U+200B are not whitespace. Nothing else is changed: no Unicode normalization, no case folding, **no maximum length and no truncation** (the schema sets none, and a truncated label would no longer equal the name it comes from).

**`with_derived_label(jsonld, label_language)`**: with `label = derive_label(jsonld, label_language)`: if `label is None` or `jsonld.get("_label") == label` (same string), the result is `jsonld` unchanged (it may be the same object); otherwise a shallow copy with `_label` set to `label`. So when there is no usable name the document's own `_label` is kept, and an absent one stays absent.

**Where the language preference comes from.** `Settings.label_language` (§2.6), read by the call sites of §2.2 and handed down as an argument; the browser gets the same value with the record it opens (§2.6). It is not the caller's locale, and not `lae.api.deps.FALLBACK_LOCALE` (the interface locale, which stays `en`): the label is stored in the record.

**`labels_from_record(jsonld, label_language) -> tuple[dict[str, str], str]`.** The default label follows the setting too: `_default_label(jsonld, names, label_language)` is the content of `primary_name(names, label_language)`, else the root `_label`, else the `id`, as today with `label_language` in the place of `ENGLISH`. The first element (the labels by language) does not depend on `label_language`. Reason: `entity_labels.default_label` is what a reader sees when the record has no name in their own languages, and what autocomplete and reference labels fall back to; if it stayed English-first, a `fr` installation would show one name as the record's `_label` and another wherever the record is referenced. With `label_language == "en"` the function returns exactly what it returns today.

### 2.6 The label language: the setting and how the browser gets it

**The setting.** `lae.settings.Settings.label_language: str = "en"`, read from `LAE_LABEL_LANGUAGE`, with the docstring "Language preferred for a record's derived `_label` and for `entity_labels.default_label` (Step 1.19a)." A `field_validator` normalizes and checks it:

1. the value must be a string and `lae.labels.langtags.normalize_tag(value)` must not be `None` (so surrounding whitespace and case are forgiven, and `fra` / `fre` become `fr`);
2. the normalized tag must be one of the 57 values of `AAT_LANGUAGE_TAGS`. That refuses a tag with a region or script (`en-GB`, `zh-Hant`: matching is by primary language, and a subtag that is silently ignored would mislead), `und`, the empty string, and a language the table does not map (it could be matched only by a `notation`, which the editor does not write).

The stored value is the normalized tag. Anything else raises pydantic's `ValidationError` naming `label_language` when `Settings()` is built, so `lae api`, `lae crdt-ws` and every other command stop before they bind a port or open the database, as for `LAE_DRAFT_TTL_DAYS=0` today. `lae.settings` may import `lae.labels.langtags` (pure data, no import of `lae.settings`).

**Who reads it.** `api` (`create_record`, `get_record`'s header, publish's `entity_labels` row, the drafts list, the Public Reader title), `crdt-ws` (`Room.snapshot`), and the `lae bootstrap` command (the load's `entity_labels` rows). `sync-worker` and `scheduler` do not use it. **All processes of one installation must be given the same value**, like `LAE_DATABASE_URL` and `LAE_BASE_URI`; `deploy/README.md` says so. Nothing checks it at run time (§4).

**It is read once, at start.** Changing it means restarting `api` and `crdt-ws` together. It is not a row of `system_settings`: Phase 2 Step 2.17's `lae/settings_store.py` does not list it and must not gain it without a contract, because a value that changes under running processes would have to reach `api`, every room of `crdt-ws` and every open browser at one instant. If it ever moves there, the header below stays the browser's channel.

**The browser's channel: `X-Label-Language` on `GET /api/records/{id}`.** The route already carries `X-Draft-Epoch`, which the editor must read before it can open a draft; the label language travels with it.

- Server: `LABEL_LANGUAGE_HEADER: Final = "X-Label-Language"` in `lae.api.records`; `get_record` sends it on every 200, with the value `settings.label_language`; it is declared in the route's OpenAPI response headers as a string, as `X-Draft-Epoch` is. Authentication, permissions, status codes, body and caching of the route are unchanged (signed in; the value is no secret, but no anonymous route is added for it). No new endpoint, and nothing in `/auth/me`, `/auth/providers` or `/api/vocab/bundle`.
- Client: `EditorRecord` gains `labelLanguage: string`; `fetchEditorRecord` reads the header and throws the `ApiError` it throws for a bad epoch when the header is absent or does not match `^[a-z]{2,3}$`. It never substitutes a default. `LABEL_LANGUAGE_HEADER` is exported next to `DRAFT_EPOCH_HEADER`.
- `frontend/src/api/schema.d.ts` is regenerated with `corepack pnpm api:generate` and committed; no other generated file changes.

**Before it has loaded, and offline.** There is no such state for `projectDraft`: a `Doc` exists only once `useEditorRecord` has answered, because `useRecordDoc` needs the epoch of that same response, and `labelLanguage` arrives in it. The value lives in that query's result (`staleTime: Infinity`, `gcTime: 0`, refetched on every mount and after publish, discard and revert) and is handed to `ValidationDrawer`, `RawInspector` and the page's `snapshot` callback; it is not copied to `localStorage`, IndexedDB or a module variable. When the connection drops the page keeps the record it loaded, so the offline editor derives with the value the server had when the draft was opened; that is deterministic, and equal to the server's as long as the server has not been restarted with another value (§4). A browser that starts offline cannot open the editor at all (`/auth/me` and the record are needed), as today.

## 3. Invariants

1. **Function of the names and the language only.** `derive_label(d, L)` depends on nothing but the root `identified_by` of `d` and `L`; two documents that differ only in `_label` give the same result. `L` only chooses among the names: `derive_label(d, L) is None` exactly when `d` has no usable name, whatever `L`, so the schema verdict on `with_derived_label(d, L)` for a missing `_label` is the same for every `L`.
2. **Idempotent and non-mutating.** `with_derived_label(with_derived_label(d, L), L)` is `same_json` to `with_derived_label(d, L)`; `d` is unchanged afterwards.
3. **Agreement with `entity_labels`.** For every document with a usable name and every label language `L` the setting accepts, `derive_label(d, L) == normalize_label(labels_from_record(d, L)[1])`; the first element of `labels_from_record(d, L)` is the same for every `L`. `labels_from_record(d, "en")` returns for every corpus record exactly what `labels_from_record(d)` returned before this step.
4. **Never empty.** No code path writes `_label: ""` or `null`. Without a usable name the document is left as it is.
5. **Every server reading of a draft is derived.** For any room, `room.snapshot().jsonld` is `same_json` to `with_derived_label(project(room.ydoc), L)`, `L` being the `label_language` of the `Settings` the `crdt-ws` process was started with. Hence draft validation, publish and `draft/diff` see the same `_label`, and what publish stores (`records.data`, the revision's JSON-LD and N-Triples, `entity_labels.default_label` up to normalization) carries it.
6. **The server writes nothing for it.** Deriving appends no `crdt_updates` row, does not change `last_update_id`, `contributors` or the `Doc`'s state vector, and broadcasts nothing. After *n* client updates a draft has had exactly *n* appended.
7. **Convergence.** Two replicas that have exchanged all updates give `same_json` `projectDraft(doc, L)` results for the same `L`, equal to the server's snapshot under that `L`, whatever the order in which concurrent edits to the names arrived.
8. **No undo entry, no loop.** `projectDraft` does not transact on the `Doc` (no `update` event fires); after one title edit the editor's `Y.UndoManager` holds one item.
9. **Python and TypeScript agree** on `derive_label`, `with_derived_label` and the schema verdict of the derived document, for every case of `derived_label_cases.json` under the language the case names and for every corpus record under each language of the file, and on the two language tables.
10. **Clients cannot write it through the write path.** A write path naming `_label` at any depth is `LAE-PROJ-007` in both languages and leaves the document unchanged. (A client speaking raw Yjs can still set the root `_label` key, ADR-0027 "Consequences"; it shows only while the record has no usable name. Not checked in this step.)
11. **A new record's row is derived.** After `POST /api/records` with a template that has a usable name, `records.data["_label"]` is the derived label under `settings.label_language`, and so is the first snapshot's.
12. **Diff.** A changed derived label appears in `semantic_diff` as one `update_literal` with `parent == []`, `property == "_label"` (`op` `set` or `change`). That is correct and must not be filtered on the server: contract 1.14 §3 items 5 and 12 need it, and it is a true statement about what the publish will store. The diff view may caption it as derived from the name.
13. **Amendment to contract 1.14 §3 item 17.** After a revert the snapshot is `same_json` to `with_derived_label(revision n, L)`, and `draft/diff` equals `revisions/{current}/diff/{n}` except for at most that one root `_label` change. The two are identical for every revision published after this step under the label language the installation has now; they differ only for a bulk-loaded revision whose source `_label` is not the derived one, and for a revision published under another label language.
14. **One language per installation, and no hidden default.** `get_record`'s `X-Label-Language`, `new_record_data`, publish's `entity_labels` row and (the processes sharing their environment) `Room.snapshot` all use `Settings.label_language`. Outside `lae.settings` and the two constructors of §2.2 no production code, Python or TypeScript, supplies a label language of its own: with the setting `fr`, nothing derives with `en`.
15. **The browser derives with the server's value.** For a record opened with `fetchEditorRecord`, every `projectDraft` call of the page uses the `labelLanguage` of that response; with the server unchanged since, the result is `same_json` to the server's snapshot of the same converged document.

## 4. Failure modes

| Situation | Result |
| :-- | :-- |
| No usable name, the document has a `_label` (most bulk-loaded records without names; a template with only `_label`) | label kept; validation and publish as before |
| No usable name and no `_label` | `LAE-SCHEMA-required` naming `_label`; publish 422 `LAE-PUB-003`; nothing written |
| All names removed from a record that had one | the `_label` the document holds (the last stored one) is kept: there is no name to follow |
| `identified_by` or a name is malformed (a string, `null`, `content` not a string, blank) | that item is not usable; no exception; the schema and `LAE-RULE-003` report it as today |
| Draft cannot be projected | 422 `LAE-CRDT-008` as before (deriving comes after projecting) |
| Stub created before this step, without `_label` | derived on the next snapshot; its parent publishes |
| Bulk-loaded record whose `_label` differs from its name | the first `draft/diff` shows the `_label` change without any user edit; publish stores the derived label; the sync worker's ordinary diff updates the label triple |
| Two primary names in the preferred language (concurrent adds) | the first in projected order on every replica (R12 order is deterministic) |
| Write path naming `_label` | `LAE-PROJ-007`, document unchanged |
| `LAE_LABEL_LANGUAGE` is not one of the 57 tags after normalization (`en-GB`, `und`, `xx`, empty) | `ValidationError` from `Settings()`; the process does not start |
| No name is in the label language (a `fr` installation, a record with English names only) | selection steps 2 and 3: the first primary name, else the first name; never an empty label |
| A name states its language only by an AAT id outside the 57 of the table, or by a non-AAT URI, without a usable `notation` | its language is `und`; it can still be chosen by steps 2 and 3 |
| The setting is changed and `api` and `crdt-ws` restarted: open drafts | nothing is migrated; every draft derives under the new language at its next read (snapshot, validation, publish, diff) |
| …: published records | `records.data`, the revisions and `entity_labels.default_label` keep the label they were stored with until the record is next published; the first `draft/diff` after the change may show a `_label` change nobody made (as for a bulk-loaded record), and reverting to an older revision likewise (invariant 13). No backfill in this step (§6) |
| …: `entity_labels` rows | a mixture of default labels chosen under the old and the new language, until each record is republished or the load is run again; `labels` (by language) are unaffected, so a reader whose locale has a name sees no difference |
| …: a browser page that was open across the restart | it keeps the old `labelLanguage` until the record is loaded again (publish, discard, revert, navigation, reload); meanwhile its raw inspector and its own schema check may show the name of the other language as `_label`. Verdicts are the same (invariant 1), and what validation, the publish diff and publish use and store is the server's. Not detected in this step |
| `api` and `crdt-ws` started with different values (a deployment mistake) | new records and the browser follow `api`, snapshots and so publishes follow `crdt-ws`: a stub's first `draft/diff` shows a `_label` change and `entity_labels.default_label` may be another name than the stored `_label`. No data is lost and nothing detects it; `deploy/README.md` warns. |
| `GET /api/records/{id}` answers without a valid `X-Label-Language` (an older `api` behind a newer page) | `fetchEditorRecord` throws; the editor shows its load error and opens no draft, rather than deriving with a guess |
