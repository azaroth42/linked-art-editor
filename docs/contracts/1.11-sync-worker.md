## 2. Interfaces

### 2.1 Translation (`lae.sync.events`)

```python
class Mode(StrEnum):
    INSERT = "insert"      # INSERT DATA of every to_version triple
    DIFF = "diff"          # DELETE DATA (old - new) ; INSERT DATA (new - old)
    REPLACE = "replace"    # DELETE WHERE per subject ; INSERT DATA of every to_version triple
    RETRACT = "retract"    # DELETE WHERE per subject

@dataclass(frozen=True, slots=True)
class Event:               # one outbox_events row, as read
    id: int
    kind: OutboxEventKind
    record_id: UUID
    from_version: int | None
    to_version: int | None
    drift_check: bool      # payload.get("drift_check") is True
    attempts: int
    created_at: datetime

def choose_mode(event: Event, *, unhealed: bool, old_lines_empty: bool) -> Mode
def subjects_of(lines: Iterable[str]) -> set[str]          # subject IRI of each canonical line
def build_event_update(mode: Mode, *, old_lines: frozenset[str], new_lines: frozenset[str],
                       retract_subjects: Collection[str]) -> str
async def translate_event(conn: asyncpg.Connection, event: Event) -> str
```

`choose_mode`, `subjects_of` and `build_event_update` are pure. `translate_event` only reads Postgres and returns the SPARQL Update text of one event, or `""` when there is nothing to send. It raises `EventError` (§2.4).

### 2.2 Worker (`lae.sync.worker`)

```python
BATCH_SIZE: Final = 50
BATCH_WINDOW_S: Final = 0.25
POLL_INTERVAL_S: Final = 1.0
MAX_ATTEMPTS: Final = 5
MAX_UPDATE_BYTES: Final = 4_000_000
SYNC_WORKER_LOCK: Final = 0x1AE0_51C0      # advisory lock key, one per database

@dataclass(frozen=True, slots=True)
class BatchResult:
    outcome: Literal["empty", "done", "rejected", "unavailable", "stale_watermark"]
    done: tuple[int, ...]            # ids marked done by this call, ascending
    failed_event: int | None         # the event that got an attempt counted, if any
    dead_lettered: bool              # that event is now `failed`
    updates_sent: int                # HTTP updates QLever acknowledged
    error: str | None

async def process_batch(conn, client: QLeverClient, *, limit: int = BATCH_SIZE) -> BatchResult
async def apply_event(conn, event_id: int, client: QLeverClient) -> str
async def replay(conn, client: QLeverClient, *, after_id: int, through_id: int | None = None,
                 statuses: Collection[OutboxEventStatus] = (OutboxEventStatus.DONE,),
                 batch_size: int = BATCH_SIZE) -> int
async def catch_up(conn, client: QLeverClient) -> int
def classify(error: QLeverError) -> Literal["unavailable", "rejected"]
def backoff_seconds(failures: int) -> float          # min(2 ** (failures - 1), 30)
async def run(settings: Settings, *, once: bool = False, client: QLeverClient | None = None,
              stop: asyncio.Event | None = None) -> int
def main(settings: Settings, argv: Sequence[str] = ()) -> Coroutine[Any, Any, int]
```

- `conn` is an `asyncpg.Connection`. The worker uses **one** connection for the advisory lock, `LISTEN`, every read and every write (§3 item 22).
- `client` is the target. `apply_event` and `replay` take any `QLeverClient`, so Step 2.18 replays into a second index by constructing a client for its URL. **Both write nothing to Postgres**: no status, no attempt, no watermark. `apply_event` returns the text it sent (`""` if nothing was sent). `replay` applies, in id order and in batches built like `process_batch`'s, every event with `after_id < id ≤ through_id` whose status is in `statuses`, and returns the last id applied (`after_id` if none). It raises on the first failure; a caller restarts from the last value it got.
- `process_batch` and `catch_up` act on the live index and are the only functions that write `outbox_events` or `sync_state`. `catch_up` returns the number of events it replayed (0 if none; fixed in review, 2026-11-23).

### 2.3 Command line and settings

- `lae sync-worker`: run until SIGTERM or SIGINT; the batch in progress is finished or not sent; exit 0.
- `lae sync-worker --once`: take the lock, run `catch_up` if needed, call `process_batch` once without the 250 ms window, exit 0 for `empty` or `done`, 1 otherwise or if the lock is held. No sleeping, no retry.
- `lae sync-worker --replay-after ID [--through ID] [--target-url URL] [--target-update-url URL]`: call `replay` against the target (default: the live index) and exit; prints the last id applied. Does not take the lock when a target URL is given.
- The worker refuses to start (`EXIT_CONFIG_ERROR`) without `LAE_QLEVER_URL` and `LAE_QLEVER_ACCESS_TOKEN`: QLever refuses an update without the token.
- New settings: `sync_metrics_host` (default `127.0.0.1`), `sync_metrics_port: int | None` (default `None` = no listener).
- `GET /metrics` on that port, Prometheus text format: gauges `outbox_pending`, `outbox_failed`, `sync_lag_seconds` (age of the oldest pending event, 0 if none), `sync_watermark`; counters `updates_sent_total`, `sync_events_done_total`, `sync_dead_letters_total`, `sync_unavailable_total`. The first four names are the guide's and must not change.

### 2.4 Errors (`lae.sync.errors`)

`EventError(Exception)` with `code` and `params`; `str()` is `"<code> <json params>"`. These are operator diagnostics, written to `outbox_events.last_error` and the log; they need no `errors.json` entry.

| Code | Meaning | `params` |
| :-- | :-- | :-- |
| `LAE-SYNC-001` | A revision the event needs does not exist, or the record row does not | `event`, `record_id`, `version` |
| `LAE-SYNC-002` | Stored N-Triples or JSON-LD cannot be read (zstd, not canonical, not JSON), or a subject cannot be written as an IRI | `event`, `record_id`, `version`, `detail` |
| `LAE-SYNC-003` | The event cannot be translated: kind `merge` or `split` (later steps), `publish` without `to_version`, `delete` without `from_version` | `event`, `kind` |
| `LAE-SYNC-004` | QLever rejected the update | `event`, `status`, `body` (first 2000 characters) |

`last_error` holds that string. QLever being unavailable is not an `EventError` and is never written to an event.

## 3. Invariants

Each is a property a named test in §5 checks.

**Translation**

1. **Only revisions.** The triples and JSON-LD an event is translated from come from `record_revisions` rows (`ntriples_zstd`, `jsonld_zstd`) and the record URI from `records.uri`. `records.data` is never read and nothing is expanded: `expand_to_ntriples` is not called by this step. A translation is therefore the same whenever it is made, however many versions have been published since.
2. **Mode.**
   - `publish`, `from_version` NULL → `INSERT`.
   - `publish`, `from_version` set, and any of: `drift_check` true; `unhealed` (item 5); the stored triples of `from_version` are empty → `REPLACE`.
   - `publish` otherwise → `DIFF`.
   - `delete` → `RETRACT`.
   - `merge`, `split` → `LAE-SYNC-003`.
   The worker trusts `payload.drift_check` as publish computed it and does not compare versions itself.
3. **`DIFF`** sends `build_update(*diff_triples(old, new))` where `old` and `new` are the stored lines of `from_version` and `to_version`. The lines are pasted unchanged; no literal is re-serialized. When the diff is empty the event contributes `""`.
4. **`REPLACE` and `RETRACT` retract every owned subject.** `retract_subjects` is the union, over every revision `v` of the record with `lo ≤ v ≤ from_version`, of `owned_subjects(jsonld_v, record_uri)` and `subjects_of(lines_v)`. `lo` is `from_version`, lowered to the smallest `coalesce(from_version, to_version)` among the failed events item 5 names. Every revision in that range must exist (`LAE-SYNC-001`). The update is `build_delete_where_subjects(retract_subjects)`, then for `REPLACE` `build_update([], new_lines)`, joined in that order. The subjects never come from `to_version` alone and never from current data: a node removed by the edit must still be retracted.
5. **A dead letter is healed by the record's next event.** `unhealed` is true when the record has an event with a lower id and status `failed`, and no event of the record between that one and this has another status. Such an event is translated as `REPLACE` (or `RETRACT`) over the wider range of item 4, so QLever holds exactly `to_version` afterwards although the failed event was never applied.
6. **`REPLACE` is always correct; `DIFF` is an optimisation** valid only when QLever holds exactly the stored triples of `from_version`. Any doubt selects `REPLACE`.
7. **Back-filled revisions.** A version-1 revision with empty N-Triples and `published_by` NULL is read like any other; the worker never reads `published_by`, `authors` or `summary`.
8. **Nothing to send.** An event whose update is `""` is acknowledged without a request. A batch whose every update is `""` sends no request and is marked done.
9. **No coalescing.** Two events of one record in a batch stay two updates, in id order. A net diff from the first `from_version` to the last `to_version` is forbidden: it breaks item 17.

**Batching, acknowledgement, watermark**

10. **Order.** A batch is the pending events with the lowest ids, ascending, at most `limit`. Events of one record are therefore applied in id order, which is their commit order because every writer of an event holds that record's row lock (Step 1.10 item 6; later writers of `delete`, `merge`, `split` events must do the same). Events of different records commute, since no two records share a subject. No event is sent while an event with a lower id is pending.
11. **One combined update.** The batch's non-empty updates are joined with `" ;\n"` in id order and sent in one `client.update` call. The batch is cut before the first event that would take the text over `MAX_UPDATE_BYTES` (one event alone is always sent) and before the first event whose translation raises (that event is then the head of the next batch).
12. **Acknowledge, then record.** After `client.update` returns, and never before, one Postgres transaction sets every event of the batch to `done` with `processed_at = now()` (the `UPDATE` requires `status = 'pending'` and must change exactly as many rows as the batch has, else roll back and raise) and writes `sync_state.qlever_index_watermark` = the batch's highest id, as a JSON integer. Nothing is written to Postgres between reading the batch and that transaction.
13. **Watermark.** It is the highest id of an event QLever has acknowledged to the live index. Only this transaction and `catch_up` write it; it never decreases through the worker; a dead letter does not move it. It does not promise that every lower id is applied: a transaction that commits late leaves a pending event with a lower id, which is applied next.
14. **A watermark someone else changed is noticed.** `process_batch` reads the watermark before translating. In the transaction of item 12 it reads it again `FOR UPDATE`; if the value differs, the transaction is rolled back, the events stay pending and the outcome is `stale_watermark`. A missing key is a value like any other.
    *Amended in review, 2026-11-23 (PR #148):* a watermark lowered while **no** batch is in flight must be noticed too, or the next batch reads the lowered value both times, writes its own highest id over it, and the `done` events in between never reach the rebuilt index. So `process_batch` first checks the condition of item 15: when the watermark exists and a `done` event has a higher id, it sends and writes nothing and returns `stale_watermark`. The worker alone never produces that state (it writes the watermark with the events it marks done), so the check never fires in normal operation. `run` makes the same check on every idle poll, so a rebuilt index is caught up within about 1 s even with an empty queue.
15. **Catch-up.** When the watermark exists and a `done` event has a higher id (an index rebuilt from an older export, a restored index directory), `catch_up` replays the `done` events above it through `replay`, writing the watermark after each acknowledged batch, before any pending event is processed. `run` calls it at start and after `stale_watermark`. With no watermark key there is no catch-up. A watermark that is not a JSON integer stops the worker with `EXIT_CONFIG_ERROR`.
16. **Crash safety.** A process death at any point leaves each event either `pending` (and its update possibly applied to QLever, wholly or in part) or `done` with its update applied. No event is `done` without an acknowledgement. After a restart the pending events are sent again.
17. **Idempotent replay.** For one record with versions `v0 = ∅, v1, …`, let QLever hold the triples of `v_c`, or any state between `v_c` and `v_{c+1}` left by an update that stopped part-way. Applying the updates of events `a … b` in order, with `a − 1 ≤ c ≤ b`, leaves exactly `v_b`. This is why a batch may be sent twice, a range replayed into a rebuilt index, and a batch cut differently on retry. It does **not** hold for a range that stops before the newest applied event, so nothing may send an old event on its own; `apply_event` is for a caller that replays in order.
18. **Bulk changes are not this worker's.** `lae bootstrap load` and `rewrite-refs` write no events. The worker does not look for records without events; an index rebuild covers them.

**Failures**

19. **Classification.** `classify` returns `unavailable` for a `QLeverError` without a status (connection refused, timeout) and for 401, 403, 408, 429 and 5xx; `rejected` for every other status.
20. **Unavailable costs no attempt.** Nothing is written to Postgres; the same events are tried again after `backoff_seconds(n)` for the `n`-th consecutive unavailable outcome (1, 2, 4, … capped at 30 s), for as long as it takes. An outage of QLever never produces a dead letter.
21. **Rejected: find the event, count it alone.** When a batch of more than one event is rejected, no attempt is counted; `process_batch` sends its events one by one, in order, each with its own transaction of item 12, and stops at the first failure. An event that is rejected when sent alone, or whose translation raises at the head of a batch, gets one transaction: `attempts += 1`, `last_error`, and when `attempts` reaches `MAX_ATTEMPTS`, `status = 'failed'` and `processed_at = now()`. Later events stay pending and untouched. `run` then sleeps `backoff_seconds(attempts)` (1, 2, 4, 8 s) before the next batch, so a poisoned event holds the queue for at most about 15 s, then is a dead letter and the queue moves on. A `failed` event is never sent again by the worker.

**Process**

22. **One active worker.** `run` takes `pg_try_advisory_lock(SYNC_WORKER_LOCK)` on its one connection before it reads any event. If the lock is held it logs once and tries again every 5 s (`--once`: exit 1). If the connection is lost the process exits 1 without sending anything more; it never reconnects in-process, so a lost lock is never used. A supervisor restarts it.
23. **Latency.** A notification on `outbox` or the 1 s poll wakes the loop. With 50 or more pending events it takes a batch at once; otherwise it waits until 250 ms after waking and takes what is pending. A publish is in QLever within 1 s on an idle system.
24. **Token.** Every update carries the access token (`QLeverClient(settings.qlever_url, settings.qlever_update_url, token)`); the token never appears in a log line, `last_error` or `/metrics`.

## 4. Failure modes

| Situation | What happens | State afterwards |
| :-- | :-- | :-- |
| QLever down, timing out, 5xx, wrong token | `unavailable`; retried with capped backoff; `sync_unavailable_total` and `sync_lag_seconds` grow | events pending, attempts unchanged |
| QLever answered but the response was lost | as above; the batch is sent again | converges (item 17) |
| QLever rejects a combined update | events sent one by one | those before the bad one `done`; the bad one `attempts + 1` |
| An event rejected 5 times, or untranslatable 5 times | `failed`, `last_error` = `LAE-SYNC-00x …` | later events continue; the record is healed by its next event (item 5) or by a rebuild |
| Revision missing, stored bytes unreadable, unsupported kind | `LAE-SYNC-001` / `-002` / `-003`, counted like a rejection | as above |
| Worker killed before sending | nothing | events pending |
| Worker killed after QLever applied, before the commit | batch sent again after restart | same QLever state as one application |
| Postgres commit of item 12 fails | the worker exits 1 | events pending; sent again |
| Watermark changed under the worker | `stale_watermark`; catch-up; then the pending events | converges |
| Index rebuilt from an older export | catch-up replays `done` events above the new watermark | index holds every published version |
| Second worker started | waits for the lock (`--once`: exit 1) | one sender |
| Database connection lost | exit 1 | restart resumes from pending |
| No `LAE_QLEVER_URL` or token; watermark not an integer | exit `EXIT_CONFIG_ERROR` | unchanged |
| Two events of one record in one batch | two updates in order | the later version |
| Event with nothing to send | `done` without a request | unchanged index |

Known limit, to record in `docs/questions.md` and not to solve: if a worker's connection dies after it read a batch and before its HTTP request completes, and a new worker applies later events of the same record within that request's 30 s, the old request can land last and reinsert a retracted triple. The nightly audit (Step 2.18 / 3.10) is the backstop.

## 6. Out of scope, and decisions to record

- No change to `lae.rdf`, `lae.sparql`, `lae.publish`, `lae.bootstrap` or `lae.sync.qlever_client`, and no migration. If one seems needed, stop and report.
- No writer of `delete`, `merge` or `split` events (Phase 2 Steps 2.4, 2.6); the worker's side of `delete` is built and tested here with a directly inserted row. Their contracts must keep §3 item 10 (event written under the record's row lock) and, for `delete`, set `from_version` to the last published version with its revision present (back-filled as in Step 1.10 item 11).
- No blue/green rebuild, swap, `sync_state.qlever_active_url` or delta-threshold trigger (Step 2.18); only `apply_event` and `replay` with a target. No consistency audit. No requeue of dead letters (an admin action of a later step; it must not simply set `pending`, see item 17). No text-index freshness (Step 1.13 covers it from Postgres). No sidecar graphs.
- Write an ADR (next free number) for the points where this contract departs from or adds to the guide: the worker trusts `payload.drift_check`; a missing `from_version` revision is an error, not a reason to re-expand (publish back-fills it); `delete` uses `DELETE WHERE` over owned subjects rather than `DELETE DATA`; unavailable and rejected are told apart and only rejection counts toward the 5 attempts; a rejected batch is retried event by event; strict id order with a poisoned event blocking for about 15 s; healing after a dead letter; the meaning of the watermark, the compare on write, and catch-up; one connection and exit on its loss; the `--replay-after` command.
