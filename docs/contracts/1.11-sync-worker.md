## 2. Interfaces

### 2.1 Translation (`lae.sync.events`)

```python
class Mode(StrEnum):
    INSERT = "insert"      # INSERT DATA of every to_version triple
    DIFF = "diff"          # DELETE DATA (old - new) ; INSERT DATA (new - old)
    REPLACE = "replace"    # DELETE WHERE per subject ; INSERT DATA of every to_version triple
    RETRACT = "retract"    # DELETE WHERE per subject

@dataclass(frozen=True, slots=True)
class Event:               # one outbox_events row, as read
    id: int
    kind: OutboxEventKind
    record_id: UUID
    from_version: int | None
    to_version: int | None
    drift_check: bool      # payload.get("drift_check") is True
    attempts: int
    created_at: datetime

def choose_mode(event: Event, *, unhealed: bool, old_lines_empty: bool) -> Mode
def subjects_of(lines: Iterable[str]) -> set[str]          # subject IRI of each canonical line
def build_event_update(mode: Mode, *, old_lines: frozenset[str], new_lines: frozenset[str],
                       retract_subjects: Collection[str]) -> str
async def translate_event(conn: asyncpg.Connection, event: Event) -> str
```

`choose_mode`, `subjects_of` and `build_event_update` are pure. `translate_event` only reads Postgres and returns the SPARQL Update text of one event, or `""` when there is nothing to send. It raises `EventError` (§2.4).

### 2.2 Worker (`lae.sync.worker`)

```python
BATCH_SIZE: Final = 50
BATCH_WINDOW_S: Final = 0.25
POLL_INTERVAL_S: Final = 1.0
MAX_ATTEMPTS: Final = 5
MAX_UPDATE_BYTES: Final = 4_000_000
SYNC_WORKER_LOCK: Final = 0x1AE0_51C0      # advisory lock key, one per database

@dataclass(frozen=True, slots=True)
class BatchResult:
    outcome: Literal["empty", "done", "rejected", "unavailable", "stale_watermark"]
    done: tuple[int, ...]            # ids marked done by this call, ascending
    failed_event: int | None         # the event that got an attempt counted, if any
    dead_lettered: bool              # that event is now `failed`
    updates_sent: int                # HTTP updates QLever acknowledged
    error: str | None

async def process_batch(conn, client: QLeverClient, *, limit: int = BATCH_SIZE) -> BatchResult
async def apply_event(conn, event_id: int, client: QLeverClient) -> str
async def replay(conn, client: QLeverClient, *, after_id: int, through_id: int | None = None,
                 statuses: Collection[OutboxEventStatus] = (OutboxEventStatus.DONE,),
                 batch_size: int = BATCH_SIZE) -> int
async def catch_up(conn, client: QLeverClient) -> int
def classify(error: QLeverError) -> Literal["unavailable", "rejected"]
def backoff_seconds(failures: int) -> float          # min(2 ** (failures - 1), 30)
async def run(settings: Settings, *, once: bool = False, client: QLeverClient | None = None,
              stop: asyncio.Event | None = None) -> int
def main(settings: Settings, argv: Sequence[str] = ()) -> Coroutine[Any, Any, int]
```

- `conn` is an `asyncpg.Connection`. The worker uses **one** connection for the advisory lock, `LISTEN`, every read and every write (§3 item 22).
- `client` is the target. `apply_event` and `replay` take any `QLeverClient`, so Step 2.18 replays into a second index by constructing a client for its URL. **Both write nothing to Postgres**: no status, no attempt, no watermark. `apply_event` returns the text it sent (`""` if nothing was sent). `replay` applies, in id order and in batches built like `process_batch`'s, every event with `after_id < id ≤ through_id` whose status is in `statuses`, and returns the last id applied (`after_id` if none). It raises on the first failure; a caller restarts from the last value it got.
- `process_batch` and `catch_up` act on the live index and are the only functions that write `outbox_events` or `sync_state`. `catch_up` returns the number of events it replayed (0 if none; fixed in review, 2026-11-23). *Amended for issue #150:* `catch_up` takes an optional `metrics` keyword and may also set a `done` event `failed` (§7.3, §7.4).
- *Amended for issue #171 (§8.3):* `BatchResult` gains a last field `refusal: Refusal | None = None`, and the module gains `confirm_rejection`, `database_failure` and `EXIT_PERSISTENT`.

### 2.3 Command line and settings

- `lae sync-worker`: run until SIGTERM or SIGINT; the batch in progress is finished or not sent; exit 0.
- `lae sync-worker --once`: take the lock, run `catch_up` if needed, call `process_batch` once without the 250 ms window, exit 0 for `empty` or `done`, 1 otherwise or if the lock is held. No sleeping, no retry.
- `lae sync-worker --replay-after ID [--through ID] [--target-url URL] [--target-update-url URL]`: call `replay` against the target (default: the live index) and exit; prints the last id applied. Does not take the lock when a target URL is given.
- The worker refuses to start (`EXIT_CONFIG_ERROR`) without `LAE_QLEVER_URL` and `LAE_QLEVER_ACCESS_TOKEN`: QLever refuses an update without the token.
- *Amended for issue #171:* the exit codes of every `lae sync-worker` command are the table of §8.5. "1 otherwise" above and "exit 1" in item 22 and §4 still hold for a lost connection; a database error that cannot pass by itself exits 4 (item 39).
- New settings: `sync_metrics_host` (default `127.0.0.1`), `sync_metrics_port: int | None` (default `None` = no listener).
- `GET /metrics` on that port, Prometheus text format: gauges `outbox_pending`, `outbox_failed`, `sync_lag_seconds` (age of the oldest pending event, 0 if none), `sync_watermark`; counters `updates_sent_total`, `sync_events_done_total`, `sync_dead_letters_total`, `sync_unavailable_total`. The first four names are the guide's and must not change.

### 2.4 Errors (`lae.sync.errors`)

`EventError(Exception)` with `code` and `params`; `str()` is `"<code> <json params>"`. These are operator diagnostics, written to `outbox_events.last_error` and the log; they need no `errors.json` entry.

| Code | Meaning | `params` |
| :-- | :-- | :-- |
| `LAE-SYNC-001` | A revision the event needs does not exist, or the record row does not | `event`, `record_id`, `version` |
| `LAE-SYNC-002` | Stored N-Triples or JSON-LD cannot be read (zstd, not canonical, not JSON), or a subject cannot be written as an IRI | `event`, `record_id`, `version`, `detail` |
| `LAE-SYNC-003` | The event cannot be translated: kind `merge` or `split` (later steps), `publish` without `to_version`, `delete` without `from_version` | `event`, `kind` |
| `LAE-SYNC-004` | QLever rejected the update | `event`, `status`, `body` (first 2000 characters) |

`last_error` holds that string. *Amended for issue #171 (item 44):* `body` is the first 2000 characters of QLever's answer **after** the access token was removed from it. QLever being unavailable is not an `EventError` and is never written to an event.

## 3. Invariants

Each is a property a named test in §5 checks.

**Translation**

1. **Only revisions.** The triples and JSON-LD an event is translated from come from `record_revisions` rows (`ntriples_zstd`, `jsonld_zstd`) and the record URI from `records.uri`. `records.data` is never read and nothing is expanded: `expand_to_ntriples` is not called by this step. A translation is therefore the same whenever it is made, however many versions have been published since.
2. **Mode.**
   - `publish`, `from_version` NULL → `INSERT`.
   - `publish`, `from_version` set, and any of: `drift_check` true; `unhealed` (item 5); the stored triples of `from_version` are empty → `REPLACE`.
   - `publish` otherwise → `DIFF`.
   - `delete` → `RETRACT`.
   - `merge`, `split` → `LAE-SYNC-003`.
   The worker trusts `payload.drift_check` as publish computed it and does not compare versions itself.
3. **`DIFF`** sends `build_update(*diff_triples(old, new))` where `old` and `new` are the stored lines of `from_version` and `to_version`. The lines are pasted unchanged; no literal is re-serialized. When the diff is empty the event contributes `""`.
4. **`REPLACE` and `RETRACT` retract every owned subject.** `retract_subjects` is the union, over every revision `v` of the record with `lo ≤ v ≤ from_version`, of `owned_subjects(jsonld_v, record_uri)` and `subjects_of(lines_v)`. `lo` is `from_version`, lowered to the smallest `coalesce(from_version, to_version)` among the failed events item 5 names. Every revision in that range must exist (`LAE-SYNC-001`). The update is `build_delete_where_subjects(retract_subjects)`, then for `REPLACE` `build_update([], new_lines)`, joined in that order. The subjects never come from `to_version` alone and never from current data: a node removed by the edit must still be retracted.
5. **A dead letter is healed by the record's next event.** `unhealed` is true when the record has an event with a lower id and status `failed`, and no event of the record between that one and this has another status. Such an event is translated as `REPLACE` (or `RETRACT`) over the wider range of item 4, so QLever holds exactly `to_version` afterwards although the failed event was never applied.
6. **`REPLACE` is always correct; `DIFF` is an optimisation** valid only when QLever holds exactly the stored triples of `from_version`. Any doubt selects `REPLACE`.
7. **Back-filled revisions.** A version-1 revision with empty N-Triples and `published_by` NULL is read like any other; the worker never reads `published_by`, `authors` or `summary`.
8. **Nothing to send.** An event whose update is `""` is acknowledged without a request. A batch whose every update is `""` sends no request and is marked done.
9. **No coalescing.** Two events of one record in a batch stay two updates, in id order. A net diff from the first `from_version` to the last `to_version` is forbidden: it breaks item 17.

**Batching, acknowledgement, watermark**

10. **Order.** A batch is the pending events with the lowest ids, ascending, at most `limit`. Events of one record are therefore applied in id order, which is their commit order because every writer of an event holds that record's row lock (Step 1.10 item 6; later writers of `delete`, `merge`, `split` events must do the same). Events of different records commute, since no two records share a subject. No event is sent while an event with a lower id is pending.
11. **One combined update.** The batch's non-empty updates are joined with `" ;\n"` in id order and sent in one `client.update` call. The batch is cut before the first event that would take the text over `MAX_UPDATE_BYTES` (one event alone is always sent) and before the first event whose translation raises (that event is then the head of the next batch).
12. **Acknowledge, then record.** After `client.update` returns, and never before, one Postgres transaction sets every event of the batch to `done` with `processed_at = now()` (the `UPDATE` requires `status = 'pending'` and must change exactly as many rows as the batch has, else roll back and raise) and writes `sync_state.qlever_index_watermark` = the batch's highest id, as a JSON integer. Nothing is written to Postgres between reading the batch and that transaction.
13. **Watermark.** It is the highest id of an event QLever has acknowledged to the live index. Only this transaction and `catch_up` write it; it never decreases through the worker; a dead letter does not move it. It does not promise that every lower id is applied: a transaction that commits late leaves a pending event with a lower id, which is applied next.
14. **A watermark someone else changed is noticed.** `process_batch` reads the watermark before translating. In the transaction of item 12 it reads it again `FOR UPDATE`; if the value differs, the transaction is rolled back, the events stay pending and the outcome is `stale_watermark`. A missing key is a value like any other.
    *Amended in review, 2026-11-23 (PR #148):* a watermark lowered while **no** batch is in flight must be noticed too, or the next batch reads the lowered value both times, writes its own highest id over it, and the `done` events in between never reach the rebuilt index. So `process_batch` first checks the condition of item 15: when the watermark exists and a `done` event has a higher id, it sends and writes nothing and returns `stale_watermark`. The worker alone never produces that state (it writes the watermark with the events it marks done), so the check never fires in normal operation. `run` makes the same check on every idle poll, so a rebuilt index is caught up within about 1 s even with an empty queue.
15. **Catch-up.** When the watermark exists and a `done` event has a higher id (an index rebuilt from an older export, a restored index directory), `catch_up` replays the `done` events above it through `replay`, writing the watermark after each acknowledged batch, before any pending event is processed. `run` calls it at start and after `stale_watermark`. With no watermark key there is no catch-up. A watermark that is not a JSON integer stops the worker with `EXIT_CONFIG_ERROR`.
    *Amended for issue #150 (§7.4):* `catch_up` no longer goes through `replay` and no longer raises on an event that cannot be replayed; such an event becomes a dead letter and catch-up continues (items 25–33). `replay` itself is unchanged.
16. **Crash safety.** A process death at any point leaves each event either `pending` (and its update possibly applied to QLever, wholly or in part) or `done` with its update applied. No event is `done` without an acknowledgement. After a restart the pending events are sent again.
17. **Idempotent replay.** For one record with versions `v0 = ∅, v1, …`, let QLever hold the triples of `v_c`, or any state between `v_c` and `v_{c+1}` left by an update that stopped part-way. Applying the updates of events `a … b` in order, with `a − 1 ≤ c ≤ b`, leaves exactly `v_b`. This is why a batch may be sent twice, a range replayed into a rebuilt index, and a batch cut differently on retry. It does **not** hold for a range that stops before the newest applied event, so nothing may send an old event on its own; `apply_event` is for a caller that replays in order.
18. **Bulk changes are not this worker's.** `lae bootstrap load` and `rewrite-refs` write no events. The worker does not look for records without events; an index rebuild covers them.

**Failures**

19. **Classification.** `classify` returns `unavailable` for a `QLeverError` without a status (connection refused, timeout) and for 401, 403, 408, 429 and 5xx; `rejected` for every other status. *Amended for issue #150:* an `UpdatesRefusedError` (the probe was rejected, §7.3) is `unavailable` whatever its status.
20. **Unavailable costs no attempt.** Nothing is written to Postgres; the same events are tried again after `backoff_seconds(n)` for the `n`-th consecutive unavailable outcome (1, 2, 4, … capped at 30 s), for as long as it takes. An outage of QLever never produces a dead letter.
21. **Rejected: find the event, count it alone.** When a batch of more than one event is rejected, no attempt is counted; `process_batch` sends its events one by one, in order, each with its own transaction of item 12, and stops at the first failure. An event that is rejected when sent alone, or whose translation raises at the head of a batch, gets one transaction: `attempts += 1`, `last_error`, and when `attempts` reaches `MAX_ATTEMPTS`, `status = 'failed'` and `processed_at = now()`. Later events stay pending and untouched. `run` then sleeps `backoff_seconds(attempts)` (1, 2, 4, 8 s) before the next batch, so a poisoned event holds the queue for at most about 15 s, then is a dead letter and the queue moves on. A `failed` event is never sent again by the worker.
    *Amended for issue #171 (§8.4, items 34–38):* "rejected when sent alone" now means a **confirmed** rejection: rejected alone, then `PROBE_UPDATE` acknowledged, then rejected alone again. Only that counts an attempt. A rejected probe counts nothing and is retried like an outage (item 20). The five attempts, the backoff of 1, 2, 4, 8 s and the rest of this item are unchanged, and an event whose translation raises is counted as before, with no probe.

**Process**

22. **One active worker.** `run` takes `pg_try_advisory_lock(SYNC_WORKER_LOCK)` on its one connection before it reads any event. If the lock is held it logs once and tries again every 5 s (`--once`: exit 1). If the connection is lost the process exits 1 without sending anything more; it never reconnects in-process, so a lost lock is never used. A supervisor restarts it.
23. **Latency.** A notification on `outbox` or the 1 s poll wakes the loop. With 50 or more pending events it takes a batch at once; otherwise it waits until 250 ms after waking and takes what is pending. A publish is in QLever within 1 s on an idle system.
24. **Token.** Every update carries the access token (`QLeverClient(settings.qlever_url, settings.qlever_update_url, token)`); the token never appears in a log line, `last_error` or `/metrics`.

## 4. Failure modes

| Situation | What happens | State afterwards |
| :-- | :-- | :-- |
| QLever down, timing out, 5xx, wrong token | `unavailable`; retried with capped backoff; `sync_unavailable_total` and `sync_lag_seconds` grow | events pending, attempts unchanged |
| QLever answered but the response was lost | as above; the batch is sent again | converges (item 17) |
| QLever rejects a combined update | events sent one by one | those before the bad one `done`; the bad one `attempts + 1` |
| An event rejected 5 times, or untranslatable 5 times | `failed`, `last_error` = `LAE-SYNC-00x …` | later events continue; the record is healed by its next event (item 5) or by a rebuild |
| Revision missing, stored bytes unreadable, unsupported kind | `LAE-SYNC-001` / `-002` / `-003`, counted like a rejection | as above |
| Worker killed before sending | nothing | events pending |
| Worker killed after QLever applied, before the commit | batch sent again after restart | same QLever state as one application |
| Postgres commit of item 12 fails | the worker exits 1 | events pending; sent again |
| Watermark changed under the worker | `stale_watermark`; catch-up; then the pending events | converges |
| Index rebuilt from an older export | catch-up replays `done` events above the new watermark | index holds every published version |
| Second worker started | waits for the lock (`--once`: exit 1) | one sender |
| Database connection lost | exit 1 | restart resumes from pending |
| No `LAE_QLEVER_URL` or token; watermark not an integer | exit `EXIT_CONFIG_ERROR` | unchanged |
| Two events of one record in one batch | two updates in order | the later version |
| Event with nothing to send | `done` without a request | unchanged index |

Known limit, to record in `docs/questions.md` and not to solve: if a worker's connection dies after it read a batch and before its HTTP request completes, and a new worker applies later events of the same record within that request's 30 s, the old request can land last and reinsert a retracted triple. The nightly audit (Step 2.18 / 3.10) is the backstop.

## 5. Required tests

All in `backend/tests/sync/`. A fixture used by every test that runs the worker empties `outbox_events` and removes `qlever_index_watermark` before the test, and restores the `sync_state` rows it found afterwards (the backend suite is serial; the worker reads the whole queue). Records are created through the real publish path (`tests/api/conftest.py` fixtures) unless a test needs rows publish cannot produce, which it inserts directly. No test sleeps to order events: crashes are injected by a client or a patched call that raises, time by patching the loop's sleep.

**The recording client** is a `QLeverClient` subclass whose `update` appends the text to a list and then succeeds, raises a scripted `QLeverError`, or raises after applying. In `test_batch.py` and `test_replay_property.py` it applies each update to a `pyoxigraph.Store`, which stands in for QLever's state. ## 7. Amendment: a `done` event that cannot be replayed (issue #150)

**Contract by:** Claude Fable 5.2 · **Date:** 2026-11-23 · **Issue:** #150 (critical; found in the review of PR #148, `docs/questions.md` Step 1.11 item 7).

Everything in §1–§6 stays in force except where this section says otherwise. Items are numbered on from §3 (25–33) and tests on from §5 (38–55).

### 7.1 The fault and the decision

`catch_up` replays the `done` events above a lowered watermark through `replay`, which raises on the first failure. `_catch_up_until_done` retries only an unavailable QLever, so an `EventError` (`LAE-SYNC-001`/`-002`/`-003`) or a rejection (a status `classify` calls `rejected`) leaves `run` with exit 1. The event is still `done` and above the watermark at the next start, so the worker never reaches a pending event again.

**Decision: skip the event as a dead letter and go on.** In catch-up the event's status goes from `done` to `failed`, the state the live path gives a poisoned pending event (item 21), and catch-up continues. The alternative of issue #150 (stop in a "rebuild required" state) is rejected. Reasons, data correctness first:

1. **Less divergence, never more.** After a skip, one record is behind in QLever (it holds an older published version). After a refusal, every record published since the lowered watermark is behind, and every later publish too, until a person rebuilds the index, which takes hours at scale and has no automation before Step 2.18. At every moment the records that differ under "skip" are a subset of those that differ under "refuse".
2. **The divergence is recorded, not silent.** The row is `failed` with its `last_error` in Postgres, `outbox_failed` is above 0, an error line is logged, and `lae sync-worker --failed` lists it (§7.5).
3. **It is repaired by existing means.** The record's next event is translated as `REPLACE` over the versions the dead letter left uncertain (items 4 and 5; `lae.sync.events` reads the status and needs no change): in the same catch-up if a later `done` event of the record exists, otherwise at its next publish. Any index rebuild repairs it too, because the export reads `records.data`.
4. **One rule for both paths.** A poisoned event is a dead letter and the queue moves on, whether it is met pending or in catch-up. Step 2.17's Health Dashboard needs one list (`status = 'failed'`), not a second state.

Marking an event `failed` is always safe for later events: its only effect on translation is that the record's next event is a `REPLACE`, which is always correct (item 6). Its cost is one record behind on an index that lacks the event.

**Not changed:** `lae.sync.events`, `lae.sync.qlever_client`, `lae.sync.errors` (no new code), `replay`, `replay_batches`, `apply_event`, `process_batch`, `_loop`'s handling of a batch result, the `--replay-after` command, the database schema (**no migration**). `replay` still raises on the first failure and writes nothing; Step 2.18 decides in its own contract what its replay into a second index does with such an event.

### 7.4 Invariants

25. **Catch-up never stops on one event.** For every `done` event above the watermark, `catch_up` ends with it either replayed (acknowledged, the watermark at or above its id) or `failed`, unless QLever is unavailable or the database fails. This replaces "through `replay`" in item 15: `catch_up` builds its batches as `process_batch` does (item 11, the same planning), over the `done` events with `watermark < id ≤ highest done id`, ascending, and handles failures itself as items 26–31 say.
26. **Permanent and transient are told apart; only a confirmed permanent failure is a dead letter.** In catch-up an event has failed permanently in exactly two cases:
    - **Untranslatable:** `translate_event` raises `EventError` for the event at the head of a batch (`LAE-SYNC-001`, `-002`, `-003`). Translation only reads committed rows, so it is not retried. An event whose translation raises further into a batch cuts the batch before it (item 11) and is judged when it is the head.
    - **Rejected, confirmed:** all of the following, in this order, with nothing else sent between: (a) the event's update, sent **alone**, gets a status `classify` calls `rejected`; (b) `PROBE_UPDATE` is then acknowledged (2xx); (c) the event's update, sent alone again, is rejected again. The error stored is the `LAE-SYNC-004` of (c).

    Everything else is transient and **writes nothing**:
    - A `QLeverError` that `classify` calls `unavailable` (no status: connection refused or a timeout; 401, 403, 408, 429, 5xx), on the combined update, on an event sent alone, on the probe, or on the second send: `catch_up` raises it unchanged.
    - The probe is rejected: `catch_up` raises `UpdatesRefusedError` with the probe's status and body. The endpoint refuses every update (a wrong update URL answering 404 or 405, a proxy, an incompatible server), so no event may be blamed.
    - The second send (c) is acknowledged: the event is replayed like any other (item 28).

    An outage or a refusing endpoint, however long, never produces a dead letter in catch-up. `_catch_up_until_done` retries both with `backoff_seconds` (item 20) for as long as it takes; `--once` exits 1.
27. **A rejected combined update is narrowed to one event.** When the combined update of a batch of more than one event is rejected, nothing is written and no event is blamed. `catch_up` sends the batch's updates one at a time, in id order, and after each acknowledgement (or event with nothing to send) writes the watermark to that event's id in its own transaction (item 28). The first event rejected alone goes through item 26. A batch of one event that is rejected has been sent alone already: that is (a).
28. **The watermark in catch-up.** Each acknowledged batch, or event sent alone, is followed by one transaction that writes the watermark to its highest id, compared on write as in item 14; a difference restarts catch-up from the new value. The watermark still never decreases through the worker and still means the highest id QLever has acknowledged to the live index (item 13). **A dead letter does not move it** (item 13, unchanged). This cannot hold catch-up open: "behind" means a `done` event above the watermark (items 14 and 15), and a `failed` event is not one. A dead letter at the top of the range therefore ends catch-up with the watermark below its id, and the next acknowledged batch moves it past.
29. **The dead-letter transaction.** One transaction: read the watermark `FOR UPDATE` and compare it with the value catch-up last read or wrote (a difference rolls back, writes nothing and restarts catch-up from the new value, so the event is judged again); then `UPDATE outbox_events SET status = 'failed', processed_at = now(), last_error = $2 WHERE id = $1 AND status = 'done'`, which must change exactly one row (else roll back and raise `RecordingError`). `attempts` is not changed: it counts the deliveries of item 21, and catch-up confirms by the probe and the second send, not by five attempts. Nothing else is written. The error line is logged after the commit.
30. **After a dead letter, catch-up plans again.** No update translated before the dead letter was recorded may be sent after it: the remaining events are translated again, from the watermark, in the next round. A later `done` event of the same record is then `unhealed` and becomes a `REPLACE` over the wider range (items 4 and 5); sent with its old `DIFF` text it would be applied to a version QLever does not hold. Events of other records are replayed as usual, in id order.
31. **Order and termination.** Events are still applied in ascending id order, and no event is sent while a `done` event with a lower id above the watermark is neither replayed nor `failed`. Every round of catch-up moves the watermark up, turns one `done` event into `failed`, or raises, so catch-up ends. After it no `done` event is above the watermark, and `process_batch` proceeds to the pending events (item 14).
32. **Crash safety.** A process death at any point of items 26–30 leaves the event `done` and above the watermark (it is judged again at the next start) or `failed`. A restart after the dead letter is recorded sends neither the event nor a probe for it. `failed` is never set without a translation error or the three steps of item 26, and never by `replay`, `apply_event` or `--replay-after`.
33. **What a catch-up dead letter leaves in QLever.** Precondition, as for all of catch-up: the index holds, for each record, the version its watermark implies (an index built from an export, or restored, with the watermark that belongs to it). Then the record of an untranslatable event keeps exactly the triples of the last of its versions QLever acknowledged, because nothing was sent for the event. The record of a rejected event keeps the same, or, if QLever applied part of the update it rejected, a state part-way to the event's `to_version`; the record's next event is a `REPLACE` whose retraction range starts at the dead letter's `from_version` and so covers both. If the cause is a missing or unreadable revision, the record's later events need that revision for their retraction range and become dead letters too, in catch-up and on the live path alike; the record stays at its old version until the revision is restored (§7.5). This limit is recorded for Step 2.18 (`docs/questions.md`, Step 1.11 item 8), not solved here.

**Operator action**, to be written into `deploy/README.md` as a section "Dead letters in the sync queue":

1. List them: `lae sync-worker --failed`. Each line names the record and the cause.
2. `LAE-SYNC-004` (QLever rejected the update; `body` holds its answer): the record is behind in QLever by at least one version. Publish the record again with any edit; its next event replaces all its triples. Or wait for the next index rebuild, which reads the current data.
3. `LAE-SYNC-001` or `-002` (a revision is missing or unreadable): the damage is in Postgres (`record_revisions`), not in QLever. Restore that row from a backup; until then every later event of the record is a dead letter too. A rebuild makes the index right for the record's current version in the meantime.
4. `LAE-SYNC-003`: the worker is older than the code that wrote the event. Deploy the matching version, then treat as 2.
5. `sync_updates_refused` in the log: fix `LAE_QLEVER_URL` / `LAE_QLEVER_UPDATE_URL` or the server. The worker recovers by itself and no event is lost.
6. Never set a `failed` row back to `pending` or `done` by hand (item 17: an old event sent on its own can undo a later one).

**For Step 2.17** (nothing to build now): `lae_outbox_failed`, and a `sync` component in `/health/ready` that is degraded, not failing, while a dead letter exists. The Health Dashboard lists the `failed` rows with the cause from `last_error` (catch-up ones marked by the `catch_up` parameter). Its "Retry" must enqueue a new replace of the record's current version, not set the old row `pending` (§6, item 17); its "Skip" is an acknowledgement and changes no status.

### 7.6 Failure modes (added to §4)

| Situation | What happens | State afterwards |
| :-- | :-- | :-- |
| Catch-up meets a `done` event QLever rejects (confirmed by the probe and a second send) | the event becomes `failed`; catch-up plans again and goes on | that record behind until its next event or a rebuild; every other record current; worker running |
| Catch-up meets a `done` event with a missing or unreadable revision, or an untranslatable kind | as above, with `LAE-SYNC-001`/`-002`/`-003` | as above; with a damaged revision the record's later events fail too |
| QLever down, timing out, 5xx or wrong token during catch-up, the probe or the second send | `catch_up` raises; retried with capped backoff | nothing written; every event still `done` |
| QLever rejects the probe | `UpdatesRefusedError`; retried with capped backoff; `sync_updates_refused` logged | nothing written; pending events wait until the endpoint is fixed |
| An event rejected once, then accepted on the second send | replayed | `done`, watermark moved |
| Worker killed between the rejection and the dead-letter commit | the event is judged again at the next start | `done`, then `failed` |
| Watermark changed while an event was being judged | the dead-letter transaction rolls back; catch-up restarts from the new value | converges |
| The dead letter is the highest `done` id | catch-up ends with the watermark below it | pending events are processed next |
| `--once` with a poisoned `done` event | it is dead-lettered, then one batch is processed | exit 0 for `empty` or `done` |
| `--replay-after` over a poisoned event | stops and prints the last id, as before | nothing written |

## 8. Amendment: live-path probe, exit codes, `--replay-after` errors, redaction (issue #171)

**Contract by:** Claude Fable 5.2 · **Date:** 2026-11-24 · **Issue:** #171 (critical; follow-ups of #150 and #151, `docs/questions.md` Step 1.11 items 9–12).

Everything in §1–§7 stays in force except where this section says otherwise. Items are numbered on from §7 (34–45) and tests on from §7.7 (56–72). Written against `main` at `2149544` (PR #170 merged).

### 8.1 The four faults and the decisions

1. **Live path, wrong endpoint.** An update URL that answers 404 or 405 rejects every update. Item 21 then dead-letters the pending events one at a time, about 15 s each, although no event is at fault. **Decision: the live path confirms a rejection exactly as catch-up does** (item 26: rejected alone, probe acknowledged, rejected alone again) before it counts an attempt. A rejected probe blames the endpoint: nothing is written and the worker retries with backoff. The five attempts stay. The second send is kept on the live path too, although five attempts already repeat the send: without it, an endpoint that refuses for a moment (a proxy answering 404 while QLever restarts) and is back when the probe arrives would cost the event an attempt.
2. **Restart loop on a persistent database error.** `run` exits 1 for every database error, and the unit restarts it every 5 s for ever. **Decision: a distinct exit code and `RestartPreventExitStatus=`, and no start limit.**
   - `StartLimitIntervalSec=`/`StartLimitBurst=` is rejected as the mechanism. systemd counts starts, not causes: a limit that stops a loop on our own SQL also stops the loop of a Postgres outage or of a Postgres that keeps crashing, and a unit that hit its start limit stays down after Postgres is back. That breaks the rule that a transient outage always recovers by itself. The unit therefore sets `StartLimitIntervalSec=0`, so the rule does not depend on the arithmetic of systemd's defaults (5 starts in 10 s) and `RestartSec=`.
   - The worker, which sees the cause, exits **4** only for a database error that cannot pass by itself (item 39: a closed list of SQLSTATE classes that mean "this statement is wrong for this schema or this data"). The unit does not restart after 4, nor after 2 (a refusal to start is not cured by starting again). Exit 1 restarts for ever, as today.
   - Everything not on the list stays exit 1, including errors of unknown persistence (a cancelled statement, a deadlock, a full disk, an internal error). A false "persistent" would stop sync until a person acts; a false "transient" costs a restart loop, which is today's behaviour. The list is therefore short.
   - No retry in-process: after an unexpected database error a new process is the only state we trust, and item 22 (never reconnect) is unchanged.
3. **`--replay-after` raises a traceback on a database error.** **Decision: one function classifies and reports a database error for every `lae sync-worker` command** (`run`, `--once`, `--replay-after`, `--failed`), with the same log lines and exit codes.
4. **A token cut in half is not redacted.** **Decision: redact the raw text first, then truncate, then encode**, in one helper used wherever QLever's answer is stored or logged.

### 8.3 Interfaces

```python
EXIT_FAILURE: Final = 1          # unchanged value
EXIT_CONFIG_ERROR: Final = 2     # unchanged value
EXIT_PERSISTENT: Final = 4       # new; 3 is lae.cli.EXIT_NOT_IMPLEMENTED

PERSISTENT_SQLSTATE_CLASSES: Final = frozenset({"0A", "22", "23", "42"})
# 0A feature not supported; 22 data exception; 23 integrity constraint violation;
# 42 syntax error or access rule violation (undefined table or column, insufficient privilege)

@dataclass(frozen=True, slots=True)
class Refusal:                   # the probe's answer, when QLever rejected the probe
    status: int
    body: str                    # token removed, then the first 2000 characters (item 44)

@dataclass(frozen=True, slots=True)
class BatchResult:
    ...                          # the six fields of §2.2, unchanged and in the same order
    refusal: Refusal | None = None

async def confirm_rejection(conn, client: QLeverClient, update: str) -> QLeverError | None
def database_failure(error: BaseException, *, closed: bool = False,
                     ) -> Literal["connection_lost", "persistent", "other"]
```

- `confirm_rejection` is called when `update`, the update of **one** event sent **alone**, has just been rejected (a status `classify` calls `rejected`). It sends `PROBE_UPDATE`, then `update` again, with nothing else between, and checks that the connection is open before each (`ConnectionLostError` otherwise). It returns `None` when the second send is acknowledged, and the `QLeverError` of the second send when that is rejected again. It raises `UpdatesRefusedError` (the probe's status and body) when the probe is rejected, and a `QLeverError` that `classify` calls `unavailable` unchanged, from either request. It writes nothing to Postgres and counts nothing.
- `database_failure` is pure. `connection_lost(error, closed=closed)` true → `"connection_lost"`. Otherwise an `asyncpg.PostgresError` whose `sqlstate` is a string starting with a member of `PERSISTENT_SQLSTATE_CLASSES` → `"persistent"`. Everything else → `"other"`: every other SQLSTATE (among them 57014 query cancelled, 40001, 40P01, 25006, classes 53, 55, 58, XX), a `PostgresError` without a `sqlstate`, and a client-side `asyncpg.InterfaceError` on an open connection. The order matters: a `FATAL` error is a lost connection whatever its class.
- **asyncpg raises some client-side argument errors as server errors** (note added for issue #176, no behaviour change). Under asyncpg 0.32 a query argument of the wrong type (a string for an `int` parameter) is not an `InterfaceError`: it is `asyncpg.exceptions.DataError`, a `PostgresError` with `sqlstate == "22000"` and no severity, raised by the client before anything is sent. `database_failure` classifies it by its class, 22, like any data exception: `"persistent"`, exit 4. That is right: the call is wrong and will be wrong the next time. Only a client-side `InterfaceError` (overlapping operations on one connection, for example) is `"other"` on an open connection.
- `BatchResult.outcome` keeps its five values. A refused probe is `outcome == "unavailable"` with `refusal` set; `refusal` is `None` in every other result.
- No new metric. `Metrics.observe` already adds 1 to `sync_unavailable_total` for an `unavailable` outcome, which now includes a refusal (as §7.5 says for catch-up). A probe is never counted in `updates_sent_total` or `BatchResult.updates_sent`; an acknowledged second send counts 1.

### 8.4 Invariants: the live path

34. **An attempt is counted only for a confirmed rejection.** On the live path a rejection is confirmed by these steps, in this order, with nothing else sent between: (a) the event's update, sent **alone**, gets a status `classify` calls `rejected`; (b) `PROBE_UPDATE` is then acknowledged; (c) the event's update, sent alone again, is rejected again. Then, and only then, the one transaction of item 21 runs (`attempts += 1`, `last_error`, `failed` at `MAX_ATTEMPTS`), with the `LAE-SYNC-004` of (c). Step (a) happens in two places: the combined update of a batch of exactly one event is rejected (that send was alone), or an event of a rejected batch of several is rejected when `_send_one_by_one` sends it. The rejected combined update of several events still blames nobody (item 21). An event whose translation raises at the head of a batch is counted as before; QLever is not asked and no probe is sent.
35. **One confirmation for both paths.** `process_batch`, `_send_one_by_one` and catch-up (`_CatchUp.judge`, item 26) all go through `confirm_rejection` for steps (b) and (c). There is no second implementation of the sequence. What differs is only what follows a confirmed rejection: one attempt on the live path, a dead letter at once in catch-up (item 29).
36. **A rejected probe blames the endpoint and writes nothing.** When (b) is rejected, `process_batch` returns `outcome = "unavailable"`, `failed_event = None`, `dead_lettered = False`, `refusal = Refusal(status, body)` of the probe's answer, `error` = the redacted text of the `UpdatesRefusedError`, and `done` and `updates_sent` for the events of the batch that were acknowledged and recorded before it (those stay `done`; QLever accepted them). No attempt is counted, `last_error` is not written, and the watermark is not moved past an unacknowledged event. `run` treats it as item 20: `outages += 1`, a log line `sync_updates_refused` at error with `status`, `body`, `consecutive` and `during="live"`, then `backoff_seconds(outages)` (1, 2, 4, … capped at 30 s), for as long as it takes. `--once` exits 1. A refusing endpoint, however long, never produces a dead letter and never changes `attempts`. Catch-up's `sync_updates_refused` line gains `during="catch_up"`.
37. **The other outcomes of the confirmation.**
    - (b) or (c) fails with an error `classify` calls `unavailable`: `outcome = "unavailable"`, `refusal = None`, nothing counted (item 20).
    - (c) is acknowledged: the event is recorded `done` by the transaction of item 12 like any acknowledged event, with `attempts` and `last_error` untouched; in `_send_one_by_one` the loop goes on with the next event of the batch.
    - The connection closes: `ConnectionLostError`, and nothing more is sent (item 22).
38. **Cost, and what does not change.**
    - No probe is sent unless an event was rejected alone: none on the normal path, none for an unavailable QLever, none for a translation error.
    - A confirmed rejection costs two more requests than before (the probe and the second send): at most 10 more for one dead letter. The probe matches no triple and changes none (test 55 measured it on QLever 0.6.0; test 63 measures that it does not raise `qlever_delta_triples`).
    - While the endpoint refuses, each round costs at most three small requests (the combined update, the head event alone, the probe) per backoff period.
    - `attempts` is never reset and never lowered: attempts counted before a refusal are kept, and the event needs `MAX_ATTEMPTS` confirmed rejections in total. `_loop` still sleeps `backoff_seconds(attempts)` (1, 2, 4, 8 s) after a counted attempt, so a poisoned event still holds the queue for about 15 s.
    - Idempotence (item 17) covers the second send: it is the same event sent again, in order.
    - A QLever that rejects the probe itself while an event is poisoned now holds the queue until the endpoint is fixed, instead of dead-lettering after 15 s. That is intended and is the rule catch-up already has; `sync_updates_refused` and a growing `sync_lag_seconds` are the signal.

### 8.5 Invariants: exit codes, the unit, the commands

39. **A database error is one of three kinds** (`database_failure`, §8.3), decided by the worker when it exits, for every error raised on its connection after it connected. A failure to connect at all (`sync_database_unreachable`) is always exit 1, whatever the reason (a wrong password or a database being restored included). *Narrowed by §9 item 46:* a `LAE_DATABASE_URL` that cannot be parsed is not a failure to connect but a setting error, exit 2.
40. **Exit codes.** One mapping for `run`, `--once`, `--replay-after` and `--failed`:

    | Code | Name | When | The unit |
    | :-- | :-- | :-- | :-- |
    | 0 | | stopped by `SIGTERM`/`SIGINT`; `--once` with `empty` or `done`; `--replay-after` finished; `--failed` | not restarted (`Restart=on-failure`) |
    | 1 | `EXIT_FAILURE` | may pass by itself, or unknown: the database is unreachable; the connection is lost (`"connection_lost"`); a database error of kind `"other"`; `RecordingError`; an `EventError` or `QLeverError` that reaches `run`; `--once`: the lock is held, the outcome is not `empty` or `done`, or QLever is unavailable or refuses updates; `--replay-after`: the lock is held, or the replay stopped on an event or on QLever | restarted after `RestartSec=5`, for ever |
    | 2 | `EXIT_CONFIG_ERROR` | refuses to start: `LAE_QLEVER_URL` or the token is missing; `LAE_DATABASE_URL` cannot be parsed (§9 item 46, every command); the metrics port cannot be bound (§9 item 47, `run`); the watermark is not a JSON integer; wrong command-line arguments | **not restarted** |
    | 4 | `EXIT_PERSISTENT` | a database error of kind `"persistent"` | **not restarted** |

    3 is `lae.cli.EXIT_NOT_IMPLEMENTED` and is not used by the worker. Exit 4 is never returned for an error `connection_lost` accepts, and never for a failure of QLever.
41. **The unit** `deploy/systemd/lae-sync-worker.service` has exactly these restart rules: in `[Unit]`, `StartLimitIntervalSec=0`; in `[Service]`, `Restart=on-failure`, `RestartSec=5`, `RestartPreventExitStatus=2 4`. There is no `StartLimitBurst=`, and 1 is never in `RestartPreventExitStatus=`. So no number of exits with code 1 ever stops the unit, and one exit with 2 or 4 leaves it `failed` until a person starts it.
42. **A transient outage recovers by itself.** Postgres down, restarting, crashing repeatedly, or ending the session: exit 1 each time, restarted every 5 s without limit, then the pending events are sent (items 16 and 22, unchanged). QLever down or refusing: the worker does not exit at all (items 20, 26, 36). The worker never retries a failed statement and never reconnects in-process (item 22, unchanged): for `"persistent"` and `"other"` alike it logs, closes its connection and exits, and the batch in flight stays pending.
43. **`--replay-after` and `--failed` report a database error like `run`.** One function is used by all of them. It takes the error, whether the connection is closed, and the command (`run`, `once`, `replay`, `failed`); it logs and returns the exit code:
    - `"connection_lost"`: `sync_connection_lost` at error, with `error`, `error_type`, `command`; returns 1.
    - `"persistent"`: `sync_worker_failed` at error, with `error` (token removed), `error_type`, `sqlstate`, `persistent=true`, `exit_code=4`, `command`, and the traceback (`exc_info`); returns 4.
    - `"other"`: the same line with `persistent=false` and `exit_code=1`; returns 1.

    The errors it covers are those `run` catches today: `asyncpg.PostgresError`, `asyncpg.InterfaceError`, `ConnectionLostError`, `OSError`. In no command does such an error leave `main` as an exception. `--replay-after` still writes nothing to Postgres (§2.2, item 32). Once it holds its connection (and the lock, when it takes one), it prints the last id applied on stdout exactly once on every exit, also after a database error, so a caller can restart from it, and after an error one line `lae sync-worker: replay stopped: …` on stderr. `--failed` prints no row on stdout when its query fails. `replay`, `replay_batches` and `apply_event` themselves are unchanged: they raise, the command reports.

### 8.6 Invariants: redaction

44. **Redact, then truncate, then encode.** The access token is removed from QLever's raw answer (`error.body`, or `str(error)`) before anything else is done to it: before it is cut to 2000 characters, and before it is put into JSON (`EventError.__str__` escapes `"`, `\` and non-ASCII characters, so a token containing one is not found in the encoded string). This holds wherever an error text is stored or logged: `last_error` on the live path and in catch-up, `BatchResult.error`, `Refusal.body`, the log lines `sync_event_failed`, `sync_dead_letter`, `sync_updates_refused` (live and catch-up), `sync_unavailable` and `sync_worker_failed`, and the stderr line of `--replay-after`. No part of the token reaches any of them, however short the piece a cut would have left. A `[redacted]` mark cut by the limit is fine.
45. **One limit, one helper.** One function in `lae.sync.worker` returns `_redact(body, client)[:REJECTED_BODY_CHARS]`. `rejected()` is always given its result (its own cut then changes nothing), and so are `Refusal.body` and the `body` of `sync_updates_refused`. `worker._BODY_CHARS` is removed: `lae.sync.errors.REJECTED_BODY_CHARS` (2000) is the only limit. The signature of `rejected()` and the form of `LAE-SYNC-004` are unchanged. Redacting the encoded string again afterwards is allowed as a second guard but is never the only redaction.

| unit `failed` with exit status 2; `refusing to start: LAE_DATABASE_URL is not a valid PostgreSQL URL: …` on stderr (§9) | same | `LAE_DATABASE_URL` cannot be parsed (no scheme, a port that is not a number, an asyncpg parameter it refuses); not restarted |
| unit `failed` with exit status 2; `refusing to start: cannot listen for metrics on <host>:<port>: …` on stderr (§9) | same | another process holds `LAE_SYNC_METRICS_PORT`, the port needs a privilege, or `LAE_SYNC_METRICS_HOST` is not an address of this host; not restarted |
| unit restarting every 5 s with exit status 1 and `sync_connection_lost` or `sync_database_unreachable` | same | Postgres is away (or its host name does not resolve); the worker comes back by itself |
| unit restarting every 5 s with exit status 1 and `sync_worker_failed` with `persistent=false` | same | a database error of unknown kind keeps coming back: read the traceback |

**The alarm for a stopped worker** is the unit state (`systemctl is-failed lae-sync-worker`) or a failed scrape of `/metrics`; alert on either. Nothing is lost while it is down: events stay `pending` and are sent after the start.

**Operator action**, to be written into `deploy/README.md` as a section "When the sync worker stops":

1. Exit status 4: read the `sync_worker_failed` line. SQLSTATE class 42 with an undefined table or column means the schema and the code do not match: run the migrations or deploy the matching version. `42501`: grant the `lae` role the privilege. Class 22 or 23: a row the worker reads or writes is wrong; report it as a bug with the traceback. Then `sudo systemctl start lae-sync-worker`.
2. Exit status 2: fix `/etc/lae/lae.env` (`LAE_DATABASE_URL`, or `LAE_SYNC_METRICS_PORT`/`LAE_SYNC_METRICS_HOST`, or stop the process that holds the port) or the `qlever_index_watermark` row of `sync_state`, then `sudo systemctl start lae-sync-worker`.
3. After a migration, or a restore into the live database, check the unit and start it if it is `failed`: a worker that met the schema half-way has stopped with 4.
4. Installing the changed unit: `sudo cp`, `sudo systemctl daemon-reload`, `sudo systemctl restart lae-sync-worker`.

Step 5 of §7.5 ("`sync_updates_refused` in the log: fix the URL or the server") now covers the live path too.

### 8.8 Failure modes (added to §4 and §7.6)

| Situation | What happens | State afterwards |
| :-- | :-- | :-- |
| The update URL answers 404 or 405 (or any `rejected` status) to everything, events pending | the probe is rejected; `unavailable` with `refusal`; `sync_updates_refused`; capped backoff | every event `pending`, `attempts` unchanged, no dead letter; resumes when the endpoint is fixed |
| A pending event QLever rejects, endpoint healthy | rejected alone, probe acknowledged, rejected again: one attempt; after five, a dead letter | as item 21 |
| A pending event rejected once, accepted on the second send | recorded `done` | no attempt counted |
| QLever unavailable at the probe or the second send | `unavailable`; retried with backoff | nothing counted |
| The endpoint starts refusing after an event had 2 attempts | refusals count nothing | `attempts` stays 2; 3 more confirmed rejections make the dead letter |
| Our SQL is wrong for the schema, a constraint is violated, a privilege is missing (classes 42, 23, 22, 0A) | `sync_worker_failed`, `persistent=true`; exit 4; the unit is not restarted | events pending; a person fixes the cause and starts the unit |
| Database connection lost; Postgres restarting or crashing repeatedly | exit 1; restarted every 5 s without limit | restart resumes from pending (unchanged) |
| A cancelled statement, a deadlock, a full disk, an internal error, a client-side `InterfaceError` | `sync_worker_failed`, `persistent=false`; exit 1; restarted | resumes if the cause passed; otherwise a restart loop every 5 s (known limit, `docs/questions.md` Step 1.11 item 11) |
| Missing setting; watermark not an integer | exit 2; the unit is not restarted (before: restarted every 5 s) | unchanged |
| `--replay-after` or `--failed` meets a database error | classified and logged as in `run`; exit 1 or 4; `--replay-after` prints the last id applied | nothing written |
| QLever's answer holds the token across character 2000 | the token is removed before the cut | no part of it stored or logged |

## 9. Amendment: malformed database URL and metrics-port errors (issue #176)

**Date:** 2026-11-25 · **Issue:** #176 (critical; follow-ups of the review of PR #174, findings 4–6 and the ruling on tests 65 and 66). The decisions are the issue's; this section records them.

### 9.1 The faults and the decisions

1. **Contract wording (no behaviour change).** Tests 65 and 66 assumed that a query argument of the wrong type is a client-side `InterfaceError`. Under asyncpg 0.32 it is `asyncpg.exceptions.DataError` with SQLSTATE 22000 and no severity, so `database_failure` calls it `"persistent"` and the worker exits 4. §8.3 now says so, and §8.9 describes tests 65 and 66 as they are. The docstring of `connection_lost` no longer gives "wrong argument type" as an example of a client-side `InterfaceError`.
2. **A malformed `LAE_DATABASE_URL` left as a traceback.** The three places that connect (`run`, `--replay-after`, `--failed`) caught only `OSError` and `asyncpg.PostgresError`. The URL is parsed twice before a socket is opened: by SQLAlchemy in `lae.bootstrap.common.asyncpg_dsn` (`nonsense` and a URL without a scheme raise `sqlalchemy.exc.ArgumentError`; `postgresql://u@h:notaport/db` raises `ValueError`), then by asyncpg (`?sslmode=bogus` raises `asyncpg.ClientConfigurationError`, an `InterfaceError` and a `ValueError`). Every one of these left `main` as a traceback and exited 1, so the unit restarted the worker every 5 s for ever. **Decision: a URL that cannot be parsed is a setting error: exit 2 with one stderr line, for every command.** A host name that does not resolve (`postgres://%zz`, `socket.gaierror`) and a server that refuses the connection are not parse errors: they stay `sync_database_unreachable`, exit 1.
3. **A metrics port that cannot be bound reported as a lost connection.** `sync_metrics.serve` runs after the lock is taken; its `OSError` (address in use, permission denied, address not available) reached `run`'s `DATABASE_ERRORS` clause and was logged `sync_connection_lost`, exit 1, restarted every 5 s for ever. **Decision: catch `OSError` from `sync_metrics.serve` only; close the connection, one stderr line, exit 2.** The bind stays where it is.

### 9.3 Interfaces

```python
class DatabaseUrlError(ValueError): ...    # LAE_DATABASE_URL cannot be parsed; the message holds
                                           # neither the URL nor its password

async def connect(database_url: str) -> asyncpg.Connection
```

- `connect` turns the SQLAlchemy URL into a DSN (`asyncpg_dsn`) and calls `asyncpg.connect`. It raises `DatabaseUrlError` for `sqlalchemy.exc.ArgumentError` or `ValueError` from `asyncpg_dsn`, and for a `ValueError` from `asyncpg.connect` (asyncpg parses the DSN synchronously, before any I/O; `ClientConfigurationError` is a `ValueError`). ### 9.4 Invariants

39 (amended). **A database error is one of three kinds** (unchanged), for every error raised on the worker's connection after it connected. A failure to connect to a URL that parses (`sync_database_unreachable`: the host does not resolve, the connection is refused or times out, the login fails, the database is being restored) is always exit 1. A URL that cannot be parsed is item 46, exit 2.

46. **A `LAE_DATABASE_URL` that cannot be parsed refuses to start.** For `run`, `--once`, `--replay-after` and `--failed` alike: exactly one line on stderr, `lae sync-worker: refusing to start: LAE_DATABASE_URL is not a valid PostgreSQL URL: <the parse error>`, nothing on stdout, no traceback, no `sync_database_unreachable` and no `sync_worker_started`, exit 2 (`EXIT_CONFIG_ERROR`). The unit does not restart after 2 (item 41): the URL will not mend itself. No part of the URL's password is in stderr, stdout or any log line. The QLever client the command opened is closed. `run` installs its signal handlers only after it has connected, so a command that refuses to start leaves none behind.
47. **A metrics port that cannot be bound refuses to start.** The listener is still started after the advisory lock is taken (so a second worker waiting for the lock does not hold the port) and before the first catch-up (§7.5). Nothing has been sent to QLever and nothing written to Postgres; `run`'s cleanup closes the connection, as on every exit, which releases the lock. It is not `sync_connection_lost` and not `sync_worker_failed`. An `OSError` anywhere else is still a lost connection (item 22).

## 10. Amendment: failures to connect, and events that commit late (issue #178, Slice C)

**Date:** 2026-11-25 · **Issue:** #178 (Phase 1 core review, Slice C: publish → sync) · **By:** Claude Fable 5.2, who also reviewed §9 and PR #177 here (both were written by Opus from issue #176 without a larger-model contract or review).

Everything in §1–§9 stays in force except where this section says otherwise. Items are numbered on from §9 (48–49) and tests on from §9.6 (77–82). Written against `main` at `c10cb0b`.

### 10.1 What the review found

1. **§9 against issue #176: one defect.** #176 decided that only an error "raised by connect's DSN parsing" is exit 2, and that socket errors stay exit 1. §9.3 implemented that as "a `ValueError` from `asyncpg.connect` is a parse error", on the ground that asyncpg parses before any I/O. That is not true of every `ValueError`: `ssl.SSLCertVerificationError` is an `OSError` **and** a `ValueError`, and it comes from the TLS handshake with a server that was reached (`sslmode=verify-ca` or `verify-full`: an expired or replaced server certificate, a host name that no longer matches). The worker printed `refusing to start: LAE_DATABASE_URL is not a valid PostgreSQL URL: certificate verify failed …` and exited 2, so the unit never started it again, also after the certificate was renewed. **Decision: an `OSError` from `asyncpg.connect` is never a parse error** (item 48). The rest of §9 matches #176: the three commands share `_open_connection`; nothing is widened to `Exception`; the password is redacted; the metrics listener is bound after the lock and before the first catch-up, and only its `OSError` is exit 2.
2. **§9.7, first point: reachable, and decided.** The example there is wrong (`ConnectionDoesNotExistError` is a `PostgresError` and was already caught). What does escape: a plain `asyncpg.InterfaceError` set by the protocol after the socket opened (the server asks for an authentication method asyncpg does not implement, such as GSSAPI without the `gssapi` module; a SCRAM server signature that does not verify), and an `asyncpg.InternalClientError` (`TargetServerAttributeNotMatched` when the URL has `target_session_attrs` and no host qualifies, as during a failover; `ProtocolError`). Each left `main` as a traceback; Python exits 1, so the unit did restart, but with no `sync_database_unreachable` line and, for `--replay-after` and `--failed`, no stderr line. **Decision: they are failures to connect to a URL that parsed: `sync_database_unreachable`, exit 1** (item 48). Each depends on the server's configuration or state, not on this host's settings alone, so a restart can find it gone; that is the rule a refused login already follows (item 39).
3. **The flaky `test_the_worker_keeps_running_past_a_poisoned_done_event[start]`: the test, not the worker.** The listener answers as soon as it is bound, several database round trips before catch-up sends its first update. The test scraped once and then asserted that the update had been sent. Under load the scrape won. Delaying catch-up by 0.3 s made the old test fail every time; the worker is right to serve before catch-up (§7.5). A failure also left the worker blocked in the test's client, so the test reported a `TimeoutError` from its cleanup, not the assertion. The test now waits for the update, then scrapes, and releases the client in its cleanup.
4. **Ids are assigned before commit (from Slice B).** The live path is sound: a batch is the pending events by id, so an event that becomes visible late is taken next; the watermark does not go down (item 13, `test_the_watermark_never_decreases`); events of one record cannot be reordered, because the id is assigned under the record's row lock (item 10); the worker assumes no gap-free sequence (a publish retried after a deadlock leaves one). Catch-up replays by id above the watermark and is sound **if the watermark it starts from covers no event the index lacks**. `lae bootstrap export-nt` did not guarantee that: it took `max(outbox_events.id)` in its snapshot, and a publish whose insert was still open then, with a lower id, was in neither the export nor the range above the watermark (recorded as open in `docs/questions.md`, Step 1.11 item 5, in the review of PR #148). Once the worker marks that event `done` on the old index, nothing gives it to the rebuilt one, and the record's next `DIFF` is applied to the wrong version: a published version silently missing from the index. **Decision: fix it at the source** (item 49); the worker is not changed.

### 10.3 Interfaces

```python
# lae.sync.worker
CONNECT_ERRORS: Final = (OSError, asyncpg.PostgresError, asyncpg.InterfaceError,
                         asyncpg.InternalClientError)

# lae.bootstrap.export
SETTLE_TIMEOUT_MS = 30_000
async def _settled_watermark(conn: asyncpg.Connection, dsn: str) -> int
```

- `connect` (§9.3, corrected): an `OSError` from `asyncpg.connect` passes through unchanged, whatever else it is; only then is a `ValueError` a `DatabaseUrlError`. `ClientConfigurationError` is still a `DatabaseUrlError` (asyncpg raises it only while it reads the DSN and the TLS settings, before any I/O).
- `_open_connection` reports every `CONNECT_ERRORS` as §9.3 says it reports `OSError` and `PostgresError`. It still catches nothing broader.
- `_settled_watermark(conn, dsn)`: `conn` is inside a `REPEATABLE READ` transaction that has run no query. A second connection (`dsn`) opens a transaction, sets `lock_timeout` to `SETTLE_TIMEOUT_MS` and takes `LOCK TABLE outbox_events IN SHARE MODE`; while it holds the lock, `conn` runs `SELECT coalesce(max(id), 0) FROM outbox_events`, its first query, which fixes its snapshot; then the second transaction ends and its connection is closed. `asyncpg.LockNotAvailableError` becomes `BootstrapError` (the export exits 1 and writes no `<out>.meta.json`).

### 10.4 Invariants

48. **A failure to connect on a URL that parsed is exit 1.** Completes item 39 as amended in §9.4 and narrows item 46: `EXIT_CONFIG_ERROR` only for an error raised before any I/O (SQLAlchemy's or asyncpg's reading of the URL). Every error of `asyncpg.connect` in `CONNECT_ERRORS` is `sync_database_unreachable` at error with `error`, `error_type` and `command`, the stderr line `lae sync-worker: database unreachable: …` for `--replay-after` and `--failed`, no traceback, no `sync_worker_started`, exit 1 (restarted every 5 s). This includes a failed TLS handshake (certificate verification), an authentication method asyncpg does not have, a SCRAM signature that does not verify, and no host with the `target_session_attrs` asked for.

13 (completed). The watermark does not promise that every lower id is **applied yet**, but every `done` or `failed` event at or below it is accounted for in the live index, and every pending one will be sent. Whoever sets the watermark from outside the worker must keep that: **a watermark `W` may be stored for an index only if the index reflects every event with id ≤ `W` that has committed or will commit.**

49. **The export's watermark covers no event that had not committed.** `export-nt` takes its snapshot at a moment when no transaction holds an uncommitted change to `outbox_events` (`SHARE` conflicts with the `ROW EXCLUSIVE` lock each insert and update keeps until its transaction ends). So every event with id ≤ the watermark is committed and in the snapshot with its record's version, or rolled back; and every event inserted afterwards gets a higher id (the sequence only grows; `outbox_events.id` is an identity column, so the id is taken inside the `INSERT`, after its table lock) and commits after the snapshot, so catch-up and `replay(after_id=watermark)` send it. Publishes and the worker's recording transaction wait for the lock to be released: the time the open inserts need to commit plus one query. Writers also queue behind the *waiting* request, so the wait is bounded: after `SETTLE_TIMEOUT_MS` the export fails and names the cause. Step 2.18 (blue/green) builds from this export and inherits the guarantee; if it takes a watermark any other way, it must keep item 13.

15 (note). With item 49, "an index rebuilt from an older export" is caught up completely whatever was in flight when the export was taken. A watermark set by hand (`build-index --watermark`, a restored index directory) is the operator's promise of item 13.

### 10.5 Failure modes (added to §4, §7.6, §8.8 and §9.5)

| Situation | What happens | State afterwards |
| :-- | :-- | :-- |
| TLS to Postgres fails verification (expired or replaced certificate, host name mismatch) | `sync_database_unreachable` with `error_type` `SSLCertVerificationError`; exit 1; restarted every 5 s | unchanged; the worker connects once the certificate is right |
| The server asks for a login asyncpg cannot do, or no host has the session attributes asked for | `sync_database_unreachable` (`InterfaceError`, `TargetServerAttributeNotMatched`); exit 1; restarted | unchanged |
| A publish is open (event inserted, not committed) when `export-nt` starts | the export waits for it, then takes its snapshot; other publishes wait those milliseconds | the event is in the export, at or below the watermark |
| A transaction keeps a change to `outbox_events` open for more than 30 s during `export-nt` | the export fails with `lae bootstrap export-nt: a transaction has held a change to outbox_events open …`, exit 1; publishes that queued behind it continue | no metadata file; run the export again |
| An event becomes visible after a higher id is `done` | the live path sends it next; the watermark stays | converges (item 13) |
