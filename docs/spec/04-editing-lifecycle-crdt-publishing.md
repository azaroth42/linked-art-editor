## 4. Editing Lifecycle, CRDT Collaboration & Publishing

### 4.1 Shared CRDT Draft vs. Publish Boundary

| Phase | Trigger | Validation | Storage Target | Indexed in QLever? |
| :---- | :---- | :---- | :---- | :---- |
| **Live CRDT Sync (Autosave)** | Continuous binary CRDT updates over WebSocket | Lenient live client-side JSON-Schema badges | `crdt_drafts / crdt_updates` (active records only) | No |
| **Validate** | On-demand or pre-publish | Full JSON-Schema + SHACL against projected JSON-LD | Transient | No |
| **Publish / Commit** | Explicit Editor-only action ("Publish Changes") | Must pass all Hard Errors; Soft Warnings require confirmation | `records`, `entity_labels`, `record_revisions`, `outbox_events` (clears draft) | Yes (sub-second via worker) |

Micro-batching outbox events in the sync worker (e.g., flushing every 250ms or 50 records) protects QLever's delta-triple layer from write storms during bulk edits or heavy concurrent publishing.

* **Bundled Transactional Publish of Dependent Stubs:** When a draft references newly minted, unpublished inline stubs (e.g., a new `Person` or `Place` created mid-form), publishing validates and commits the primary record together with all dependent unpublished stubs atomically in a single PostgreSQL transaction and emits outbox events for the entire bundle.  
* **5-Day Abandoned Draft Expiry:** A scheduled reaper automatically discards CRDT drafts with no edits for 5 consecutive days (resetting modified records back to their live published revision or deleting unpublished new draft records) to prevent stale draft accumulation. Human Editors can monitor approaching expirations and click **Extend TTL** or **Inspect & Publish** from the Active Drafts & Review Inbox.

### 4.2 Real-Time CRDT Co-Editing Architecture (Yjs + pycrdt)

* **CRDT Stack:** Clients run Yjs in TypeScript connected over WebSockets to pycrdt and pycrdt-websocket (Rust-backed, Yjs wire-compatible) inside the FastAPI backend, providing simultaneous multi-cursor editing, live presence/awareness indicators, and offline resilience.  
* **Graph-Safe CRDT Schema (Avoiding Array Interleaving):** Repeated Linked Art properties are modeled as keyed Y.Maps rather than ordered Y.Arrays—embedded sub-nodes (Name, Dimension, LinguisticObject, AttributeAssignment) are keyed by their skolemized UUID IRI, and entity-reference lists (classified_as, made_of, member_of) are keyed by target URI. Concurrent additions merge cleanly and duplicate identical assertions deduplicate automatically. Collaborative prose fields (content) use Y.Text for character-level co-editing, while scalar fields use LWW Y.Map entries.  
* **Order Preservation (`_order`):** Keyed Y.Maps discard source order, which is meaningful for `Name.part`, the display order of identifiers and statements, and any unprofiled arrays that must round-trip verbatim. Every keyed entry therefore carries a fractional-index `_order` LWW value assigned on hydration and on insert; projection sorts by `_order` and uses the IRI/key only as a tie-break, so round-tripped documents keep their original order while concurrent inserts still merge without interleaving conflicts.  
* **Deterministic Projection & Lossless Round-Tripping:** On validation or publish, the Y.Doc is projected deterministically into canonical Linked Art JSON-LD arrays (sorted by `_order`, then IRI/key). Any unprofiled JSON-LD properties remain intact in the root Y.Map and serialize back verbatim.  
* **Low-Concurrency Room Topology (No Redis Needed):** With 10–30 concurrent users, a single dedicated CRDT WebSocket worker process (or single async FastAPI instance) manages all active rooms in memory without needing Redis pub/sub fan-out. Rooms hydrate lazily from PostgreSQL on first open and evict from memory when idle. `pycrdt-websocket` is still a beta-stage release (used in production by Jupyter), so an early spike validates it under load and the room manager sits behind a narrow interface so a Yjs-wire-compatible sidecar (y-websocket / Hocuspocus) remains a drop-in fallback.  
* **Process Topology & Publish Path:** The deployment consists of discrete processes: `api` (REST, content negotiation, `/mcp`), `crdt-ws` (the single-process room manager), `sync-worker`, `scheduler` (draft reaper, QA sweeper, backup runner), `embedder`, local LLM server, QLever, and PostgreSQL. Because rooms live in memory in `crdt-ws`, validate and publish requests that need the live Y.Doc are routed from `api` to `crdt-ws` over an internal RPC rather than reading room state from another worker; `crdt-ws` also persists every update to `crdt_updates` synchronously so room state is reconstructable by any process after a restart.  
* **Offline Stale-Base Reconnection Guard (`draft_epoch`):** Every active `crdt_draft` room tracks a monotonic `draft_epoch` and `base_version`. If a client makes offline Yjs edits while another Editor publishes revision `N+1` (clearing the previous draft room), FastAPI rejects blind binary replay against the superseded epoch on reconnect and opens a **Rebase Offline Changes Modal**. For v1 the modal presents the offline edits as a read-only structured change list (reusing the semantic diff format) with per-change **Apply** / **Discard** against the fresh room, rather than attempting a full automatic three-way merge, so changes are reconciled safely rather than silently corrupted or lost.

### 4.3 Provenance, Diffs & Review Workflows

* **Human-Readable Semantic Diffs:** Revisions compare parsed entity patterns (e.g., *"Changed `produced_by -> carried_out_by` from Unknown to Rembrandt van Rijn"*) rather than raw JSON Pointer paths. The backend emits structured typed change objects (`add_ref`, `remove_ref`, `update_literal`) rather than hardcoded English prose so the client (and Mermaid Visual Diff labels) render in the user's active locale. Includes an optional Mermaid Visual Diff diagram highlighting added, removed, and modified CRM subgraphs.  
* **Revision History Time-Travel & 1-Click Revert:** Dedicated **Revision History Browser** allowing editors to inspect any historical version of a record, compute semantic and Mermaid Visual Diffs between arbitrary revisions (`rev M` vs. `rev N`), and execute a 1-click **Revert to Revision N** (committing a new forward revision restored losslessly from the stored zstd JSON-LD snapshot/patch while keeping history strictly append-only).  
* **Anchored Discussions:** Comment threads (`comment_threads` / `comments`) attach to a record URI or a specific skolemized sub-node ID (e.g., questioning a specific `Dimension` or `AttributeAssignment`). Supports `@user` and `@agent` mentions alongside `open`/`resolved` thread states. Typing `@agent` in an anchored thread can launch a scoped turn in the Embedded Agent Chat Workbench targeting that specific sub-node.  
* **Shared Live Draft (Collaborators Edit, Editors Publish):** Each actively edited record has one shared live CRDT draft room. Any authenticated user with edit_draft permission can co-edit in real time; only users with the publish (Editor) role can inspect the semantic diff against the live published revision and publish changes (or discard/revert the draft back to the published revision).  
* **Multi-Author Attribution:** The CRDT session records all contributing user IDs since the last publish so the committed record_revision credits every collaborator alongside the publishing editor. Interactive chat-driven edits record dual attribution—crediting both the instructing human user (`AI Agent (via <user>)`) and the underlying LLM provider/model identifier.  
* **First-Class `AttributeAssignment`:** UI affordance allowing catalogers to attach provenance (who asserted it, when, and bibliographic source) to disputed fields like attribution, dating, or classification. Local LLM data translations automatically attach `AttributeAssignment` (`assigned_by`) provenance recording the translation activity, local model identifier/version, timestamp, and `source_content_hash`.  
* **Active Drafts & Review Inbox (5-Day Expiry Triage):** Dedicated Editor triage dashboard listing every open CRDT draft across the system, filterable by contributor (human vs. AI agent), SHACL validation status (`0 errors`, `warnings`, `violations`), and remaining time before the 5-day inactivity reaper fires, with 1-click **Extend TTL**, **Inspect & Publish**, or **Discard** actions.  
* **Watchlists & Notification Inbox:** Wikidata-style watchlists allowing editors to watch individual records, `Set`s, or Vocabulary Value Sets and receive in-app notifications on draft edits, publishes, merges, `@mentions`, and Tier 2 agent escalations.
