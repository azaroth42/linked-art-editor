# ADR-0025: Validation engine details the guide left open

**Status:** Accepted · **Date:** 2026-11-22 · **Decided by:** Claude Fable 5.2 as implementer of Phase 1 Step 1.9, amended and accepted by the critical-step reviewer under the owner's delegation (Rob Sanderson may override) · **Recorded by:** Claude · **Reviewed by:** Claude Fable 5.2 · **Amended by:** ADR-0028 (the schema check ignores the ids of embedded nodes; the `uri` format accepts an `id` that RDF can percent-encode, reported as the warning `LAE-RDF-006`)

## Context
Step 1.9 fixes the pipeline (JSON Schema, then Python rules and SHACL), the diagnostic shape `{code, path, severity, params, message_en}` and the code families. Implementing it needed nine choices the guide and spec §5 do not make. Each is small; together they define what Step 1.10 (publish), Step 1.19 (validation drawer) and Phase 3 (agents) see. All are refinements inside decisions C1 to C3; none changes a locked decision. The review amended items 1, 3, 4, 5 and 6 and added item 9.

## Decision
1. **Expansion failures have codes of their own, area `RDF`.** `LAE-RDF-001` (`BlankNodeError`), `-002` (`OwnershipError`), `-003` (`InvalidIRIError`), `-004` (`InvalidLiteralError`), `-005` (any other `ExpansionError`). All are violations with the exception text in `params.detail`. The exception does not say where in the document the term is, so the path is `""` (the record) except where the cause can be found again in the JSON-LD: a root `id` that is not the record URI (`/id`), and a string that is not valid Unicode or a number that is not finite (its own pointer). Malformed IRIs and date-times do not reach expansion in `validate`, because the schema's `format` checks report them first with their paths, so in practice a root-located `LAE-RDF-*` is rare and is about the record as a whole (a nested `@context`, a bad record URI). `detail` is developer text and may quote an internal node IRI; the endpoints that return it are authenticated editor endpoints, not public serializations.
2. **`LAE-RULE-005` is added for an invalid `TimeSpan` bound**; `LAE-RULE-001` stays the ordering rule, as the guide words it. The retired shapes `LAE-SHACL-009` (validity) and `-010` (order) so map to two rule codes with two messages, rather than one code with a `reason` parameter. In practice the schema's `format: date-time` check reports an invalid bound first (`LAE-SCHEMA-format`).
3. **One meaning of "valid date-time" everywhere.** The JSON Schema format check, the rules and RDF expansion accept the lexical form of `lae.rdf.sanitize.VALID_DATETIME` (signed years, optional time zone). The schema check and the rules also require a real date and time (month, day of that month, `24:00:00` as the only hour 24, no leap second, zone offset at most 14:00) written in ASCII digits; `VALID_DATETIME` alone accepts the digits of any script, because Python's `\d` does (`docs/questions.md`, Step 1.9). Years are astronomical in the proleptic Gregorian calendar (XSD 1.1 and ISO 8601: `0000` is 1 BCE). Bounds are compared as instants on the UTC timeline, with exact fractional seconds; a value without a zone is compared as UTC.
4. **`LAE-RULE-002` (EDTF) checks only strings that claim to be EDTF**: a `Name` or `Identifier` in a `TimeSpan`'s `identified_by` that is `classified_as` `http://id.loc.gov/datatypes/edtf`. It is a warning. A `TimeSpan`'s other names are display labels in free text, and some in the corpus ("1503-1506", "2011-02-03 - 2011-05-01") look like EDTF and are not, so a heuristic would warn on good data. The syntax check is `lae.validation.edtf` (levels 0 to 2), written here because the Python EDTF packages pull in unrelated dependencies. **Its reference is edtf.js, not the prose specification:** it accepts exactly the strings `parse()` of the `edtf` npm package 4.12.0 accepts with default options, since that is the parser the editor uses (Step 1.18) and a string one side accepts and the other rejects would surface as a client/server disagreement. The module is a transcription of that package's grammar; `backend/tests/validation/data/edtf_js_cases.json` holds edtf.js's verdict on about 3,200 strings and a test compares each (the review compared 220,000 generated strings and found no difference; the first version, written from the specification, disagreed with edtf.js on about 6,200 of the first 22,500). The differences from the specification, in both directions, are listed in the module docstring.
5. **A referenced entity's class comes from `entity_labels.type`, else from the `type` the reference declares.** Without the fallback every reference to an entity that has no row yet (imports, the CLI, the golden corpus) would fail every `sh:class` constraint. `entity_labels` wins when both exist, with one exception that follows from the class hierarchy: a row that says only `Type` does not contradict a reference that declares a subclass of `Type` (`Material`, `Language`, `MeasurementUnit`, `Currency`), and the entity then has both classes. `lae bootstrap aat-labels` stores every AAT concept as `Type`, so without the exception every `made_of` and every `Name` `language` that points at AAT failed its shape as a violation once the labels were loaded. A reference of one of the four subclasses is also a `crm:E55_Type` in the data graph, which has no `rdfs:subClassOf` triples and no inference. When several references to one entity declare different classes, all of them count (not the first in document order).
6. **SHACL results about a node the record does not own are dropped.** Of a referenced entity the data graph holds only its class, so any conclusion a shape draws about it is about missing data. This cannot hide a finding about the record's own data as long as a constraint on what a property refers to is a property shape whose focus node is the referring node; `profiles/shapes/README.md` rule 6 requires that. A focus node in the record's namespace that is not one of its references is never dropped, even if the path index should lack it.
7. **Internal node IRIs do not appear in diagnostics.** A node is addressed by its JSON Pointer; `params.value` is given only for literals and references. A path may name a property that is absent when the absence is the finding (`/dimension/0/unit`). SHACL reports a value once per focus node however many ways lead to it, so one result becomes one diagnostic for every place the value is found (the same wrong actor on two parts of a production gives two), in path order.
8. **`message_en` is rendered from `frontend/public/locales/en/errors.json`**, the one place English messages live (decision C3), with `{name}` placeholders filled from `params`. Without an entry it falls back to the validator's own text.

9. **Diagnostics are identified by `code` + `path`, and both are deterministic** for a given document and given `entity_labels` rows: they do not depend on dict or set order, on the hash seed, or on the order the triple store iterates in (checked over the corpus under three hash seeds and over 8,000 mutated records). Several findings may share one `code` + `path` (they differ in `params`); accepting the pair accepts them all. Paths are positions in arrays, so an edit that inserts or removes an earlier item moves them: a warning accepted before such an edit has to be accepted again.

Also: JSON Schema `format` is asserted for `date-time` and `uri` only, `uri` being exactly what expansion accepts, so a malformed `id` is reported with its path by the schema instead of at the root by `LAE-RDF-003`. `anyOf` / `oneOf` diagnostics carry `params.cause`, the first error in the alternative whose `type` the instance has.

## Consequences
- Step 1.10 can treat every refusal by `expand_to_ntriples` as a violation from `validate`, and key accepted warnings by `code` + `path` (item 9). It must validate with a session, so that `entity_labels` and deleted targets are consulted.
- Step 1.19 focuses the slot whose path is the longest prefix of a diagnostic's path. A path may name an absent property (item 7), and `""` means the record: such a diagnostic has no slot and belongs in a general section of the drawer.
- Step 1.18's `EdtfWidget` must classify the EDTF string it stores with the IRI in item 4 if it wants it checked (`docs/questions.md`, Step 1.9). It should ask `parse()` whether a string is EDTF: the constructor `edtf()` reads five or more digits as a Unix time and refuses an interval whose start is after its end, neither of which the server does. If the `edtf` package is pinned at another version, regenerate `edtf_js_cases.json` with it and re-run `tests/validation/test_edtf.py`.
- A record whose embedded nodes carry ids of their own (ADR-0021) is located correctly by SHACL diagnostics, but the vendored JSON Schema rejects `id` on an embedded `Name` (`object-3.json`), so such a record does not reach SHACL at all (`docs/questions.md`, Step 1.9).
- New shapes need an `errors.json` entry; a test fails otherwise.
