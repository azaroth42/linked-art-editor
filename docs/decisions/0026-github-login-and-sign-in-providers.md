# ADR-0026: GitHub login and several sign-in providers

**Status:** Accepted · **Date:** 2026-11-22 · **Decided by:** Claude Opus 5.5 (follow-up to Phase 1 Step 1.7 at the owner's request; spec §8.1 lists GitHub among the supported providers; conventions §8.2 for the details the spec leaves open) · **Recorded by:** Claude

## Context
The owner wants to sign in with an existing GitHub account. Step 1.7 built OpenID Connect only (ADR-0020, decision E1). GitHub is OAuth 2.0, not OpenID Connect: it has no discovery document and no ID token, and the user is identified by calling its REST API with the access token. Nothing says how several providers share the login routes, how a GitHub account maps to `users`, which e-mail address counts, or who may sign in.

## Decision
1. **Providers.** `lae.auth.providers.LoginProvider` is an Authlib OAuth 2.0 client plus `identify(token) → LoginIdentity(subject, display_name, email)`. There are two: `oidc` (Step 1.7, unchanged) and `github`. Any subset may be enabled; they are ordered `oidc`, `github`, and the first enabled one is the default. `GET /auth/providers` (public) lists `[{id, display_name}]`, default first. `GET /auth/login/{provider}` and `GET /auth/callback/{provider}` run one provider; `GET /auth/login` and `GET /auth/callback` keep working for the default provider. An id that is not an enabled provider is 404 `LAE-AUTH-011`. Sessions, the `Viewer` default role and deactivation are as in ADR-0020 for every provider.
2. **Redirect URIs.** Each provider returns to `/auth/callback/<id>`, except that `oidc` keeps returning to `/auth/callback`, so identity-provider registrations made for Step 1.7 stay valid. It does not matter whether the login started at `/auth/login` or `/auth/login/<id>`.
3. **GitHub flow.** An OAuth App; authorization at `https://github.com/login/oauth/authorize` with `state` and PKCE `S256` (GitHub supports only `S256`); code exchange at `https://github.com/login/oauth/access_token` with `client_secret_post` and `Accept: application/json`. Scopes `read:user user:email`, plus `read:org` only when `LAE_GITHUB_ALLOWED_ORGS` is set (without it GitHub hides private organization memberships). GitHub reports a refused exchange with HTTP 200 and an `error` field; that is 400 `LAE-AUTH-007` with the same `error`. A 5xx, an unreachable GitHub, or a non-200 REST API answer is 502 `LAE-AUTH-008`. The access token is used only during the callback and is not stored.
4. **User mapping.** `users.subject = "github:<numeric id>"` from `GET https://api.github.com/user`, never the login, which its owner can rename and someone else can then register. OIDC subjects stay the bare `sub` (rows from Step 1.7 are unchanged). `display_name` is `name`, else `login`. `email` is the primary address from `GET /user/emails` only if GitHub has verified it, else `NULL`; an unverified address is never stored. Accounts are never linked by e-mail: the same person signing in through OIDC and GitHub is two users.
5. **Who may sign in.** `LAE_GITHUB_ALLOWED_USERS` (logins, case-insensitive) and `LAE_GITHUB_ALLOWED_ORGS` (organizations whose *active* members may sign in, from `GET /user/memberships/orgs/{org}`; a pending invitation, 403 or 404 is not membership) are comma-separated. Being on either list is enough. They are checked at the callback before any `users` row is written; a rejected account gets 403 `LAE-AUTH-012` (`{provider}`). With neither set, any GitHub user may sign in, as `Viewer`.
6. **Settings.** `LAE_GITHUB_CLIENT_ID` and `LAE_GITHUB_CLIENT_SECRET` (`SecretStr`). The provider is enabled only when both are set; `lae api` refuses to start when only one is (`AuthConfigError`), as it does for `LAE_OIDC_ISSUER` without a client id.
7. **SPA.** `/login` reads `GET /auth/providers` and shows one button per provider, linking to `/auth/login/<id>?next=…`. Labels are `common` keys `login.provider.<id>` for the ids it knows (`oidc`, `github`) and `login.provider_named` (`Sign in with {name}`) otherwise; `login.none` when the list is empty.

## Consequences
- An installation can use GitHub as its only identity provider with an OAuth App and two environment variables; no identity provider has to be run.
- GitHub compares the redirect URI with the app's registered callback URLs (exactly, unless wildcard matching is enabled for that URL), and the redirect URI is built from the origin the browser used, so each origin users sign in from (`http://localhost:8000`, a Vite dev server, production) must be registered.
- A login on `LAE_GITHUB_ALLOWED_USERS` stops matching when its owner renames it, and a login given up can be taken by someone else; the organization list is the better control for groups. Roles and deactivation follow the numeric id, so they survive renames.
- An organization that restricts OAuth App access hides its members from an app it has not approved; its members are rejected until an organization owner approves the app.
- A GitHub user without a verified primary address has `users.email = NULL`; grant roles by `subject` (`docs/dev-setup.md`).
- Step 1.7's ADR-0020 and decision E12 are unchanged; this extends E1 (OIDC *and* GitHub OAuth 2.0 for humans).
