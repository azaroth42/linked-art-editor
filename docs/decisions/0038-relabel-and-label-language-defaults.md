# ADR-0038: `lae relabel` recomputes the default labels; AAT and vocabulary defaults follow the label language

**Status:** Accepted · **Date:** 2026-11-24 · **Decided by:** Rob Sanderson (owner's answers to items 5–9 of `docs/questions.md` "Owner decision, 2026-11-23 (derived `_label`)", issue #162, and to items 11, 12 and 14, 2026-11-24), specified by the Step 1.19b contract (`docs/contracts/1.19b-relabel.md`, Claude Fable 5.2), implemented by Claude Opus 5.5 · **Recorded by:** Claude

## Context
ADR-0036 made `LAE_LABEL_LANGUAGE` an environment setting and left everything already stored alone when it changes: `entity_labels.default_label` kept the label chosen under the old language until each record was next published, and rows that do not come from a record (the AAT seed, a vocabulary term's curated `label_override`) kept an English default under every setting. The owner overturned both: an administrator must be able to backfill the default labels, and AAT and vocabulary defaults must follow the setting.

## Decision
1. **A CLI command, nothing else.** `lae relabel [--dry-run] [--batch N] [--report PATH]` (`lae.labels.relabel.relabel`) is run by the operator who edits the environment file and restarts the processes, as for `lae migrate` and `lae bootstrap`. No HTTP route, permission, job table or scheduler job; there is no language option (it relabels under `Settings.label_language`). Phase 2 Step 2.17 may call the same function behind `manage_system` with an `admin_audit_log` row; until then the audit trail is the log (`relabel_started`, `relabel_progress`, `relabel_finished`, `relabel_failed`, with the operator's login name and no label text). Exit 0 when every row was visited, 1 when rows stayed locked or the run failed; running it again completes the work.
2. **One column.** The only write is `UPDATE entity_labels … SET default_label = …` in raw SQL over one `asyncpg` connection. `records`, the revisions, the outbox, the drafts, `qa_findings`, QLever and `crdt-ws` are not touched, so **published records keep their stored `_label`** (raw JSON-LD, revisions, `rdfs:label`) until each is next published. Rewriting them would be a publish of every record (a version, revision and outbox event each; every open draft refused as stale); what users see already follows `entity_labels` or is computed at read time. A batch republish, if ever wanted, belongs with Phase 2's edit batches (Step 2.8) after the rebuild of Step 2.18.
3. **`updated_at` is kept.** The ORM would move it (`onupdate`), and it feeds the autocomplete overlay: a relabel adds no literal that QLever's index lacks, and moving it for most of 1M rows would put them all in the overlay. A record published since the last index build is then found by its new-language default label only, until the next build.
4. **Skip locked, and read the record after the lock.** Each batch pages URIs without a transaction (`_page`), then in a READ COMMITTED transaction locks the `entity_labels` rows with `FOR UPDATE SKIP LOCKED` (`_lock`), reads the records of the locked local rows in a statement of its own (`_records`), and writes (`_apply`). A publish of a record takes the same row lock for its upsert (contract 1.10 §3 item 13), so it either committed before the lock (and the read sees it) or writes its own label after the batch. The run never waits for a row lock, never locks `records` or the drafts, and is outside the publish lock order; a publish waits for it at most one batch. Rows it could not lock are retried after a pause (5 passes, 2 s); a row still held is `skipped_locked`, one that disappeared is `gone`.
5. **The registry touch.** At the end of a real run (not a dry run, not after an exception) one `vocabularies.updated_at` is set to `clock_timestamp()`, which moves `registry_version`, so every running `api` rebuilds its vocabulary bundle from the new default labels and every browser refetches it, without a restart.
6. **AAT and sidecar rows** (`lae.labels.defaults.default_label_from_labels`): the label in the label language (exact tag, else the first regional tag), else the label in the source's own language (`SOURCE_LANGUAGES = {"aat": "en"}`, a fact about the dataset), else the row is left alone. The AAT seed (`lae.bootstrap.aat.aat_row`) and `lae relabel` use the same function, so they agree. **The Phase 1 AAT CSV holds English names only**, so with it every AAT default stays the English preferred name under every setting; the rule takes effect when AAT rows carry other languages (Phase 2 Step 2.14 must use the same function and extend `SOURCE_LANGUAGES`).
7. **A vocabulary term with a `label_override`** (`lae.vocab.service._resolved`): its default label is the label in the label language from the override laid over the `entity_labels` labels; else the override's `en` (the entry every `LangMap` must have: the curated label of last resort, not a second label language); else the row's default label; else the URI. So on a non-`en` installation a label in the configured language beats a curated override that exists only in English (owner, 2026-11-24). A term without an override keeps the row's default label, which already follows the setting. Under `en` every valid override gives what it gave before.
8. **The bundle's `ETag` covers the label language** (`bundle_etag(version, label_language)` hashes `version|label_language`), and the in-process cache is reused only when both match, so a browser holding a bundle built under another language gets 200, not 304. `registry_version` is unchanged (Step 2.2 keys its rules on the registry alone). Every ETag changes once when this is deployed: one refetch.

## Alternatives considered
- **An admin endpoint now.** It would need a permission, an audit row and a job model before Step 2.17 provides them; the operator who changes the setting already has a shell.
- **Rewriting `records.data`.** Without a revision it breaks contract 1.10 §3 item 9 (the stored JSON-LD is what `records.etag` hashed); with one it is a mass publish (above).
- **`SELECT … FOR UPDATE` without `SKIP LOCKED`, or reading the record in the page query.** The first waits behind publishes and enters the lock order; the second reads the record from a snapshot taken before the row lock, so a concurrent publish's label could be overwritten with a stale one.
- **Keeping the override's `en` first.** Overturned by the owner: a French installation would show curated English labels as defaults even where a French label exists.
- **A language option on the command.** It would let the stored defaults disagree with the processes' setting.

## Consequences
- After `lae relabel`, reference labels, autocomplete, the drafts list and the vocabulary bundle follow the new language; the Public Reader title already did. Raw JSON-LD, revisions and SPARQL keep the stored `_label` until the next publish of each record, and the first `draft/diff` may show that one root `_label` change (ADR-0036).
- The command must run after `api` and `crdt-ws` were restarted; run before, or while one process has the old value, it leaves a mixture that a second run repairs. Nothing detects it.
- `build_bundle`, `cached_bundle`, `get_bundle` and `search_terms` take the label language as a required argument; `lae.api.vocab` passes `Settings.label_language`.
- Contracts 1.10, 1.11, 1.14 and 1.19a are unchanged; publish, `lae.sync` and `lae.crdt` were not edited.
