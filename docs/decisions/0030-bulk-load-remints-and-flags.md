# ADR-0030: A bulk load re-mints record URIs, loads and flags schema failures, and rejects what RDF cannot hold

**Status:** Accepted · **Date:** 2026-11-22 · **Decided by:** Rob Sanderson (owner decisions of 2026-11-22 on the Step 1.12 questions; items marked *orchestrator* were decided by the orchestrator under his delegation) · **Recorded by:** Claude · **Implemented by:** Claude Fable 5.2 · **Supersedes:** ADR-0024

## Context
Step 1.12 built `lae bootstrap load` under three assumptions that it put to the owner (`docs/questions.md`, Step 1.12): a record keeps the URI it arrives with (ADR-0024); a record that fails JSON Schema is skipped; a record that RDF expansion refuses stays in PostgreSQL and is left out of QLever. Measured on the 1M synthetic set, the second skipped 37 % of the input and the third left 14 records in one store and not the other. The owner decided all three the other way, and asked for stub normalization at load as well.

## Decision

### 1. Every record of an installation has the URI `<base_uri><uuid>`; a bulk load re-mints the rest
- A loaded record whose root `id` is exactly `<base_uri><uuid>` keeps it, and that UUID is its `records.id`. Any other record gets a new UUIDv7 and the URI `<base_uri><uuidv7>`. So `records.uri == record_uri(records.id)` for every row, and `lae.ids.record_id_from_uri` / `owner_of` recognise every record and node IRI again.
- The source URI is appended to the root `equivalent` as a reference `{"id": <source URI>, "type": <the record's type>}`, unless an entry with that `id` is already there. It is therefore in the public JSON-LD and in QLever (`<record> la:equivalent <source URI>`).
- Internal node IRIs the input already carries under the source URI (`<source>/node/<uuidv7>`: an export of an editor) move to `<new>/node/<uuidv7>`. A reference the record makes to itself is rewritten too.
- **Aliases.** Table `record_aliases (alias_uri text primary key, record_id uuid → records.id on delete cascade, source text, created_at)` holds every source URI (`source = 'bootstrap'`). `lae.aliases` has the lookups: `resolve_alias`, `resolve_aliases`, `resolve_record_id` (own URI, node IRI or alias). An alias is unique: a source URI that is already an alias or a record URI is a duplicate and is not loaded again, which is what makes a repeated load a no-op.
- **References.** After all records are in, a second pass over the loaded rows replaces every `id` below the root that is an alias by the URI of the alias's record: plain references, references inside embedded nodes, and `equivalent` entries of other records. Not rewritten: `@context`; `access_point` (an address to fetch, not a reference); and an alias of the record itself, which is its own `equivalent` entry. A root `id` that is a node IRI of a local record (`<base_uri><uuid>/node/<uuid>`) is rejected (`LAE-BOOT-002`): `lae.ids` already resolves it to the record that owns the node, so it cannot also be the alias of another record. The pass looks aliases up per batch in `record_aliases`, so aliases of earlier loads resolve as well and no map of 10M URIs is held in memory.
- **Redirects.** The editor can only be asked for URIs on its own host (the host of `LAE_BASE_URI`). A `GET`/`HEAD` for an alias on that host, at any path, is answered `301` with the canonical `/id/{uuid}` (`?format=` kept). The lookup uses the configured host, not the request's `Host` header, tries both `http` and `https`, and runs only when the request would otherwise be a 404, so an alias cannot shadow a route or a record. Aliases on other hosts cannot be redirected by the editor; the institution redirects them, and they resolve in data.

### 2. Load and flag
- A record that fails JSON Schema is loaded if it can be expanded to RDF. Its violations go to `qa_findings`, created now by migration `0008` with exactly the columns Phase 3 Step 3.10 specifies (`id`, `code`, `severity` enum `info|warning|error`, `record_id`, `node_id` null, `params` JSONB, `status` enum `open|claimed|resolved|dismissed`, `claimed_by`, `resolved_by`, `sweep_run_id`, `created_at`, `updated_at`). Step 3.10 adds `curation_campaigns` and the sweeps; it no longer creates this table.
- One finding per record and diagnostic code: `code` is the validation code (`LAE-SCHEMA-<keyword>`), `severity = error`, `status = open`, `node_id` null, `sweep_run_id` the id of the load run, and `params = {"source": "bootstrap", "count": n, "diagnostics": [{"path", "params"}, …]}` with the first 10 occurrences. No message text is stored (conventions §4). The unique index `(code, record_id, node_id)` treats a missing `node_id` as a value (`NULLS NOT DISTINCT`), so Step 3.10's upsert key works for whole-record findings.
- Such a record cannot be published again until it validates, because publish runs the same schema check. Nothing else marks it. **Publish (Step 1.10) closes the findings:** a publish only succeeds on a record that validates, so in its transaction it sets the record's open `LAE-SCHEMA-*` findings to `resolved` (`resolved_by` the publisher, `updated_at = now()`). Nothing does this before Step 1.10 exists.
- `LAE-BOOT-005` (skipped for JSON Schema) is retired and not reused.

### 3. Reject what cannot be written to RDF (*orchestrator*, Step 1.12 item 3)
The load expands every record with `lae.rdf.expand_to_ntriples`, the production expansion, before writing it. A record it refuses (`LAE-BOOT-007` at stage `load`) is not loaded at all and is listed in the report. PostgreSQL and QLever therefore hold the same records. This costs one expansion per record at load on top of the one at export (measured in `docs/spikes/S6-bootstrap.md`). Also still rejected, as before: input that is not a JSON object (`001`), ids that cannot be repaired (`002`, `003`), and a root `type` that is not a Linked Art record class (`004`): there is no schema, profile or editor for it. `LAE-BOOT-010` reports a record whose preparation raised anything unexpected, so one record cannot stop a load.

The second pass cannot make a loaded record unexpandable: it replaces one valid foreign IRI by another that is neither the record's URI nor one of its node IRIs, and removes `_label`; the classification of ADR-0021 looks at an object's keys and `type`, not at its `id`, and ignores `_label`. `export-nt` still checks and reports every record.

### 4. Normalize stubs after the load (*orchestrator*, Step 1.12 item 4)
The same second pass removes `_label` from every reference whose target has an `entity_labels` row (`lae.labels.normalize_refs`; spec §3.2, ADR-0006, ADR-0019), as publish does. References to targets with no row keep their label. Loading sidecar labels first (`lae bootstrap aat-labels`) lets concept references be normalized in the same run; `lae bootstrap rewrite-refs` runs the pass again at any time.

### 5. The second pass only touches rows a bulk load wrote, and is restartable
It updates `records.data` and `etag` without a revision or an outbox event, like the load itself, so it is limited to rows that are still `version = 1`, active, with no `record_revisions` row and no open draft; a record published through the editor is never changed by it. The `UPDATE` repeats these conditions and compares the `etag` it read, so a draft opened or a publish made while the pass runs wins. While a load is unfinished, `sync_state.bootstrap_rewrite_since` holds the time it began; the next load's pass starts from there, and `lae bootstrap rewrite-refs` covers every bulk row. Between the two passes the data is consistent but not final: references still carry source URIs, each of which is an alias. A load or `rewrite-refs` on a database that already has a QLever index must be followed by `export-nt` and `build-index`; both commands report `index_rebuild_needed` when that is the case. One load runs at a time per database (advisory lock).

### 6. A record's own class is accepted in its `equivalent`
`event.json` and `abstract.json` allow only `Activity` and `LinguisticObject` references in `equivalent`, although they are also the schemas of `Event`, `Period` and `PropositionalObject` records. With item 1 every re-minted record of those classes would fail validation on the entry the load itself added, and could never be published. `lae.validation.validate_schema` therefore does not report a `const`/`enum` violation on the `type` of a root `equivalent` entry whose `type` is the record's own. The vendored schema files are not edited; the defect is reported upstream (`docs/questions.md`, Step 1.12). ADR-0028 does not cover this case: it removes the `id` of embedded nodes and nested repeats of the pinned `@context` before the schema check, but the `equivalent` entry is a reference, so its `id` and `type` stay and the class error would still be raised (checked on the merged ADR-0028 code: `tests/validation/test_schema.py`).

## Alternatives considered
- **Keep source URIs (ADR-0024).** Rejected by the owner: it leaves two kinds of record URI, and everything that maps a SPARQL subject to its record needs a second code path.
- **UUIDv5 of the source URI as the record id.** Deterministic across reloads without a table, but not time-ordered (A6), and the alias table is needed anyway for redirects and for references.
- **A staging table for pass 1, with the final rows copied into `records` by pass 2.** No dead tuples in `records`. But `record_aliases.record_id` is a foreign key, so aliases could only be written with the final rows; a crash in pass 2 would then leave records whose references point at URIs that were minted and never loaded, with the map to repair them gone if the staging table was unlogged. Writing final ids and aliases in pass 1 and updating in place keeps every intermediate state resolvable; the cost is one `VACUUM` of `records`.
- **Rewrite references in pass 1 from an in-memory map.** Needs every source URI before the first record is written: a third read of the input and a 10M-entry map in every worker.
- **Flag unexpandable records instead of rejecting them.** They would be in PostgreSQL and not in QLever: invisible to search, backlinks and delete protection, and reported by the consistency audit forever.
- **One `qa_findings` row per schema error.** Step 3.10 keys findings by `(code, record_id, node_id)`; two errors with the same code in one record would collide, and some records have hundreds.

## Consequences
- The corpus loads completely (276 of 276 with the 32 LUX records; the 92 known schema failures are flagged: 60 and the 32 LUX records, which carry LUX's own `_links`). On the 1M synthetic set the load keeps the 37 % it used to skip; timings are in `docs/spikes/S6-bootstrap.md`, "ADR-0030 rerun".
- `records.data` of a re-minted record differs from its source by its root `id` and one `equivalent` entry, and by the ids of references to other loaded records. The round trip to the source's own JSON-LD is no longer byte-exact for these; nothing is lost, since the source URI is in `equivalent`.
- External links to a source URI keep working only where the institution redirects them (other hosts) or the editor serves that host.
- `owner_of` and `record_id_from_uri` hold for every record, so Phase 2 Step 2.7 needs no special case. Code that receives a URI from outside (imports, pasted references, reconciliation) should call `lae.aliases.resolve_record_id`.
- **Publish (Step 1.10) must resolve aliases:** a reference whose `id` is a `record_aliases.alias_uri` (pasted, or picked from a sidecar label row whose URI was later loaded as a record) is replaced by the record's URI before `normalize_refs` (`lae.aliases.resolve_aliases`, one query). Otherwise QLever gets a link to a URI that is no subject, and backlinks and delete protection miss it.
- Later import paths (Phase 2) must write `record_aliases` rows for re-minted records with their own `source`, and merges may add aliases; a record can have several.
- Not done here: `ref.unresolved_target` findings for references that keep their `_label` (the Step 3.10 sweep), and rewriting references to another record's *node* IRIs under its source URI (none seen in the corpus).
- Register entry A6 cites this ADR; ADR-0024 is superseded.

*Amended 2026-11-23 (owner):* label-only `entity_labels` rows (`source <> 'local'`) whose URI becomes the alias of a loaded record are deleted by the load and by `rewrite-refs`, so autocomplete offers the record once.
