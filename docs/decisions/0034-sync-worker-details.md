# ADR-0034: Details of the sync worker (translation, ordering, failures, watermark, replay)

**Status:** Accepted · **Date:** 2026-11-23 · **Decided by:** the Step 1.11 contract (`docs/contracts/1.11-sync-worker.md`, Claude Fable 5.2), implemented by Claude Opus 5.5 (Rob Sanderson may override) · **Recorded by:** Claude

## Context
Phase 1 Step 1.11 builds `lae sync-worker`, which applies `outbox_events` to the live QLever index (decisions A2, A13, A14; spec §3.3). The guide step says what the worker does in outline: diff two revisions, fall back to `DELETE WHERE` on drift, batch up to 50 events into one update, count failures toward a dead letter after 5 attempts, advance `sync_state.qlever_index_watermark`. It leaves open, or states loosely, what decides between a diff and the fallback, what happens to the events of a batch QLever refuses, how a dead letter affects the record's next event, what the watermark promises, and how a second index is filled (Step 2.18). Each answer decides whether QLever can ever drift from Postgres, so the contract fixed them; this ADR records where they depart from or add to the guide.

## Decision
1. **The worker trusts `payload.drift_check`.** Publish computes it (ADR-0033 item 1) from the index build's versions in `sync_state`; the worker does not compare context or expander versions itself. A publish event is `INSERT` when `from_version` is NULL, `REPLACE` (`DELETE WHERE` per owned subject, then `INSERT DATA` of every `to_version` line) when `drift_check` is true, the stored lines of `from_version` are empty, or the previous event of the record is a dead letter (item 6), and `DIFF` (`DELETE DATA` of old − new, `INSERT DATA` of new − old) otherwise. Any doubt selects `REPLACE`, which is always correct; `DIFF` is the optimisation (fewer delta triples, Spike S1 §3).
2. **Only revisions are read.** Triples and JSON-LD come from `record_revisions`, the record URI from `records.uri`; `records.data` is never read and nothing is expanded. A missing revision is an error (`LAE-SYNC-001`), not a reason to re-expand the current data: publish back-fills the revision of a bulk-loaded version (ADR-0033 item 2), and a translation must be the same whenever it is made.
3. **A `delete` event retracts with `DELETE WHERE` over the owned subjects** (`owned_subjects` of each JSON-LD and the subjects of each stored N-Triples line, over the versions QLever may hold), not with `DELETE DATA` of the stored lines, which would miss triples an older expander wrote.
4. **Unavailable and rejected are told apart.** No answer, a timeout, 401, 403, 408, 429 and 5xx mean QLever is unavailable: nothing is written to Postgres, no attempt is counted, and the same events are retried after 1, 2, 4, … seconds (capped at 30) for as long as it takes. An outage never produces a dead letter. Any other status is a rejection (`LAE-SYNC-004`, with the first 2000 characters of the answer). QLever 0.6.0 answers 403 for a missing or wrong access token and 400 for a syntax error (measured, `docs/questions.md`, Step 1.11).
5. **A rejected batch is retried event by event**, each acknowledged event recorded in its own transaction, stopping at the first failure. Only the event rejected alone, or whose translation fails at the head of a batch, gets `attempts + 1`; at 5 it is `failed` and the queue moves on.
6. **Strict id order; a poisoned event holds the queue for about 15 s.** No event is sent while one with a lower id is pending, so a record's events apply in commit order. The worker sleeps 1, 2, 4, 8 s between the attempts of a rejected event, then dead-letters it. **The record's next event heals it:** it is translated as `REPLACE` over the owned subjects of every version from the dead letter's `from_version` on, so QLever holds exactly the new version although the failed event was never applied. A dead letter is never sent again by the worker; requeueing one is a later admin action and must not simply set `pending`.
7. **No coalescing.** Two events of one record in a batch stay two updates in id order; a net diff across them would break item 8.
8. **Acknowledge, then record; idempotent replay.** Events become `done` only after QLever answers 2xx, in one transaction with the watermark. A crash leaves events pending with their updates possibly applied, wholly or in part; sending them again in order converges, because applying the updates of events `a … b` to any state from `v_{a−1}` to `v_b` (or part-way through an update in that range) leaves exactly `v_b`.
9. **The watermark** is the highest event id QLever has acknowledged to the live index. Only the worker's batch transaction and `catch_up` write it; it never decreases through the worker and a dead letter does not move it. It does not promise that every lower id was applied (a transaction that commits late leaves a lower pending id, applied next). It is **compared on write**: read before translating and again `FOR UPDATE` when recording; if someone changed it, the batch is not recorded (`stale_watermark`) and the worker catches up. **Catch-up:** when the watermark exists and a `done` event has a higher id (an index rebuilt from an older export, a restored index directory), those events are replayed before any pending event. A watermark that is not a JSON integer stops the worker (`EXIT_CONFIG_ERROR`).
10. **One connection, exit on its loss.** One `asyncpg` connection takes `pg_try_advisory_lock(0x1AE051C0)`, listens on `outbox`, and makes every read and write. A second worker waits for the lock (`--once`: exit 1). If the connection is lost the process exits 1 and never reconnects in-process, so a lost lock is never used; the supervisor restarts it. The `/metrics` listener renders a snapshot the loop refreshes, so it needs no connection of its own.
11. **`lae sync-worker --replay-after ID [--through ID] [--target-url URL] [--target-update-url URL]`** applies the `done` events above `ID` to a target and prints the last id applied, writing nothing to Postgres. `replay` and `apply_event` take any `QLeverClient`, so Step 2.18 replays into a second index with them. With a target URL the lock is not taken.

## Alternatives considered
- **Recompute drift in the worker** (compare `sync_state` versions itself). Two places would decide the same thing and could disagree; publish already holds the record's lock and knows whether the loaded version expanded.
- **Re-expand `records.data` when a revision is missing** (the guide's wording). The data may be several versions newer than the event, so the update would depend on when it is translated, and replay would not be idempotent.
- **`DELETE DATA` for `delete` events.** Misses triples written by another expander version; `DELETE WHERE` over owned subjects cannot touch another record (ADR-0021).
- **Count every failure toward the 5 attempts** (the guide's wording). A QLever restart of a minute would dead-letter a whole queue of good events.
- **Count an attempt for every event of a rejected batch.** One bad event would dead-letter up to 49 good ones.
- **Skip a poisoned event at once and continue.** Later events of the same record would be applied as diffs against a version QLever does not hold; the heal in item 6 needs the strict order.
- **Coalesce a record's events in a batch into one net diff.** Fewer triples sent, but a partially applied or repeated batch would no longer converge (item 8).
- **Set the watermark unconditionally.** A rebuild that lowered it while a batch was in flight would be overwritten, and the done events above the new value would never reach the rebuilt index.
- **Reconnect in-process.** The advisory lock is lost with the connection; a reconnecting worker could run alongside a second one that took it.

## Consequences
- Every later writer of `delete`, `merge` and `split` events (Steps 2.4, 2.6) must write the event under the record's row lock (strict id order is commit order per record), and a `delete` must set `from_version` to the last published version with its revision present. `merge` and `split` are `LAE-SYNC-003` until those steps extend `lae.sync.events`.
- Step 2.18 builds the green index from an export at a watermark, replays with `replay(conn, green_client, after_id=watermark)`, and swaps; it must not send an old event on its own (`apply_event` is for a caller that replays in order).
- A record whose event is dead-lettered is stale in QLever until its next publish or a rebuild; the nightly audit (Steps 2.18, 3.10) is the backstop. A known race (a worker that lost its connection while a request was in flight) is recorded in `docs/questions.md`, Step 1.11.
- QLever's `qlever_delta_triples` grows by 2 for a changed triple of the built index (and by 1 when the old triple was itself inserted by an update): the rebuild trigger counts churn.

Evidence: `backend/tests/sync/` (`test_events.py`, `test_batch.py`, `test_replay_property.py` with Postgres and a pyoxigraph store; `test_qlever_integration.py` against QLever 0.6.0, run locally only, never in CI).
