# ADR-0036: The root `_label` is derived from the primary name, on read, in the installation's label language

**Status:** Accepted · **Date:** 2026-11-23 · **Decided by:** Rob Sanderson (owner decision 2026-11-23, `docs/questions.md` "Owner decision, 2026-11-23 (derived `_label`)"), specified by the Step 1.19a contract (`docs/contracts/1.19a-derived-label.md`, Claude Fable 5.2), implemented by Claude Opus 5.5 · **Recorded by:** Claude

## Context
PR #155 (Step 1.19) found that a record's root `_label` was whatever its creator typed: no profile slot edits it, it did not follow title edits, and a stub created from the dialog had none, so its parent could not be published (`LAE-SCHEMA-required`, `LAE-PUB-003`). The owner decided that the root `_label` is derived from the record's primary name, follows every title edit, cannot be edited, and comes from the dialog's name for a stub; and (at resume) that the preferred language is a setting of the installation, not the constant `en`.

## Decision
1. **Derive on read; never write into the CRDT.** `_label` is a pure function of the draft's names and the label language, applied where a draft becomes JSON-LD: `Room.snapshot()` on the server (`with_derived_label(project(doc), room.label_language)`; draft validation, publish and `draft/diff` all read it), `new_record_data` for a new record's `records.data`, and `projectDraft(doc, labelLanguage)` in the browser (raw inspector, validation drawer, publish dialog snapshot). No Yjs update, no observer, no undo entry; drafts and stubs from before this step are correct at their next read. `lae.projection.project` / `hydrate` are unchanged (R17 stands).
2. **Selection and normalization** (`lae.labels.extract.primary_name`, `lae.labels.derive`, mirrored in `frontend/src/crdt/derivedLabel.ts` and `langtags.ts`): among the usable names of the root `identified_by` (type `Name`, string `content` with a non-whitespace character), the first Primary Name (`aat:300404670`, any AAT spelling) in the label language, else the first Primary Name, else the first name. A name's language is its first `language` entry: a well-formed `notation` decides alone (shortened through ISO 639-2), else an AAT id of the 57-language table, else `und`. The label is the content with Python's 29 whitespace code points trimmed and collapsed to one space; no Unicode normalization, case folding or truncation. Without a usable name the document's own `_label` is kept (an absent one stays absent), and the schema's `LAE-SCHEMA-required` / publish's `LAE-PUB-003` apply as before.
3. **The label language is an environment setting**, `LAE_LABEL_LANGUAGE` (`Settings.label_language`, default `en`): normalized by `normalize_tag` and accepted only if it is one of the 57 tags of `AAT_LANGUAGE_TAGS`, so a region or script (`en-GB`), `und` or an unmapped language stops every process at start. It is read once, by `api`, `crdt-ws` and `lae bootstrap`, and passed as a required argument to the pure functions, which have no default. All processes of an installation must have the same value; changing it means restarting `api` and `crdt-ws` together. It is not a `system_settings` row.
4. **The browser gets it as `X-Label-Language`** on `GET /api/records/{id}`, next to `X-Draft-Epoch`. `fetchEditorRecord` refuses a response without a valid header (`^[a-z]{2,3}$`) rather than guess, and the value lives only in that query's result.
5. **`entity_labels.default_label` follows the setting**: `labels_from_record(jsonld, label_language)` picks its default label with the same selection; under `en` its results are what they were. Label rows that do not come from a record (AAT rows, vocabulary overrides) keep their English default.
6. **Bulk load keeps the source `_label`** (ADR-0030): the load stores what it was given; only its `entity_labels` rows follow the setting. A bulk-loaded record gets the derived label at its first publish through the editor, whose diff shows a `_label` change nobody asked for (accepted by the owner).
7. **Amendment to contract 1.14 §3 item 17:** after a revert to revision *n* the snapshot is `with_derived_label(revision n, L)`, and `draft/diff` equals `revisions/{current}/diff/{n}` except for at most that one root `_label` change (only for a bulk-loaded revision whose source `_label` is not the derived one, or one published under another label language). A changed derived label is a true `update_literal` on `_label` at the root and is not filtered from any diff.
8. **The write path refuses `_label`** at any depth with `LAE-PROJ-007`, in Python as in TypeScript (`WRITE_FORBIDDEN_KEYS = {id, type, _label}`, checked on each `.`-separated part of the path up to its first `[`, before parsing). This settles `docs/questions.md` Step 1.17 item 2. `add_reference(label=…)` still stores a reference's label.

## Alternatives considered
- **A server-written `_label` update after each title edit.** It needs a second persisted update per keystroke through a private replica (ADR-0027), moves `last_update_id` behind the client (spurious `LAE-PUB-004`), and a snapshot taken between the two updates is stale, so the snapshot would have to derive anyway.
- **Deriving inside `project`.** It would add a key projection never adds (R17) and break the corpus round trip.
- **A constant `en`.** Overturned by the owner: a non-English installation would label its records in English.
- **A list of fallback languages, a region or a per-user language.** More than the decision asks; matching is by primary language, and the label is stored in the record, not chosen per reader.
- **Re-deriving at bulk load.** 141 of the 276 corpus records have no usable name and 63 of the other 135 have a different `_label`; the load would rewrite or blank them.

## Consequences
- Every server-side and browser-side reading of a draft carries the same `_label`, provided `api` and `crdt-ws` have the same setting; nothing detects a mismatch, and a page open across a restart keeps the old value until the record is loaded again.
- Changing the setting migrates nothing: drafts re-derive at their next read; published records, revisions and `entity_labels.default_label` keep their label until the record is next published.
- `upsert_entity_labels_for_record`, `labels_from_record`, `new_record_data`, the bootstrap's `prepare` / `build` / `build_batch` and the Public Reader's `record_title` take the language as an argument.

Evidence: `backend/tests/labels/test_derive.py`, `backend/tests/labels/test_derived_label_cases.py` with `data/derived_label_cases.json` (shared with `frontend/src/crdt/derivedLabel.test.ts`), `backend/tests/test_settings.py`, `backend/tests/crdt/test_rooms.py`, `backend/tests/crdt/test_server.py`, `backend/tests/publish/test_derived_label.py`, `backend/tests/bootstrap/test_label_language.py`, `backend/tests/projection/fixtures/write-forbidden-keys.json`, and the frontend tests of `ValidationDrawer`, `EditorPage` and `fetchEditorRecord`.
