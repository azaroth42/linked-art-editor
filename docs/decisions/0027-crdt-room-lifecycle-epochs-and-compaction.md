# ADR-0027: Room lifecycle: what ends a draft epoch, lossless compaction, the socket contract

**Status:** Accepted (items 7 to 12 added by the critical-step review of Step 1.8) · **Date:** 2026-11-22 · **Decided by:** Claude Fable 5.2 (Phase 1 Step 1.8, conventions §8.2: the guide and spec are silent on these points) · **Recorded by:** Claude

## Context
Step 1.8 builds the room manager on decisions A4, B1, B5 and B6. Four points are not settled by the guide or the spec, and each one decides whether edits survive or documents get corrupted.

1. **B6 says `records.draft_epoch` increments "on every publish".** A draft is also deleted by discard (Step 1.10), by the reaper (Step 1.15) and by revert-to-revision (Step 1.14). If the epoch stays the same, the next draft of the record is a *new hydration with the old epoch*. A client that still holds a document of the deleted draft (an open tab, IndexedDB) passes the epoch guard, and Yjs merges the two hydrations: every key is last-writer-wins between two unrelated histories. `lae.projection.hydrate` forbids exactly this.
2. **B5 says compaction writes `Doc.get_update()`.** Measured on the pinned `pycrdt` 0.14.13: an update that arrives before something it depends on is kept by yrs as *pending*, and `Doc.get_update()` leaves pending structs and pending deletes out (`tests/crdt/test_protocol.py::test_doc_get_update_drops_pending_parts`). Compaction then deletes the `crdt_updates` row, and the update is gone after the next restart.
3. **A room can outlive its draft.** Publish deletes the draft rows in the `api` process and then calls `close(discard=True)` "best effort". If that call is lost, `crdt-ws` keeps a room for a draft that no longer exists and would go on appending updates and, at compaction, re-create state for it.
4. **The wire contract** (how the epoch is stated, what a Viewer gets, which close codes) is only sketched, and `pycrdt.websocket.ASGIServer` can neither see the request nor send a close code (S2 finding 8).

## Decision
1. **Deleting a draft ends its epoch.** `lae.crdt.store.delete_draft` deletes `crdt_drafts` and `crdt_updates` for a record and raises `records.draft_epoch` to one more than the deleted draft's epoch unless it is already greater. `RoomManager.close(discard=True)` calls it. Publish increments the epoch itself and then deletes through the same function, so a publish still adds exactly one. **Nothing else may delete draft rows.** B6 now reads "increments whenever a draft is cleared (publish, discard, reaper, revert)".
2. **Compaction is lossless.** The room tracks every update the `Doc` has not fully integrated (`lae.crdt.protocol.is_integrated`: all structs below the state vector, all delete ranges inside it). The compacted state is `Doc.get_update()`, merged at the update level (`pycrdt.merge_updates`) with those updates when there are any. In normal operation there are none, because an update is persisted and applied before any peer can build on it.
3. **Every write names its epoch.** `append_update` and `compact` are single statements that only match a `crdt_drafts` row with the room's epoch (and lock it, so they queue behind a publish). When they match nothing, the room is retired: sockets are closed with 4409 and nothing is written. `open` checks the same before it returns a room that is in memory, so snapshot, apply and connect never see a superseded room.
4. **Wire contract.** A FastAPI WebSocket route with a `pycrdt.Channel` adapter replaces `ASGIServer`; rooms are `pycrdt.websocket.YRoom` subclasses. The handshake is always accepted and a refusal is a close frame. The client must state its epoch (`?epoch=` or `X-Draft-Epoch`); any epoch other than the room's is closed with `4409 stale-epoch`, and a missing one with `4400`. Codes 4400–4499 are final for `y-websocket` 3.1 and every other code makes it reconnect, so: `4400` bad request or protocol error, `4401` unauthenticated, `4403` ejected, `4404` no such record (or, for a Viewer, no draft), `4409` stale epoch, `4410` record deleted or merged; `1012` room left memory, `1011` update could not be persisted (both: reconnect and resync). A caller without `edit_draft` is read-only: it never creates a draft, its document updates are dropped, and its user id is listed under `read_only` in the server's awareness state. The server stamps `user_id`, `display_name`, `kind` and `read_only` on every presence state.
5. **`Snapshot.last_update_id` is the draft's version.** It is `crdt_drafts.last_update_id`: the id of the last update appended to the draft, set by `append_update` in the statement that inserts the row, and kept across compaction, eviction and restarts. Publish (Step 1.10) calls `lae.crdt.store.draft_unchanged(session, record_id, draft_epoch, last_update_id)` inside its transaction; it locks the draft row, so no update can slip in before the commit. (The first version compared with `max(crdt_updates.id)`. Compaction deletes those rows, so an edit that arrived after the snapshot and triggered a compaction was invisible, and the publish would have deleted the draft with the edit in it.)
6. **`transact` and `revert` stay unimplemented** until Phase 3 Step 3.6. A transaction on the live `Doc` would be broadcast before it is persisted; the docstring of `InMemoryRoomManager.revert` records the route that keeps B5.
7. **Lock order: the `records` row, then the `crdt_drafts` row.** `append_update` takes `FOR KEY SHARE` on the record before it touches the draft, `delete_draft` takes `FOR NO KEY UPDATE`, a room being loaded takes `FOR SHARE`, and publish locks `records` `FOR UPDATE` first (as the guide says). Measured before the change: a write and a publish locked in opposite orders and PostgreSQL ended one of them with `deadlock detected`. The `FOR SHARE` in the load also closes a race: a publish could commit between the load's read of `records` and its read of `crdt_drafts`, and the room was then a second hydration at the old epoch, built from the old `data`.
8. **Memory never falls behind the database.** If the insert of an update fails, its outcome is unknown (the acknowledgement of a commit can be lost); if a committed update cannot be applied, the `Doc` lacks a row. In both cases the room is closed (`RoomFailedError`), its sockets get `1011`/`1012` and reconnect, and the next open rebuilds the room from the rows. Otherwise the next compaction would delete a row the `Doc` does not contain.
9. **One `crdt-ws` per database is enforced** (decision A4). `lae.crdt.instance.InstanceLock` holds a PostgreSQL session-level advisory lock on a connection of its own. A second process waits 30 s (a restart) and then exits. If the lock's connection is lost the process drops its rooms without writing and terminates itself; the service manager restarts it. Measured without the lock: two processes on one draft, one compacts, the other's persisted update is gone. The lock needs a direct connection or session pooling, not a transaction-pooling proxy.
10. **`Origin` allowlist on the WebSocket route.** A handshake with an `Origin` header is answered with HTTP 403 unless the origin is that of `LAE_BASE_URI`, is listed in `LAE_ALLOWED_ORIGINS`, or (only when `LAE_ENV=development`) is a loopback origin. A handshake without `Origin` is not from a browser and goes on to authentication. This is the defence against cross-site WebSocket hijacking; `SameSite=Lax` does not cover another origin of the same site, and with `LAE_DEV_USER` there is no cookie to withhold at all.
11. **A client with another epoch creates nothing.** `open(expected_epoch=)` raises `EpochMismatchError` before a draft is hydrated, so a stale tab reconnecting after a publish gets `4409` and leaves no new draft behind.
12. **A discard can name its draft.** `close(discard=True, draft_epoch=N)` leaves a room or draft of another epoch alone. Publish passes the epoch of the draft it published; without it, a close arriving after the next editor had opened the next draft discarded that draft.

## Consequences
- Steps 1.10, 1.14 and 1.15 delete drafts only through `CrdtWsClient.close(discard=True)` or `store.delete_draft`. If the reaper or discard ever deletes rows directly while `crdt-ws` is down, it must use `store.delete_draft` so that the epoch still moves.
- `GET /api/records/{id}` should return `records.draft_epoch` (Step 1.17 reads it); after a discard the editor must fetch it again before reconnecting.
- A client without an epoch cannot connect, including ad-hoc tools; they read the epoch from `POST /internal/rooms/{id}/open` or the records API.
- Phase 4 Step 4.15's `{code: STALE_EPOCH, current_epoch, base_version}` payload is not sent yet: a text frame would break `y-websocket`'s binary reader, and the close reason is limited to 123 bytes. The server's awareness state already carries `draft_epoch` and `base_version`.
- A deployment whose editor is served from another origin than its record URIs must set `LAE_ALLOWED_ORIGINS`, or browsers cannot open a room.
- Migration 0006 also adds `crdt_drafts.last_update_id`.
- A client holding `edit_draft` can still write any Yjs structure into a draft, including one that no longer projects to JSON-LD (`snapshot` then answers 422 `LAE-CRDT-008` and the draft can only be discarded). Checking every update against the projection was not added (see `docs/questions.md`, Step 1.8).
