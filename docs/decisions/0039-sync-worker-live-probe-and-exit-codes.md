# ADR-0039: The sync worker confirms live rejections with the probe, and exits 4 on a persistent database error

**Status:** Accepted · **Date:** 2026-11-24 · **Decided by:** the amendment of the Step 1.11 contract for issue #171 (`docs/contracts/1.11-sync-worker.md` §8, Claude Fable 5.2), confirmed by the owner on 2026-11-24 (exit 2 and 4 not restarted; the live path holds the queue while QLever refuses the probe), implemented by Claude Opus 5.5 · **Recorded by:** Claude

## Context
Four follow-ups of issues #150 and #151 (`docs/questions.md`, Step 1.11 items 9–12):

1. On the live path an update URL that answers 404 or 405 rejects every update, and contract item 21 then dead-lettered the pending events one at a time, about 15 s each, although no event was at fault. Catch-up already told the endpoint from the event with a probe (ADR-0037).
2. The worker exited 1 for every database error and the unit restarted it every 5 s for ever, so a persistent bug (our own SQL against the wrong schema) became a restart loop at the supervisor level.
3. `lae sync-worker --replay-after` raised a traceback on a database error that was not a lost connection (#151 had changed only `run`).
4. `rejected()` cut QLever's answer to 2000 characters before the access token was removed, so a token across the cut left its first part in `last_error`; and the removal ran on the JSON-encoded text, where a token containing `"`, `\` or a non-ASCII character is escaped and not found.

## Decision
1. **The live path confirms a rejection exactly as catch-up does.** An attempt is counted only when the event's update, sent alone, is rejected, `PROBE_UPDATE` is then acknowledged, and the update, sent alone again, is rejected again; the stored `LAE-SYNC-004` is the second rejection's. One function, `confirm_rejection(conn, client, update)`, sends the probe and the second send for both paths (`process_batch`, `_send_one_by_one`, catch-up's `judge`); only what follows differs (one attempt live, a dead letter at once in catch-up). The five attempts and their backoff (1, 2, 4, 8 s) are unchanged. **The second send is kept** although five attempts already repeat the send: without it an endpoint that refused for a moment (a proxy answering 404 while QLever restarts) and is back when the probe arrives would cost the event an attempt. An event accepted on the second send is recorded `done` like any other. A translation error is counted as before, without asking QLever.
2. **A refused probe on the live path is `unavailable` with a `Refusal`.** `process_batch` returns `outcome = "unavailable"` and `refusal = Refusal(status, body)`; nothing is written, no attempt is counted, the events acknowledged before it stay `done`, and `run` logs `sync_updates_refused` (`during="live"`) and backs off as for an outage (`backoff_seconds(outages)`, capped at 30 s), for as long as it takes. `--once` exits 1. A refusing endpoint never produces a dead letter. Consequence, accepted by the owner: if QLever ever rejects the probe itself while an event is poisoned, the queue is held until the endpoint is fixed instead of the event being skipped after 15 s; `sync_updates_refused` and a growing `sync_lag_seconds` are the signal. A probe is never counted in `updates_sent`.
3. **Exit codes.** One mapping for `run`, `--once`, `--replay-after` and `--failed`: 0 stopped or finished; 1 (`EXIT_FAILURE`) may pass by itself or unknown (the database unreachable, the connection lost, a database error of kind `"other"`, `RecordingError`, an `EventError` or `QLeverError` that reaches `run`, a `--once` or `--replay-after` that did not finish); 2 (`EXIT_CONFIG_ERROR`) refuses to start; **4 (`EXIT_PERSISTENT`, new)** a database error that cannot pass by itself. `database_failure(error, closed=)` decides: `connection_lost` first (a `FATAL` error is a lost connection whatever its class, so a lost connection never exits 4), then a `PostgresError` whose SQLSTATE class is in the closed list `PERSISTENT_SQLSTATE_CLASSES = {0A, 22, 23, 42}` ("this statement is wrong for this schema or this data"), else `"other"`. **Everything not on the list stays 1** (a cancelled statement, a deadlock, a serialization failure, a full disk, a read-only server, an internal error, a client-side `InterfaceError`): a false "persistent" stops sync until a person acts, a false "transient" costs a restart loop, which was already the behaviour. Nothing is retried in-process; item 22 (never reconnect) is unchanged.
4. **The unit: `RestartPreventExitStatus=2 4` with `StartLimitIntervalSec=0`.** `deploy/systemd/lae-sync-worker.service` keeps `Restart=on-failure` and `RestartSec=5`, so exit 1 is restarted every 5 s without limit and a Postgres outage of any length recovers by itself; 2 and 4 leave the unit `failed` until a person runs `systemctl start`. **A start limit (`StartLimitBurst=`) was rejected:** systemd counts starts, not causes, so a limit that stops the loop of a bug also stops the loop of a long or repeated Postgres outage, and the unit would stay down after Postgres is back. `StartLimitIntervalSec=0` is set explicitly so the rule does not depend on systemd's defaults (5 starts in 10 s) and on `RestartSec=`.
5. **Exit 2 is no longer restarted** (owner, 2026-11-24). A missing setting or a watermark that is not an integer is not cured by starting again; before, the unit retried every 5 s. The operator fixes `/etc/lae/lae.env` or the `sync_state` row and starts the unit.
6. **One reporter for every command.** `report_database_error(error, closed=, command=, token=)` logs `sync_connection_lost` (exit 1) or `sync_worker_failed` with `error_type`, `sqlstate`, `persistent`, `exit_code`, `command` and the traceback (exit 4 or 1), and returns the code. `run`, `--once`, `--replay-after` and `--failed` all use it, so no database error leaves `main` as an exception. `--replay-after` still writes nothing, prints the last id applied exactly once on every exit once it holds its connection (and the lock), and says `replay stopped: …` on stderr; `--failed` prints no row when its query fails. `replay`, `replay_batches` and `apply_event` are unchanged: they raise, the command reports.
7. **Redact, then truncate, then encode.** `redacted_body(body, client)` returns `_redact(body, client)[:REJECTED_BODY_CHARS]`; `rejected()` is always given its result, and so are `Refusal.body` and the `body` of both `sync_updates_refused` lines. `lae.sync.errors.REJECTED_BODY_CHARS` (2000) is the only limit (`worker._BODY_CHARS` is gone). Redacting the encoded `LAE-SYNC-004` string again is kept as a second guard, never as the only one.

## Alternatives considered
- **No probe on the live path** (the #150 position). Leaves the fault of item 1: a wrong URL turns the queue into dead letters at about one per 15 s.
- **Probe without the second send.** Cheaper by one request, but a refusal that passed between the rejection and the probe blames the event.
- **`StartLimitBurst=` / `StartLimitIntervalSec=` as the brake.** Rejected for the reason in decision 4.
- **Backoff in the unit (`RestartSteps=`, `RestartMaxDelaySec=`).** Needs systemd 254 or later and also delays the recovery from a long outage. Not added; the remaining loop is a known limit (`docs/questions.md`, Step 1.11 item 11).
- **Retry the failed statement in-process, or reconnect.** After an unexpected database error a new process is the only state we trust; item 22 stays.
- **A longer list of persistent classes** (for example 25, 40, 53, 55, XX). Some of these pass by themselves (a deadlock, a serialization failure, a lock not available, a full disk that is freed); stopping the worker on one of them would break self-recovery.

## Consequences
- A wrong update URL no longer produces dead letters; `sync_updates_refused` (`during="live"`), `sync_unavailable_total` and `sync_lag_seconds` grow until it is fixed, and the worker then recovers by itself.
- A confirmed rejection costs two more requests (at most 10 more per dead letter); none on the normal path, for an unavailable QLever, or for a translation error. The probe changes no triple and does not raise `qlever_delta_triples` (test 63, QLever 0.6.0).
- A worker that meets a wrong schema, a violated constraint or a missing privilege stops with 4 and stays down: the alarm is the unit state (`systemctl is-failed lae-sync-worker`) or a failed scrape of `/metrics`. After a migration or a restore into the live database, check the unit (`deploy/README.md`, "When the sync worker stops").
- A database error of unknown kind that does not pass is still a restart loop every 5 s, each restart sending the batch in flight again (harmless, contract item 17) (`docs/questions.md`, Step 1.11 item 11).
- asyncpg 0.32 raises a wrong argument type as `asyncpg.exceptions.DataError`, a `PostgresError` with SQLSTATE 22000, not as the client-side `InterfaceError` of the same name, so it exits 4 (a bug in our call that never passes). Contract test 66 had listed it among the exit-1 cases; it is tested under test 65 instead, and a genuine client-side `InterfaceError` on an open connection takes its place in test 66.
- No migration, no new metric, no new `LAE-SYNC` code; `lae.sync.events`, `lae.sync.qlever_client`, `lae.sync.metrics`, `replay`, `classify`, `connection_lost` and contracts 1.10 and 1.14 are unchanged.

Evidence: `backend/tests/sync/test_batch.py` (tests 56–62, 71, 72, and tests 17, 18, 19 and the token test as adapted), `backend/tests/sync/test_connection_loss.py` (tests 64–70), `backend/tests/sync/test_qlever_integration.py` (test 63, run locally against QLever 0.6.0).
