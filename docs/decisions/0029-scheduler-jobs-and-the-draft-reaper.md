# ADR-0029: Scheduler jobs and the draft reaper

**Status:** Accepted · **Date:** 2026-11-22 · **Decided by:** Claude Opus 5.5 (Phase 1 Step 1.15, conventions §8.2: the guide and spec are silent on these points) · **Recorded by:** Claude

## Context
Step 1.15 asks for a job runner that records `last_run`, `last_status` and `duration` in `sync_state` under `job:<name>`, an hourly reaper for drafts idle longer than `draft_ttl_days` (decision B7), and `GET /api/drafts` plus `POST /api/records/{id}/draft/extend`. It leaves open how two scheduler processes are kept from running one job twice, what happens when `crdt-ws` is down, what to do with a never-published record that has no draft at all (Step 1.8, `docs/questions.md` item 9), and who sees which drafts.

## Decision
1. **Runner.** A plain asyncio loop (no scheduling library): one task per job, schedules `Every(interval)` (from the start of the last run; at once if never run) and `DailyAt(time)` (UTC). The next run is computed from `last_run` in `sync_state`, so a restart neither repeats a recent run nor skips a missed one (a missed run is made up once). A run holds a session-level advisory lock (`pg_try_advisory_lock`, key = 64-bit BLAKE2b of the job name) on a connection that is closed afterwards; if another process holds it, the run is skipped. `sync_state['job:<name>']` is `{last_run, last_status: running|ok|error|interrupted, duration, last_error, result, next_run}`; `last_run` and `running` are written when a run starts. On `SIGTERM`/`SIGINT` no new run starts, running jobs see `ctx.should_stop()` and may finish their current item for up to 30 s, then they are cancelled and recorded as `interrupted`; the process exits 0. Without `LAE_INTERNAL_TOKEN` in staging or production it refuses to start, as `crdt-ws` does.
2. **Reaper.** For each draft idle beyond the TTL (database clock): read it again (same epoch, still idle), then `crdt-ws` `close(discard=True, draft_epoch=<its epoch>)`. If `crdt-ws` cannot be reached, one transaction locks `records` then the draft row, checks again and calls `store.delete_draft(only_epoch=...)` (ADR-0027). If the record is at `version = 0`, its row is then deleted in a transaction that locks it `FOR UPDATE` and finds no draft. Then never-published records with no draft whose `created_at` is older than the TTL are deleted the same way (abandoned creations); migration `0007` adds the partial index `ix_records_unpublished_created_at` (`created_at` where `version = 0`) for that query. Each action is logged as `draft_reaped` with `record_id`, `action`, `contributors`, `draft_epoch`, `last_activity_at` and `via`; a failing draft is logged and counted and the pass goes on. `draft_ttl_days` must be at least 1.
3. **Drafts API.** `GET /api/drafts` (`edit_draft`): a caller with `publish` sees every draft, anyone else the drafts they created or contributed to; entries carry `record_id`, `uri`, `type`, `label`, `version`, `draft_epoch`, `base_version`, `created_by`, `contributors` (`{id, display_name, kind}`), `last_activity_at` and `expires_at = last_activity_at + draft_ttl_days`, closest expiry first. `label` comes from `entity_labels` (published records) or from `records.data` (never published), not from the live draft. `POST /api/records/{id}/draft/extend` (`edit_draft`, any draft: editing would reset the clock too) sets `last_activity_at = now()` in one statement and answers with the entry; 404 `LAE-REC-001` / `LAE-CRDT-003`.

## Consequences
- ~~An edit or extend that lands in the single internal HTTP call between the reaper's re-check and `crdt-ws`'s discard is lost with the draft.~~ **Closed 2026-11-25 (core review A, #178):** the reaper passes its TTL to the close RPC (`idle_seconds`; `RoomManager.close(idle_for=...)`), and `crdt-ws` deletes the draft only if `last_activity_at` is still older than the TTL in the statement that locks the draft row (`store.delete_draft(idle_for=...)`). An edit or extend that commits first keeps the draft, its room and its sockets, and the reaper counts the draft as skipped; one that comes after the delete finds the draft gone, as after a publish. The answer is 204 either way, so the reaper reads `crdt_drafts` afterwards: a draft that is still there and still idle is an error.
- If the lock's connection is lost mid-run (database restart), another scheduler may start the same job; jobs must tolerate an overlap. The reaper does, because it re-checks every draft under row locks.
- Phase 2 Step 2.1 registers `refresh_usage_counts` with `DailyAt`; Step 2.17's dashboard reads `sync_state` `job:*` rows (`lae.scheduler.jobs.read_job_state`); Step 2.9 adds filters to `GET /api/drafts`.
