# Architecture & Design Document: Collaborative Linked Art Editor

**Status:** Architecture Locked (v0.13)  
**Target Stack:** Python (FastAPI \+ pycrdt \+ MCP) · PostgreSQL \+ pgvector (System of Record) · QLever (SPARQL Index) · TypeScript \+ React 19 (Frontend)

---

## 1\. Vision & Design Philosophy

This system combines the strongest ergonomics of three established platforms for cultural heritage data authoring:

* **Arches:** Schema-aware forms ("cards") that hide CIDOC-CRM graph complexity behind intuitive, domain-specific inputs.  
* **Wikidata:** Collaborative editing, transparent revision history, statement-level provenance, and seamless authority linking.  
* **Google Docs:** Frictionless autosaving, real-time awareness of co-editors, inline discussion, and zero fear of lost work.

### Core Engineering Principles

1. **Single System of Record:** PostgreSQL owns durability, versioning, drafts, and permissions. QLever is a derived, queryable graph index—never the sole source of truth.  
2. **Draft/Publish Isolation:** Continuous autosaving must never destabilize the triplestore or leak broken fragments into search and autocomplete.  
3. **Lossless Round-Tripping:** Valid Linked Art JSON-LD that the UI does not explicitly model must pass through edit cycles untouched.  
4. **Cohesive Ontology Over Raw Forms:** The UI adapts to Linked Art patterns (flattening multi-hop CRM structures) rather than exposing raw RDF triples to catalogers.  
5. **Open Once Published & Single-Tenant Simplicity:** This is a Linked Open Usable Data (LOUD) authoring platform, not a closed collections management system. All published records are fully open with no field-level redaction, and each installation serves a single tenant cleanly.  
6. **Human \+ AI Co-Authoring & Tiered Governance via MCP:** AI agents collaborate through the same live CRDT draft rooms, validation rules, and structured curation queues as humans. Cheap discovery agents edit drafts and propose cross-record merges, frontier-model arbiter agents evaluate proposals (auto-executing low-blast-radius merges within strict guardrails, rejecting false positives, or escalating uncertain/high-impact cases to human Editors), and human Editors retain final oversight and 1-click reversibility.

## 3\. Data Model, Identifiers & Graph Boundaries

### 3.1 PostgreSQL Storage Layout (Asymmetric Scale: 10M+ Records, 10–30 Editors)

* **`records`:** Canonical published Linked Art records stored as `JSONB` (TOAST `lz4` compression, which applies to out-of-line values) keyed by **UUIDv7** (for time-ordered B-tree locality across 10M+ rows) with **flat persistent public URIs** (e.g., `/id/{uuidv7}`, ensuring records survive reclassification while allowing class-typed routes to be injected later if desired), alongside `type`, `version`, `status` \[`active`, `deleted`, `merged`\], and `etag`. Indexing stays lean (B-tree indexes on UUIDv7, URI, and type—avoiding whole-document GIN indexes since QLever handles full-text and graph search).  
* **`entity_labels`:** Compact lookup table (`uri` primary key, `type`, `labels` \[`JSONB` mapping BCP-47 language tags to preferred labels, e.g., `{"en": "Oil paint", "fr": "Peinture à l'huile"}`\], precomputed `default_label` \[`TEXT NOT NULL`\] fallback, primary classification, compact `metatype_uris` and `vocab_ids` arrays, source dataset) covering both local records and locally loaded **Linked Art sidecar datasets** for sub-millisecond locale-aware transclusion reads, bidirectional UI card routing, concept-aware drag-and-drop highlighting, and SHACL membership checks without extra runtime joins.  
* **`entity_embeddings (pgvector)`:** Sibling table to `entity_labels` storing compact `halfvec` (float16) multilingual embeddings for Concepts (`Type`, `Material`, `Language`, `MeasurementUnit`, `Currency` \+ loaded sidecar vocabularies) and Reference Authorities (`Place`, `Person`, `Group`)—typically \<= 2–3M rows—indexed with HNSW (`pgvector`, with optional `pgvectorscale` StreamingDiskANN if scaled further). Updated transactionally alongside `entity_labels` on publish and sidecar vocabulary reloads, eliminating any third data store to keep in sync while enabling native SQL pre-filtering against `entity_labels.vocab_ids` and `metatype_uris`. Embeddings encode enriched concept text (`preferred_label` \+ alternate labels \+ scope note/description \+ `broader` parent chain) rather than bare labels alone.  
* **`vocabularies / vocabulary_terms / slot_vocabulary_bindings`:** Lightweight metadata tables (hundreds to thousands of rows) storing named Value Set definitions (mode \[`enumerated` \| `rule`\], metatype URI, broader root URIs, exclusion URIs, enforcement level), curated/pinned term lists (display order, deprecated flag), with all Value Set labels, term labels, and cataloger scope notes stored as BCP-47 `LangMap` JSONB objects (with optional auto-translation review status metadata) rather than bare strings, contextual `(EntityClass, PropertyPath)` slot bindings, and a materialized membership cache refreshed automatically when sidecar datasets reload or local `Type` records change.  
* **`record_revisions`:** Immutable append-only audit log written on edits (initial bulk-loaded records remain at version 1 without duplicating payloads until edited), storing **zstd-compressed canonical N-Triples** (application-level `bytea`; PostgreSQL TOAST does not offer zstd) alongside the pinned @context version for deterministic triple diffing, where edited revisions also persist compact zstd-compressed JSON-LD snapshots (or lossless JSON patches) alongside canonical zstd N-Triples to enable arbitrary historical version browsing, `rev M` vs. `rev N` diffs, 1-click **Revert to Revision N**, and versioned/Memento permalinks, plus contributing author IDs (humans and AI agents), publishing editor ID, timestamp, edit summary, accepted validation warnings, and a shared `merge_batch_id` or `split_batch_id` for revisions created during a merge or split to enable reversible unmerges and unsplits.  
* **`crdt_drafts / crdt_updates`:** Sparse tables storing binary Yjs/`pycrdt` state only for records with active unpublished drafts (dozens to hundreds of rows, never tens of millions). Rooms hydrate lazily from `records` on open, clear on publish, and are **automatically purged after 5 days of inactivity** (reverting abandoned edits on existing records or deleting abandoned unpublished new records). Each draft room records a monotonic `draft_epoch` and `base_version` to detect stale offline client reconnects after a publish clears a room.  
* **`curation_proposals / merge_batches / split_batches`:** Relational queue for cross-record structural proposals (`merge`, `split`, `bulk_reclassify`), exempt from the 5-day CRDT draft reaper. `curation_proposals` stores `id` (UUIDv7), `proposal_type`, `source_record_id`, `target_record_id`, `status` \[`pending`, `claimed`, `approved`, `rejected`, `needs_human_review`, `executed`, `superseded`\], `proposed_by` (actor \+ model identifier), structured `evidence` (`JSONB` storing matcher signals, confidence, and rationale), `field_resolution_plan` (`JSONB`), `reviewed_by`, `review_rationale`, `claim_expires_at` lease timestamp, and a `block_resubmission` negative-cache flag preventing cheap sweep agents from endlessly re-proposing rejected "Do Not Merge" pairs. `merge_batches` stores pre-merge manifests (exact source record state plus rewritten referencing UUIDs and JSON paths) linked via `merge_batch_id` for 1-click Unmerge. `split_batches` stores pre-split manifests (original conflated record state, newly minted UUIDv7 record ID, and selectively reassigned inbound referencing UUIDs and JSON paths) linked via `split_batch_id` for reversible splits.  
* **`comment_threads / comments`:** Anchored discussion threads (anchor = record URI or internal sub-node IRI, `open`/`resolved` state) and their comments with `@user` / `@agent` mentions, retained across publishes since anchors are stable.  
* **`agent_jobs`:** Server-owned asynchronous job table for long-running agent operations (batch translation, IIIF transcription, set enrichment) storing `status`, progress counters, per-item results, cancellation flag, and the invoking actor; exposed to MCP clients as `linkedart://job/{id}` progress resources.  
* **`watchlists / notifications / saved_smart_sets / qa_findings / curation_campaigns / agent_audit_log / agent_quotas / ephemeral_translations`:** Lightweight relational tables supporting Wikidata-style watchlists (records, `Set`s, and Value Sets), @mention/escalation notifications, saved Visual Query Builder Smart Sets, scheduled cross-record QA and link-rot worklists, `curation_campaigns` (tracking Queue Focus Mode progress, skipped records, and optional cataloger assignments over `Set`s, Dynamic Smart Sets, and `qa_findings`), per-agent MCP audit logs, rate-limit quotas, circuit-breaker flags, and `ephemeral_translations` (disposable cache keyed by `(record_id, version, target_lang, model_id)` for optional on-demand Public Reader translations, automatically invalidated on new revisions and never touching `records` or QLever). Note that `notifications` and `qa_findings` store structured typed event payloads rather than frozen English prose so clients localize them dynamically.  
* **`llm_provider_configs / agent_chat_sessions / agent_chat_messages`:** Lightweight tables storing envelope-encrypted LLM provider configurations and API keys (`llm_provider_configs`, encrypted at rest via an instance master key from env/KMS, supporting institutional admin-configured keys and optional admin-togglable per-user BYOK keys for Gemini, Claude, OpenAI, and institutional cloud endpoints alongside local models—never exposed to browsers or logs) plus persistent chat threads (`agent_chat_sessions`, `agent_chat_messages`, optionally linked to a `record_id` or `set_id` with configurable retention).  
* **`backup_jobs / usage_metrics_daily / sidecar_datasets / system_settings / webhooks / webhook_deliveries / admin_audit_log`:** Lightweight operational tables supporting automated/on-demand backup run metadata and restore-verification checksums (`backup_jobs`), rolled-up per-user, per-class, and per-function usage analytics without storing sensitive query PII (`usage_metrics_daily`), versioned manifests for locally loaded Linked Art sidecar datasets (`sidecar_datasets`), versioned operational thresholds and SSRF egress rules (`system_settings`), HMAC-signed outbound webhook subscriptions and delivery retry logs dispatched from `outbox_events` (`webhooks` / `webhook_deliveries`), and an immutable, SIEM-exportable administrative security and configuration audit log (`admin_audit_log`).  
* **`outbox_events`:** Written in the same DB transaction as any incremental publish (including bundled dependent stubs), merge, or delete to guarantee at-least-once delivery to QLever.

### 3.2 Normalized Stubs & Read-Time Transclusion

Linked Art documents routinely embed references to external entities (artists, places, concepts, collections) as stubs containing `id`, `type`, and `_label`.

* **Local Sidecar Datasets for External Authorities (No Live Remote Queries):** External vocabularies and reference datasets (Getty AAT/ULAN/TGN, Wikidata, GeoNames, etc.) are loaded locally as Linked Art into sidecar datasets. The editor never performs live external web requests or remote SPARQL queries during CRDT editing sessions.  
* **Uniform Write-Time Normalization:** Both local and external entity references follow the exact same rule: before persisting to PostgreSQL, references are stripped down to canonical stubs (`{"id": "...", "type": "..."}`), discarding mutable labels. The one exception is a reference whose target has no `entity_labels` row (neither a local record nor a loaded sidecar entity, e.g., a pasted external URI): its incoming `_label` is retained as a fallback and the reference is flagged as an *unresolved reference* `qa_findings` item, since stripping it would lose the only label available. When expanding a record to RDF for QLever, non-owned stub attributes (`_label`, `type`) on referenced entities are similarly stripped so only the linking triple is emitted, enforcing strict subject ownership in the flat graph.  
* **Read-Time Transclusion:** On API read, export, or UI hydration, current `_label` (and optionally primary classification) values are dynamically resolved from local records and sidecar datasets via a single batched index-only lookup against the compact `entity_labels` table. Transclusion takes the caller's ordered `locale_chain` (from `Accept-Language`) to resolve `_label` in the user's preferred UI language from `entity_labels.labels`, falling back cleanly to `default_label`. Renaming an artist or refreshing a sidecar vocabulary immediately propagates everywhere without cascading record updates or triplestore deletion anomalies.

### 3.3 Flat Graph Model, Revision-Diff Syncing & Skolemized Nested Nodes

* **Flat Default Graph \+ Local Sidecar Graphs:** Maintaining millions of per-record named graphs introduces high SPARQL query complexity, dictionary bloat, and cross-record join overhead. All local published Linked Art records are indexed into a single flat default graph in QLever. External authorities loaded as Linked Art sidecar datasets live in a small, fixed set of coarse-grained sidecar graphs (e.g., `urn:graph:sidecar:<dataset>`), keeping total graph count minimal and enabling independent bulk refreshes.  
* **Revision-Diff Syncing (DELETE DATA / INSERT DATA):** On publish, the sync worker computes the exact triple set difference between `rev N-1` and `rev N` (`T_delete = triples(rev N-1) - triples(rev N)` and `T_insert = triples(rev N) - triples(rev N-1)`) and issues a single idempotent SPARQL 1.1 `DELETE DATA` / `INSERT DATA` update. This minimizes delta-triple churn in QLever's edit sidecar—editing a single title retracts 1 triple and inserts 1 triple rather than churning the entire record.  
* **Strict Subject Ownership:** A Linked Art record may only emit triples to QLever whose subject is owned by that record (its root IRI and internal record-scoped sub-node IRIs). References to other local records or sidecar external entities emit only the linking triple—never the target's `rdf:type` or `rdfs:label`—eliminating deletion anomalies.  
* **Internal Skolemized Slash Paths (Never Exposed Externally):** Because SPARQL `DELETE DATA` cannot delete blank nodes across requests, nested structures (`Name`, `Identifier`, `Dimension`, `Production`, `TimeSpan`, `AttributeAssignment`) receive stable, internal record-scoped **slash-path IRIs** (`<record_uri>/node/<uuid>`) inside PostgreSQL, CRDT state, and QLever. These internal sub-node IRIs enable deterministic triple diffing, field-anchored comments, and keyed CRDT merging, but are **strictly internal—never shown in the UI and always stripped back to anonymous nested objects / blank nodes in public JSON-LD and RDF exports**. (They necessarily appear in SPARQL results from QLever; `/id/{uuidv7}/node/{id}` therefore 303-redirects to the parent record rather than 404ing.)  
* **Locked zstd N-Triples & Blue/Green Offline Rebuilds:** Edited revisions persist **zstd-compressed canonical N-Triples** so `triples(rev N-1)` is guaranteed exact without re-expansion drift. Initial multi-million-record migrations bootstrap via PostgreSQL `COPY` and offline QLever `IndexBuilderMain`. QLever runs with `--persist-updates` so delta triples survive server restarts, and the sync worker persists a `qlever_index_watermark` (the last `outbox_events` id applied to the live index) so replay after any crash, restore, or rebuild is deterministic. Ongoing maintenance uses a **blue/green rebuild**: when the delta-triple count exceeds a **configurable threshold** (or on admin demand), a new index is built with `IndexBuilderMain` from a PostgreSQL snapshot taken at a recorded watermark in a second index directory/container, outbox events past that watermark are replayed into the new index, and traffic is switched atomically—the Public Reader, autocomplete, and public SPARQL endpoint stay online throughout, and the previous index is retained for rollback. Rebuilds never depend on "no editors logged in", since public traffic is continuous.  
* **First Edit of Bulk-Loaded Records:** Bulk-loaded records carry no stored N-Triples, so `triples(rev N-1)` for their first edit is re-expanded from the stored JSON-LD. Each bulk build records the pinned `@context` version and expander version it used; if the current versions differ, the sync worker issues `DELETE WHERE { ?s ?p ?o }` over the record's owned subjects (root IRI plus its `/node/` IRIs) instead of a computed diff, then `INSERT DATA` for the new triple set. A sampled PostgreSQL-vs-QLever consistency audit in the scheduled QA sweeper detects orphaned or missing triples.

### 3.4 Referential Integrity, Merges & Tombstones

* **Delete Protection:** Before deleting a record, the API queries QLever for inbound references. If referenced, hard deletion is blocked; users must either unlink references or merge the record.  
* **Tombstones:** Deleted records remain in Postgres with `status = 'deleted'`, serving HTTP `410 Gone` to public dereferencers and retracting their owned triples from QLever via DELETE DATA.  
* **Entity Merge Workflow:** Merging Record A into Record B rewrites all inbound references in Postgres (enqueuing affected records in the outbox), appends A's URI to B's `equivalent` array, and sets A to `status = 'merged'` (serving HTTP `301 Moved Permanently` to B).  
* **Safe Merge Execution & 1-Click Unmerge:** Before executing any merge (human or agent-approved), FastAPI checks whether Record A or Record B has an active `crdt_draft` or live WebSocket session and defers execution if actively being edited, avoiding mid-session invalidation. Both rows are locked via `SELECT ... FOR UPDATE` in deterministic UUIDv7 order (preventing deadlocks and double-merges) after verifying both remain `status = 'active'`. Every `record_revision` generated during a merge shares a `merge_batch_id` pointing to a pre-merge manifest in `merge_batches`, allowing human Editors to perform a clean **1-click Unmerge** if an automated or manual over-merge occurs.  
* **Entity Split Workflow (`split_batch_id`):** Guided dual-pane Split Workbench for executing `split` proposals from `curation_proposals` (or manually separating conflated entities such as homonymous artists, father/son workshops, or combined buildings/institutions). Defers execution if the source record has an active CRDT session, locks affected rows deterministically, mints a new UUIDv7 record, partitions statements and `equivalent` links, selectively reassigns inbound QLever backlinks atomically in PostgreSQL (enqueuing updated referencers in `outbox_events`), and links all generated `record_revisions` via `split_batch_id` pointing to a pre-split manifest in `split_batches` for 1-click rollback.  
* **Safe Record Reclassification Wizard:** Leveraging flat `/id/{uuidv7}` URIs so records survive class changes (e.g., `Person` \<-\> `Group`, `HumanMadeObject` \<-\> `Set`), checks QLever inbound predicate compatibility first (blocking or flagging invalid backlinks such as `took_place_at` if reclassifying `Place` \-\> `Group`), remaps compatible fields onto the target Declarative UI Profile, and surfaces incompatible subgraphs for explicit resolution prior to publishing.

## 4\. Editing Lifecycle, CRDT Collaboration & Publishing

### 4.1 Shared CRDT Draft vs. Publish Boundary

| Phase | Trigger | Validation | Storage Target | Indexed in QLever? |
| :---- | :---- | :---- | :---- | :---- |
| **Live CRDT Sync (Autosave)** | Continuous binary CRDT updates over WebSocket | Lenient live client-side JSON-Schema badges | `crdt_drafts / crdt_updates` (active records only) | No |
| **Validate** | On-demand or pre-publish | Full JSON-Schema \+ SHACL against projected JSON-LD | Transient | No |
| **Publish / Commit** | Explicit Editor-only action ("Publish Changes") | Must pass all Hard Errors; Soft Warnings require confirmation | `records`, `entity_labels`, `record_revisions`, `outbox_events` (clears draft) | Yes (sub-second via worker) |

Micro-batching outbox events in the sync worker (e.g., flushing every 250ms or 50 records) protects QLever's delta-triple layer from write storms during bulk edits or heavy concurrent publishing.

* **Bundled Transactional Publish of Dependent Stubs:** When a draft references newly minted, unpublished inline stubs (e.g., a new `Person` or `Place` created mid-form), publishing validates and commits the primary record together with all dependent unpublished stubs atomically in a single PostgreSQL transaction and emits outbox events for the entire bundle.  
* **5-Day Abandoned Draft Expiry:** A scheduled reaper automatically discards CRDT drafts with no edits for 5 consecutive days (resetting modified records back to their live published revision or deleting unpublished new draft records) to prevent stale draft accumulation. Human Editors can monitor approaching expirations and click **Extend TTL** or **Inspect & Publish** from the Active Drafts & Review Inbox.

### 4.2 Real-Time CRDT Co-Editing Architecture (Yjs \+ pycrdt)

* **CRDT Stack:** Clients run Yjs in TypeScript connected over WebSockets to pycrdt and pycrdt-websocket (Rust-backed, Yjs wire-compatible) inside the FastAPI backend, providing simultaneous multi-cursor editing, live presence/awareness indicators, and offline resilience.  
* **Graph-Safe CRDT Schema (Avoiding Array Interleaving):** Repeated Linked Art properties are modeled as keyed Y.Maps rather than ordered Y.Arrays—embedded sub-nodes (Name, Dimension, LinguisticObject, AttributeAssignment) are keyed by their skolemized UUID IRI, and entity-reference lists (classified\_as, made\_of, member\_of) are keyed by target URI. Concurrent additions merge cleanly and duplicate identical assertions deduplicate automatically. Collaborative prose fields (content) use Y.Text for character-level co-editing, while scalar fields use LWW Y.Map entries.  
* **Order Preservation (`_order`):** Keyed Y.Maps discard source order, which is meaningful for `Name.part`, the display order of identifiers and statements, and any unprofiled arrays that must round-trip verbatim. Every keyed entry therefore carries a fractional-index `_order` LWW value assigned on hydration and on insert; projection sorts by `_order` and uses the IRI/key only as a tie-break, so round-tripped documents keep their original order while concurrent inserts still merge without interleaving conflicts.  
* **Deterministic Projection & Lossless Round-Tripping:** On validation or publish, the Y.Doc is projected deterministically into canonical Linked Art JSON-LD arrays (sorted by `_order`, then IRI/key). Any unprofiled JSON-LD properties remain intact in the root Y.Map and serialize back verbatim.  
* **Low-Concurrency Room Topology (No Redis Needed):** With 10–30 concurrent users, a single dedicated CRDT WebSocket worker process (or single async FastAPI instance) manages all active rooms in memory without needing Redis pub/sub fan-out. Rooms hydrate lazily from PostgreSQL on first open and evict from memory when idle. `pycrdt-websocket` is still a beta-stage release (used in production by Jupyter), so an early spike validates it under load and the room manager sits behind a narrow interface so a Yjs-wire-compatible sidecar (y-websocket / Hocuspocus) remains a drop-in fallback.  
* **Process Topology & Publish Path:** The deployment consists of discrete processes: `api` (REST, content negotiation, `/mcp`), `crdt-ws` (the single-process room manager), `sync-worker`, `scheduler` (draft reaper, QA sweeper, backup runner), `embedder`, local LLM server, QLever, and PostgreSQL. Because rooms live in memory in `crdt-ws`, validate and publish requests that need the live Y.Doc are routed from `api` to `crdt-ws` over an internal RPC rather than reading room state from another worker; `crdt-ws` also persists every update to `crdt_updates` synchronously so room state is reconstructable by any process after a restart.  
* **Offline Stale-Base Reconnection Guard (`draft_epoch`):** Every active `crdt_draft` room tracks a monotonic `draft_epoch` and `base_version`. If a client makes offline Yjs edits while another Editor publishes revision `N+1` (clearing the previous draft room), FastAPI rejects blind binary replay against the superseded epoch on reconnect and opens a **Rebase Offline Changes Modal**. For v1 the modal presents the offline edits as a read-only structured change list (reusing the semantic diff format) with per-change **Apply** / **Discard** against the fresh room, rather than attempting a full automatic three-way merge, so changes are reconciled safely rather than silently corrupted or lost.

### 4.3 Provenance, Diffs & Review Workflows

* **Human-Readable Semantic Diffs:** Revisions compare parsed entity patterns (e.g., *"Changed `produced_by -&gt; carried_out_by` from Unknown to Rembrandt van Rijn"*) rather than raw JSON Pointer paths. The backend emits structured typed change objects (`add_ref`, `remove_ref`, `update_literal`) rather than hardcoded English prose so the client (and Mermaid Visual Diff labels) render in the user's active locale. Includes an optional Mermaid Visual Diff diagram highlighting added, removed, and modified CRM subgraphs.  
* **Revision History Time-Travel & 1-Click Revert:** Dedicated **Revision History Browser** allowing editors to inspect any historical version of a record, compute semantic and Mermaid Visual Diffs between arbitrary revisions (`rev M` vs. `rev N`), and execute a 1-click **Revert to Revision N** (committing a new forward revision restored losslessly from the stored zstd JSON-LD snapshot/patch while keeping history strictly append-only).  
* **Anchored Discussions:** Comment threads (`comment_threads` / `comments`) attach to a record URI or a specific skolemized sub-node ID (e.g., questioning a specific `Dimension` or `AttributeAssignment`). Supports `@user` and `@agent` mentions alongside `open`/`resolved` thread states. Typing `@agent` in an anchored thread can launch a scoped turn in the Embedded Agent Chat Workbench targeting that specific sub-node.  
* **Shared Live Draft (Collaborators Edit, Editors Publish):** Each actively edited record has one shared live CRDT draft room. Any authenticated user with edit\_draft permission can co-edit in real time; only users with the publish (Editor) role can inspect the semantic diff against the live published revision and publish changes (or discard/revert the draft back to the published revision).  
* **Multi-Author Attribution:** The CRDT session records all contributing user IDs since the last publish so the committed record\_revision credits every collaborator alongside the publishing editor. Interactive chat-driven edits record dual attribution—crediting both the instructing human user (`AI Agent (via <user>)`) and the underlying LLM provider/model identifier.  
* **First-Class `AttributeAssignment`:** UI affordance allowing catalogers to attach provenance (who asserted it, when, and bibliographic source) to disputed fields like attribution, dating, or classification. Local LLM data translations automatically attach `AttributeAssignment` (`assigned_by`) provenance recording the translation activity, local model identifier/version, timestamp, and `source_content_hash`.  
* **Active Drafts & Review Inbox (5-Day Expiry Triage):** Dedicated Editor triage dashboard listing every open CRDT draft across the system, filterable by contributor (human vs. AI agent), SHACL validation status (`0 errors`, `warnings`, `violations`), and remaining time before the 5-day inactivity reaper fires, with 1-click **Extend TTL**, **Inspect & Publish**, or **Discard** actions.  
* **Watchlists & Notification Inbox:** Wikidata-style watchlists allowing editors to watch individual records, `Set`s, or Vocabulary Value Sets and receive in-app notifications on draft edits, publishes, merges, `@mentions`, and Tier 2 agent escalations.

## 5\. Validation Engine (JSON-Schema & SHACL)

Validation runs as a two-tier, dual-engine pipeline. JSON-Schema is the first-order gate (reusing the upstream Linked Art JSON Schema); SHACL shapes are authored and maintained by this project (Linked Art publishes none) and run only on documents that already pass JSON-Schema, within a per-record latency budget that keeps the Batch Staging Wizard and agent self-correction loops practical.

1. **Structural Validation (JSON-Schema):** Runs in both browser (instant feedback via Ajv) and Python backend (canonical gatekeeper). Enforces Linked Art JSON-LD framing, required `@context`, valid field keys, and primitive datatypes.  
2. **Semantic / Graph Validation (SHACL):** Runs in Python (e.g., `pyshacl` or compiled shape evaluators over the single-record graph plus referenced entity types). Validates ontology rules that JSON-Schema cannot easily express (e.g., `made_of` targets must be `Type` entities classified under AAT Materials; `begin_of_the_begin` must not exceed `end_of_the_end`).

### Tiered Severity Levels

* **Hard Errors (`sh:Violation`):** Structurally or ontologically invalid. Blocks publishing; highlighted inline on the offending widget.  
* **Soft Warnings (`sh:Warning`):** Editorial quality or completeness gaps (e.g., missing preferred title, unlinked creator string, missing measurement unit). Surfaced in a validation drawer; publishable with acknowledgment.  
* **Vocabulary-Driven Enforcement:** Contextual Value Set bindings from the Vocabulary Management Layer compile directly into SHACL/JSON-Schema validation rules with per-slot enforcement levels: `strict` (`sh:Violation`, blocking publish), `extensible` (`sh:Warning`, publishable with confirmation for valid `Type`s outside the list), or `advisory` (UI guidance only). Updating a Value Set in the Vocabulary Manager updates both form pickers and backend validation without hand-editing Turtle shape files. Note that JSON-Schema and SHACL validators emit structured diagnostic codes \+ typed parameters (`code`, `path`, `params`) for localized client rendering alongside language-tagged `sh:message` literals (`"..."@en`) for RDF and MCP consumers.  
* **Cross-Record Data Quality & Temporal Sanity Sweeps:** Because single-record SHACL cannot catch multi-record graph contradictions, a scheduled QLever-backed **QA Sweep & Link-Rot Checker** detects cross-record anomalies—such as death before birth on a referenced `Person`, artwork production dated after its creator's death, circular `part_of` or `broader` hierarchies, and broken external IIIF/image URLs—populating structured worklists (`qa_findings`) that human catalogers or Tier 1 MCP agents can claim and repair. The QA sweeper also flags stale machine translations when a source node's current text hash diverges from `source_content_hash`.

## 6\. Schema-Driven UI & Ergonomics

### 6.1 Declarative UI Profile Layer

SHACL and JSON-Schema define *what is valid*, not *how humans should edit it*. A separate declarative **UI Profile** (YAML/JSON per Linked Art class—`HumanMadeObject`, `Person`, `Group`, `Place`, `VisualItem`, `Set`, `Concept`) drives form rendering:

* **Path Flattening:** Maps deep CRM paths into single visual controls. Example: A single "Creation Date" widget reads and writes `produced_by.timespan.{begin_of_the_begin, end_of_the_end, identified_by[0].content}`.  
* **Progressive Disclosure:** Surfaces the 20% of properties used in 90% of cataloging by default; tucks specialized CRM paths (e.g., `part_of`, `changed_ownership_through`, `assigned_by`) behind "+ Add Details" panels.  
* **Lossless Round-Tripping:** The frontend maintains the full source JSON-LD AST in memory and applies targeted mutations only to nodes bound to active UI controls. Any unrecognized or unprofiled properties are preserved verbatim on save (with an optional "Raw JSON-LD Inspector" drawer for power users).  
* **Contextual Value Set Binding & Card Partitioning:** Profile slots bind to named Value Sets from the Vocabulary Management Layer so multi-purpose `classified_as` arrays automatically partition into distinct, class-appropriate UI cards (e.g., Gender, Occupation, and Nationality on `Person` vs. Type of Work, Style, and Shape on `HumanMadeObject`). Any valid `Type` in `classified_as` not matched by a configured Value Set surfaces in a lossless **"Other Classifications"** fallback bucket rather than being hidden or stripped on save.  
* **BCP-47 `LangMap` Config Localization:** All human-readable UI Profile strings (`sections[].label`, `slots[].label`, `help_text`, `grid_columns[].label`) are stored as BCP-47 language maps (`{ "en": "Type of Work" }`) resolved via a shared RFC 4647 fallback chain rather than bare strings.

### 6.2 Specialized Cultural Heritage Widgets

* **EDTF / Fuzzy Dates:** Parses Extended Date/Time Format strings (e.g., `1880~/1895?`) directly into Linked Art `TimeSpan` bounds and human-readable display labels.  
* **Multilingual Strings:** Native BCP-47 language selector, per-field script direction (`dir="rtl" | "ltr" | "auto"`, decoupled from UI chrome direction so an Arabic title renders RTL cleanly inside an English workbench), preferred-vs-alternate `Name` classification toggles, and a 1-click **"Translate to..."** inline action streaming local LLM output directly into an additive, provenance-tracked sibling node in the live CRDT room.  
* **IIIF Media Integration:** Inline **Canvas Panel** (Digirati's embeddable web component on IIIF Vault, React-compatible) as the editor's viewer: lightweight single-canvas embedding, native IIIF Content State and region selection for SpecificResource / Media Fragment detail references, annotation display, and manifest navigation via its companion `sequence-panel`. Time-based media (IIIF A/V) falls back to Clover IIIF; Mirador is not used.  
* **Map Authoring UI (Place.defined\_by):** Interactive **MapLibre GL JS** \+ **Terra Draw** editor supporting **Points**, **Bounding Boxes** (drag-to-draw closed 5-vertex POLYGON), and **Polygons** / MULTIPOLYGONs (with vertex editing and inner holes). Automatically normalizes WGS84/CRS84 lon lat coordinate order and OGC counter-clockwise outer-ring winding before serializing to defined\_by (geo:wktLiteral), supports raw WKT paste and .geojson file drop, and provides 1-click geometry seeding from locally loaded Linked Art gazetteer sidecar datasets (e.g., TGN, Wikidata, GeoNames, WHG). Geometries are stored as atomic LWW values in the Y.Map (avoiding concurrent vertex corruption) with active map-editing state broadcast via Yjs Awareness, and index directly into QLever's native GeoSPARQL spatial index.

### 6.3 Context-Aware Real-Time Autocomplete & Reconciliation

* **Local & Sidecar Search (QLever):** Prefix/full-text SPARQL queries across both local records and locally loaded Linked Art sidecar datasets (AAT, ULAN, TGN, Wikidata, etc.) ranked by local usage frequency, returning label, disambiguating context (lifespan dates, parent hierarchy), and URI in under 100ms—with zero live external web or remote SPARQL calls during CRDT editing.  
* **On-Demand Reconciliation Service Callout:** Explicitly invoked by an editor (or MCP agent)—never run automatically in the background due to compute cost—sending the record to a dedicated `lae-reconcile` process to review ranked candidate URIs and confirm `equivalent` links or initiate an entity merge. The LUX data pipeline has no reconciliation service to wrap: its reconciler is exact-key name and identifier lookup over LMDB indexes with a differents blocklist, embedded in a batch build. `lae-reconcile` therefore vendors that reconciler and index code, runs with network access disabled, and is extended to return ranked candidates with match evidence (which name variant or external identifier matched), paired with the editor's lexical and semantic candidate search for fuzzy suggestions.  
* **Inline Stub Creation:** If an entity does not exist locally or in sidecar datasets, users can click *"+ Create new Person/Place/Concept"* inside the autocomplete dropdown, fill a minimal modal, mint a draft stub immediately, and publish it atomically alongside the parent record via bundled transactional publish.  
* **Pre-Creation Duplicate Guard ("Did You Mean...?"):** Runs a lightweight live check combining QLever lexical search and `pgvector` semantic similarity directly inside both the *"Create New Record"* and *"Inline Stub Creation"* modals, warning catalogers about near-duplicate existing entities before a new UUIDv7 is minted.  
* **Hybrid Lexical \+ Semantic Autocomplete (pgvector \+ RRF):** For `rule`\-backed Value Sets and open entity-reference slots targeting Concepts and Reference Authorities (skipping small client-side `enumerated` Value Sets already shipped in the boot bundle), the editor pairs fast QLever prefix/full-text search (\&lt;20ms per keystroke) with debounced (\~150–200ms) semantic vector search over PostgreSQL `entity_embeddings` (`pgvectorhalfvec` HNSW), natively filtered in SQL by `entity_labels.vocab_ids`, `metatype_uris`, and target class. Query strings are embedded in \&lt;20–40ms by a warm local multilingual embedding worker (ONNX Runtime / `llama.cpp` alongside FastAPI, with zero remote API calls). Results merge via **Reciprocal Rank Fusion (RRF)**, tagging purely conceptual hits with a subtle *"Semantic match"* badge so catalogers immediately see why a non-matching label surfaced (e.g., *"round painting"* \-\&gt; *tondo*).  
* **QLever SPARQL SERVICE Integration (Two-Store Simplicity):** FastAPI exposes a lightweight `/sparql/vector` SPARQL `SERVICE` wrapper backed by PostgreSQL `pgvector` so QLever graph queries and Tier 1 MCP duplicate-detection sweeps can invoke semantic similarity natively inside SPARQL without deploying or syncing a third vector store. Abstracting vector search behind this single FastAPI/`SERVICE` contract also leaves a clean drop-in migration seam if QLever's native dense vector indexing matures later.

### 6.4 Ontology-Aware Drag-and-Drop Workbench

* **Typed Drag-and-Drop for Local Records:** A collapsible **Entity Workbench** surfaces search results, recently viewed records, and a persistent pinned tray (so catalogers can pin recurring entities such as an artist, place, or material and drag them across records). Uses native HTML5 Drag-and-Drop (or @dnd-kit with HTML5 fallback) carrying a custom MIME payload (application/x-linked-art-ref+json with id, type, \_label, and primary classified\_as) plus a text/uri-list fallback for cross-tab dragging. Initiating a drag highlights schema-valid drop targets across the active record using UI Profile, SHACL range/classification rules, and Value Set / metatype constraints (e.g., dragging a `Person` highlights `produced_by.carried_out_by`, `current_owner`, and `about`, while dragging a Style concept like *Baroque* highlights the **Style** slot on a `HumanMadeObject` and dims **Occupation**, **Gender**, and **Type of Work**) and auto-expands collapsed progressive-disclosure sections after \~400ms of hover. * **Drag-and-Drop for Images, IIIF Manifests & Web Pages:** Dropping external URLs or IIIF drag-and-drop badges/Content State payloads onto a slot or the record canvas routes through a lightweight FastAPI **Resource Introspection Proxy** (bypassing browser CORS limits) to detect the resource type and generate the appropriate Linked Art subgraph:  
  * *IIIF Manifest / Content State:* Maps to subject\_of \-\> LinguisticObject / DigitalObject (conforms\_to IIIF Presentation API, access\_point) and loads immediately in the inline Canvas Panel viewer.

  * *Generic Web Page (text/html):* Scrapes title, OpenGraph, or embedded JSON-LD into subject\_of \-\> LinguisticObject (classified\_as AAT web pages, identified\_by title, digitally\_carried\_by \-\> DigitalObject with access\_point).  
  * *External Linked Data URI:* Offers 1-click insertion into equivalent (or as a typed entity reference when dropped on a relational slot).  
* **Canvas vs. Slot Disambiguation & Asset Boundary:** Dropping directly onto a typed slot commits immediately to that property; dropping onto the record header or an ambiguous zone opens a 1-click disambiguation popover (e.g., "Add as Primary Representation" vs. "Add as Homepage / Reference (subject\_of)"). v1 stays URL-based to keep the editor decoupled from digital asset storage, with an optional S3/IIIF upload extension point for desktop file drops.

Supports **two-speed model routing** (fast 4B–9B quantized interactive tier for inline editor and on-demand Public Reader clicks; 14B–32B high-quality batch tier for CI catalog drafting, Vocabulary Manager localization, and MCP batch enrichment), a bounded async semaphore queue prioritizing interactive human requests ahead of background MCP jobs, and **graph-grounded glossary injection** pulling authoritative multilingual terms from `entity_labels` (local \+ AAT/Wikidata sidecars) and the Vocabulary Registry into the prompt.  
* **Track A — UI & Config Localization (Offline & Admin-Time):** A CLI/CI diff pipeline (`la-i18n translate`) hashes canonical `en` ICU keys and drafts only new/changed strings via the local LLM, gated by an automated **ICU AST validator** (verifying placeholders, target-language plural categories, tags, and length budgets, with error-feedback retries) and a provenance lockfile (`machine_draft` vs. `human_reviewed`, never overwriting confirmed human edits). In the Vocabulary Manager Admin UI, localizing terms resolves authoritative sidecar dataset labels (AAT, Wikidata, ISO 639\) first before offering a 1-click **"Translate Missing Labels & Scope Notes"** local LLM action (badged as auto-translated until confirmed).  
* **Track B — Entered Linked Art Data Translation (Additive, Provenance-Tracked & Safeguarded):**  
  * *Persisted Authoring (Editor & MCP Batch):* Hard allowlist restricts data translation strictly to `Name.content` and `LinguisticObject.content` (never `Identifier`s, ISO `TimeSpan` bounds, `Place.defined_by` WKT strings, URIs, or diplomatic transcriptions). Never overwrites source text: appends a sibling `Name` (`classified_asaat:300417194`*Translated Title*) or `LinguisticObject` in the live `pycrdt` draft room with mandatory Linked Art `AttributeAssignment` (`assigned_by`) recording the translation activity, model ID/version, timestamp, and `source_content_hash`. Unreviewed entries display a *"Machine-translated"* badge until human Editor publication, at which point `entity_labels` and `entity_embeddings` update transactionally. Subsequent edits to the source node trigger *"Source text changed since translation"* staleness badges and `qa_findings` worklist items with 1-click **Re-translate**.  
  * *Ephemeral Public Reader Translation:* Optional on-demand local LLM translation for anonymous visitors browsing in an unauthored locale, cached in disposable `ephemeral_translations` (invalidated automatically on new revisions), clearly labeled as non-canonical, and never written to `records` or QLever.

## 7\. Vocabulary Management Layer

In Linked Art, most domain distinctions live inside `classified_as` targeting `Type` (and its subclasses `Material`, `Language`, `MeasurementUnit`, `Currency`) rather than separate ontology classes. A dedicated **Vocabulary Management Layer**—functioning as a lightweight, Linked Art–native equivalent of Arches' Reference Data Manager (RDM)—provides a single source of truth governing allowed concept lists across UI Profiles, SHACL validation, drag-and-drop targeting, and MCP agent grounding.

### 7.1 Two-Tier Value Set Model

* **Enumerated / Curated Value Sets (Small, Ordered Lists):** Explicitly ordered lists of `Type` URIs with optional default values and cataloger scope notes (e.g., `vocab:person_name_parts` for Given/Middle/Family/Prefix/Suffix; `vocab:work_title_types` for Primary Name/Title/Subtitle/Alternate Title/Translated Title; plus Dimension types, Measurement Units, Statement types, and Identifier types). Shipped as an ETag-cached JSON bundle to the React SPA at boot so dropdowns, radio pills, and segmented toggles render with zero SPARQL latency.  
* **Rule-Backed / Dynamic Value Sets (Large, Hierarchical, or Metatype-Scoped):** Declaratively defined over local records and locally loaded Linked Art sidecar datasets in QLever (`urn:graph:sidecar:<dataset>`) using Linked Art metatype membership (e.g., concepts classified as AAT *Occupation*, *Gender*, *Nationality*, *Type of Work*, or *Style*), `broader+` hierarchy roots with optional exclusions, or concept class constraints (`Material`, `Language`, `MeasurementUnit`, `Currency`, `Type`). Supports an optional pinned shortlist of frequently used terms on input focus while typing queries the full scoped tree in QLever.

### 7.2 Contextual Slot Binding & Metatype Routing

* **Class- and Path-Scoped Bindings:** Value Sets bind to specific `(EntityClass, PropertyPath)` slots so `Person` records expose Name Part types (`identified_by[Name].part[Name].classified_as`), Gender, Occupation, and Nationality, while `HumanMadeObject`, `VisualItem`, and `LinguisticObject` records expose Work Title types, Type of Work, Style, and Shape—preventing cross-class concept leakage.  
* **Bidirectional Routing & Lossless Fallback:** On load, the UI Profile reads `metatype_uris` / `vocab_ids` from `entity_labels` to route each `classified_as` URI into its matching card, placing any unmatched valid `Type` into a read/removable **"Other Classifications"** fallback bucket to preserve lossless round-tripping.  
* **Linked Art Metatype Integrity:** Adding a local or sidecar concept to a metatype-backed Value Set ensures the concept carries the corresponding Linked Art metatype URI so downstream discovery systems (such as LUX) interpret it consistently.

### 7.3 Single Source of Truth Across Subsystems

* **UI Widgets:** Drives dropdowns, multi-select comboboxes, optional hierarchical tree pickers for AAT facets, and inline cataloger scope notes.  
* **SHACL & JSON-Schema Validation:** Compiles slot bindings directly into `strict` (`sh:Violation`), `extensible` (`sh:Warning`), or `advisory` validation rules.  
* **Concept-Aware Drag-and-Drop:** Refines drop-target highlighting to Value Set / metatype granularity rather than coarse `Type` class matching.  
* **MCP AI Agent Grounding:** Exposes active Value Sets and slot bindings as cacheable MCP resources so agents know exact allowed URIs per class and slot without hallucinating vocabulary terms.

### 7.4 Vocabulary Manager Admin UI & Term Lifecycle

* **Slot & Value Set Workspace:** Dedicated admin UI (Editor / Vocabulary Admin role) organized by Linked Art class to configure slot bindings, toggle curated vs. rule-backed modes, set enforcement levels, edit scope notes, and drag-to-reorder terms without code changes or container redeploys. Labels and scope notes include a compact BCP-47 `LangMap` pill switcher with sidecar-first translation resolution and a 1-click **"Translate Missing Labels & Scope Notes"** local LLM button (marking generated entries as auto-translated until confirmed by a Vocabulary Admin).  
* **Unified Local \+ Sidecar Curation:** Search across local records and sidecar datasets to include existing authority URIs, or mint new local `Type` records (stored in `records` and `entity_labels` with `broader` AAT parent links and optional `equivalent` links) so institutional house terms behave identically to external authority terms.  
* **Deprecation & One-Click Migration:** Marking a concept deprecated hides it from pickers for new edits while preserving display on existing records. QLever backlinks surface exact usage counts (e.g., *"Used in 184 records"*) alongside a 1-click **"Replace Across Records"** action invoking the undoable batch find-and-replace workflow.  
* **Versionable Config Export/Import:** Value Set definitions and slot bindings export and import as declarative YAML/JSON so institutions can version-control vocabulary policy in Git or share a Linked Art Core Vocabulary starter pack.

## 8\. Security, Authentication & Open-Data Governance

### 8.1 Flexible Authentication & Single-Tenant Deployment

* **Interactive Users:** Standard OIDC / OAuth 2.0 integration (supporting institutional SSO/SAML bridges, GitHub, Google, ORCID, or local Keycloak) via Python `Authlib`.  
* **Programmatic Access:** Scoped Personal Access Tokens (PATs) and OAuth2 Client Credentials (service accounts) for ETL scripts, migration pipelines, and CI validation.  
* **Single-Tenant Deployment Model:** Each installation serves a single institution or community with one base URI namespace, one PostgreSQL database, one QLever instance, and one configuration set (OIDC providers, UI profiles, SHACL shapes). Running separate platforms is handled cleanly via separate container deployments rather than multi-tenant data partitioning.

### 8.2 Open Published Data & Write-Only Governance

* **Fully Open Published LOUD:** Once published, all records and fields are publicly readable Linked Open Usable Data—there are no private published records and no field-level redaction profiles.  
* **Write & Lifecycle Permissions (Tiered Human & Agent Governance):** Record-level and role-based ACLs govern authoring, curation, and review actions (`edit_draft`, `propose_merge`, `review_proposal`, `approve_merge_scoped`, `publish`, `delete`, `merge`, `unmerge`, `protect`/lock record, `manage_vocabularies`, `manage_roles`, `manage_users`, `manage_backups`, `manage_system`, `view_analytics`), mirroring Wikidata's page-protection model. System Admin and Ops administrative permissions are separated cleanly from editorial publish rights. AI agents authenticate as role-scoped service accounts across two tiers:  
  * *Tier 1 (Discovery / Triage Agents — small, low-cost models):* Hold `edit_draft` and `propose_merge` only; zero publish or destructive merge rights.  
  * *Tier 2 (Arbiter / Reviewer Agents — frontier models):* Hold `review_proposal` and policy-scoped `approve_merge_scoped`; may approve and auto-execute merges only within server-enforced blast-radius guardrails (neither record `protected`, source inbound QLever backlink count below a configurable threshold or an exact hard external identifier match such as identical ULAN/Wikidata/VIAF URI, and no contradictory core facts), reject false positives into the negative cache, or escalate uncertain, contradictory, protected, or high-blast-radius cases to human Editors (`needs_human_review`).  
  * *Human Editors:* Hold full `publish`, `merge`, `unmerge`, and `protect` authority, resolving escalated proposals in the Visual Merge Workbench and reversing any over-merge via 1-click Unmerge.  
  * *Interactive Chat Permission Intersection:* When a human instructs an agent through the Embedded Agent Chat Workbench, tool execution runs under the strict intersection of the invoking user's permissions and the selected agent tier (`effective_perms = user_perms ∩ agent_tier_perms`), preventing prompt-based privilege escalation (e.g., a Collaborator cannot instruct a frontier cloud model to publish or auto-approve a merge; Editor-initiated merges or multi-record agent jobs require explicit in-chat confirmation).  
* **Draft Boundary:** Unpublished drafts (including brand-new records not yet published) reside solely in PostgreSQL and never enter QLever until an editor publishes them.

### 8.3 Public QLever Access & Operational Protection

Because QLever indexes only fully open published data, no visibility graphs, secondary QLever instances, or SPARQL ACL query rewriting are required.

1. **Read-Only Public SPARQL & Autocomplete:** QLever serves autocomplete, backlinks, and open SPARQL queries directly behind a lightweight reverse proxy / FastAPI layer that enforces read-only methods (blocking external SPARQL Update), query timeouts, and basic rate limiting.  
2. **Internal Write Channel:** SPARQL 1.1 Update endpoints are bound exclusively to the internal network for the Python Sync Worker.

## 9\. AI Agent Collaboration (Model Context Protocol / MCP)

AI agents participate in the editor as first-class collaborative contributors and reviewers via an embedded **Model Context Protocol (MCP)** server, leveraging both live CRDT draft rooms (for single-record edits) and the `curation_proposals` queue (for cross-record merges) with tiered governance and human escalation.

* **Stateless Streamable HTTP Transport:** Mounted directly at `/mcp` inside the FastAPI service using the official MCP Python SDK v2 (stateless Streamable HTTP transport with explicit state handles and cacheable resource metadata, backwards-compatible with earlier MCP clients).  
* **Unified Auth, Attribution & Mandatory CRDT Routing:** Agents authenticate through the same OAuth 2.0 / OIDC and scoped service-account token layer across two role tiers (Tier 1 discovery/draft agents with `edit_draft` and `propose_merge`; Tier 2 frontier arbiter agents with `review_proposal` and guardrail-scoped `approve_merge_scoped`). Single-record draft mutations MUST route through the `pycrdt` room manager—never writing directly to PostgreSQL—so human editors viewing the same record see agent edits stream in live with a distinct "AI Agent" presence badge in Yjs Awareness. Committed revisions record agent service accounts (and model identifiers) in multi-author attribution and support Linked Art `AttributeAssignment` provenance for model-generated claims.  
* **Schema-Aware MCP Surface:** Exposes high-level semantic primitives so agents never hand-author fragile raw CIDOC-CRM JSON-LD:  
  * *Read-Only Resources:*`linkedart://record/{uuid}`, `linkedart://draft/{uuid}`, `linkedart://profile/{class}`, `linkedart://shapes/{class}`, `linkedart://vocabularies`, `linkedart://vocabulary/{id}`, `linkedart://proposals/pending?type=merge`, `linkedart://proposal/{id}`, and `linkedart://qa/worklists` (providing hydrated records, active diffs, UI Profiles, SHACL shapes, curated Value Sets, slot bindings, scope notes, bundled hydrated JSON-LD of both records, QLever backlink summaries, Tier 1 evidence, prior rejected merge history, and structured cross-record QA and link-rot findings).  
  * *Discovery & Reconciliation Tools:*`search_entities` (supporting hybrid lexical \+ semantic `pgvector` search), `run_sparql_readonly` (able to call FastAPI's `/sparql/vector` SPARQL `SERVICE` for multilingual concept discovery and duplicate-detection sweeps), `get_backlinks`, and `reconcile_entity` (invoking the on-demand reconciliation service).  
  * *Draft Authoring Tools:*`create_draft_record`, `set_preferred_name`, `add_statement`, `add_classification`, `set_production`, `add_equivalent`, `set_place_wkt`, and `add_comment` (automatically minting internal sub-node slash IRIs, normalizing stubs, and anchoring agent questions to specific nodes).  
  * *Validation & Long-Running Tasks:*`validate_draft` and `preview_semantic_diff` (enabling agent self-correction loops against JSON-Schema \+ SHACL until zero `sh:Violation` errors remain), `translate_record_fields` (running on a server-owned **asynchronous job model**—an `agent_jobs` table, `linkedart://job/{id}` progress resources, and `cancel_job`—rather than the MCP Tasks extension, which MCP Python SDK v2 does not implement—so Tier 1 agents can batch-translate a `Set` or exhibition checklist into live `pycrdt` draft rooms with `AttributeAssignment` provenance, subject to `edit_draft` permissions, Agent Operations Console quotas, and Editor-gated publication in the Active Drafts & Review Inbox), with the same job model covering other asynchronous multi-record workflows such as IIIF transcription or batch set enrichment.  
* **Embedded Agent Chat Orchestrator & Multi-Provider LLM Layer:** FastAPI hosts an in-process **Agent Chat Orchestrator** that connects as an MCP client directly to `/mcp`—eliminating duplicated tool definitions while guaranteeing mandatory `pycrdt` room routing, `agent_audit_log` recording, `agent_quotas` enforcement, and circuit-breaker compliance. Extends the OpenAI-compatible local LLM client into a unified **Multi-Provider LLM Adapter Layer** (thin native adapters or `litellm`) supporting local models (`llama.cpp` server, `vLLM`, `Ollama`) alongside cloud frontier providers (Google Gemini, Anthropic Claude, OpenAI, and institutional Vertex AI / AWS Bedrock / Azure OpenAI endpoints). API keys are configured primarily by institutional Admins in `llm_provider_configs` (envelope-encrypted at rest, never sent to browsers or logged), with optional admin-togglable **per-user BYOK** keys scoped strictly to that user's own sessions, governed by an instance-level `local_only` vs. `allow_cloud` policy switch.  
  * *Proposal & Two-Tier Merge Review Tools:* Tier 1 calls `propose_merge(source_uri, target_uri, evidence, field_resolution_plan)` (automatically deduplicating and rejecting blocked "Do Not Merge" pairs via the negative cache). Tier 2 calls `claim_proposal(proposal_id)` (short lease preventing duplicate parallel reviews), `approve_merge(proposal_id, rationale, final_field_plan)` (executes only if server-side blast-radius guardrails pass; otherwise automatically routes to human review), `reject_merge(proposal_id, rationale, block_future=True)` (populates negative cache), and `escalate_to_human(proposal_id, rationale)` (flags `needs_human_review` for the Visual Merge Workbench).  
* **Agent Observability, Quotas & Circuit Breaker (Agent Operations Console):** Dedicated Admin/Editor operations console tracking per-agent rate limits, daily auto-merge caps, live MCP tool-call audit logs (`agent_audit_log`), per-user and per-provider token and spend caps for cloud chat models, and **per-model over-merge / unmerge rate metrics**, paired with a 1-click **"Pause All Agents / Pause Auto-Merge"** circuit breaker to halt misbehaving models or prompt regressions immediately.

## 10\. Administration Control Plane & Operations

Operational and administrative workflows are consolidated into a dedicated **Administration Control Plane** (restricted to `System Admin` / `Ops` roles, cleanly separated from editorial `publish` authority), unifying infrastructure reliability, telemetry, identity management, and policy governance alongside the Vocabulary Manager Admin UI (Section 7.4) and Agent Operations Console (Section 9).

### 10.1 Automated & On-Demand Backups (Disaster Recovery)

* **Automated Scheduled Backups (PostgreSQL SoR):** Continuous WAL archiving for **Point-in-Time Recovery (PITR)** (via `pgBackRest` or `Barman` to institutional S3/object storage or NFS) paired with automated daily incremental and weekly full backups covering `records`, `record_revisions`, `entity_labels`, `vocabularies`, `curation_proposals`, `merge_batches`, and `crdt_drafts`.  
* **On-Demand Snapshots & Pre-Migration Checkpoints:** 1-click **"Create Backup Now"** in the Admin UI (with optional reason label, e.g., before a sidecar refresh or large batch commit) plus optional automatic pre-flight checkpoints before major batch imports or schema migrations.  
* **Verification, Retention & Portable Logical Dumps:** Automated periodic restore-verification dry runs (checksum and schema integrity checks), configurable GFS retention policies (daily/weekly/monthly), encrypted backup storage (isolating `llm_provider_configs` master keys), and 1-click downloads of portable logical Linked Art JSON-LD / N-Triples archives for long-term institutional preservation.  
* **Derived Index Recovery:** QLever indexes and `entity_embeddings` (`pgvector`) rebuild deterministically from PostgreSQL, with optional cold snapshots of compiled QLever index files captured after each blue/green `IndexBuilderMain` rebuild so disaster recovery takes minutes rather than hours.

### 10.2 Health Checks, Process Monitoring & Outbox Observability

* **Probes & Telemetry Endpoints:** Exposes `/health/live`, `/health/ready`, and Prometheus/OpenMetrics `/metrics` endpoints for institutional Grafana/Alertmanager integration alongside an in-app **System Health Dashboard**.  
* **Subsystem Monitoring & Remediation Controls:** Tracks **PostgreSQL \+ `pgvector`** (connection pool saturation, WAL lag, disk usage, HNSW index bloat, slow queries), **QLever** (p50/p95 query latency, memory footprint, delta-triple edit sidecar count vs. rebuild threshold, query timeouts), **Python Sync Worker** (`outbox_events` queue depth, sync lag, micro-batch throughput, and dead-letter/failed events with N-Triples diff inspection and 1-click **Retry** or **Skip & Alert**), **CRDT WebSocket Manager** (active rooms in memory, connected editors/agents, room memory, oldest uncompacted `crdt_updates`, with force-compact and idle/stuck room eviction controls), **AI & Sidecar Services** (warm embedding worker latency, local LLM interactive/batch queue depth, cloud LLM reachability/error rates, reconciliation service health, with graceful lexical-only fallback when the embedder stalls), and **Background Daemons** (5-day draft reaper, QA & link-rot sweeper, and backup runner—showing last run status, duration, next schedule, and 1-click **Run Now / Pause**).  
* **Degraded Modes:** The system runs with the embedding worker, local and cloud LLMs, and the reconciliation service all absent or paused: autocomplete and the Pre-Creation Duplicate Guard fall back to lexical-only, translation, chat, and semantic features disable with a visible status, and nothing in the core edit \-\> validate \-\> publish \-\> sync loop depends on them.

### 10.3 Usage Statistics & Institutional Analytics

* **Per User & Per Agent:** Rolled-up metrics (`usage_metrics_daily`, `record_revisions`, `agent_audit_log`—never logging sensitive query PII) tracking records created, drafts edited, records published, merges approved/rejected/unmerged, comments resolved, active session time, and MCP tool calls, token consumption, and cloud LLM spend.  
* **Per Record Type (Linked Art Class):** Total published record counts, growth over time, active drafts, validation warning density, and QA finding counts across `HumanMadeObject`, `Person`, `Group`, `Place`, `VisualItem`, `LinguisticObject`, `Set`, and `Concept`.  
* **Per Function / Feature:** Request counts and latency across REST endpoints, read-only SPARQL queries, hybrid lexical vs. semantic autocomplete hit rates, on-demand reconciliation calls, local LLM translations (inline, batch, and ephemeral Public Reader), IIIF/URL introspection drops, Force-Directed Graph / Mermaid usage, and Lightweight Public Reader traffic plus JSON-LD/Turtle download counts.  
* **Exportable Reporting:** Date-range filterable dashboards with CSV/JSON export for museum/library grant and institutional reporting.

### 10.4 User, Role & Token Administration

* **User Directory & IdP Role Mapping:** Manage human users and AI service accounts, map OIDC/SSO IdP groups to platform roles (`Viewer`, `Collaborator`, `Editor`, `Vocabulary Admin`, `System Admin`, `Tier 1 Agent`, `Tier 2 Agent`), and grant or revoke granular permissions.  
* **Session Control & Effective-Permission Debugging:** Immediate account suspension/deactivation (revoking active OIDC sessions and ejecting open CRDT WebSocket connections without deleting historical revision attribution) plus impersonation-free **"View Effective Permissions"** debugging (including `user_perms ∩ agent_tier_perms` chat rules).  
* **Service Accounts & API Token Lifecycle:** Issue, scope, set expirations on, rotate, and revoke Personal Access Tokens (PATs) and OAuth2 Client Credentials for ETL pipelines, CI validators, and MCP agents with last-used timestamp and IP visibility.

### 10.5 Operational Lifecycle, Policy Controls & Security Governance

* **Sidecar Dataset & Vocabulary Ingestion Manager:** Upload, version, refresh, or unload locally loaded Linked Art sidecar datasets (`urn:graph:sidecar:aat`, `ulan`, `tgn`, `wikidata`, `geonames`, `whg`) via UI or CLI, displaying dataset version, entity count, and refresh timestamp while orchestrating the full downstream cascade (QLever sidecar graph swap \-\> `entity_labels` upsert \-\> materialized `vocab_ids` refresh \-\> `entity_embeddings` re-embedding).  
* **Maintenance Mode, Broadcast Notices & Manual QLever Rebuilds:** Push live WebSocket toast/banner notices to all connected React editors, toggle **Read-Only Maintenance Mode** (blocking CRDT writes and publishing while keeping the Lightweight Public Reader and `/id/{uuidv7}` content negotiation online), inspect active CRDT rooms, and trigger blue/green `IndexBuilderMain` rebuilds on demand.  
* **Central System Policy & SSRF Egress Controls:** Versioned settings screen (`system_settings`) governing the 5-day draft expiry TTL, QLever rebuild delta-triple threshold, public SPARQL query timeouts/rate limits, Tier 2 auto-merge blast-radius guardrails and daily caps, LLM & privacy policies (`local_only` vs. `allow_cloud`, per-user BYOK toggle, chat retention, model endpoints), and an **Egress / SSRF Security Allowlist & Denylist** for the FastAPI Resource Introspection Proxy and Link-Rot Checker (blocking RFC 1918, loopback, and cloud metadata IPs).  
* **Schema, UI Profile, Embedding Model & i18n Lifecycle:** Manage Declarative UI Profiles, SHACL shape bundles, and pinned `@context` versions with dry-run impact previews and GitOps YAML/JSON export/import \+ rollback; run zero-downtime **Embedding Model Migrations** (background re-embedding into a shadow `entity_embeddings` column/table with atomic swap); and upload/activate UI locale packs or flush the disposable `ephemeral_translations` cache.  
* **Protected Records, Batch Rollback & Merge Audit Console:** Central registry of all `protected` records with bulk lock/unlock, unified history of Batch Staging Wizard commits, `merge_batches`, and `split_batches` with 1-click **Rollback / Unmerge / Unsplit**, and admin cleanup controls for stuck `curation_proposals` leases or stale `qa_findings`.  
* **Immutable Security Audit Log & Scheduled Bulk LOUD Exports:** Tamper-evident `admin_audit_log` capturing all administrative mutations (role grants, API key/BYOK vault edits, circuit-breaker toggles, hard-deletes/unmerges, backup restores, policy changes) filterable in the UI and exportable (JSONL/CSV) to institutional SIEMs; paired with management of **Outbound Signed Webhooks** (HMAC-signed event subscriptions filtered by publish, merge, split, delete, or Tier 2 escalation, subject to the SSRF egress allowlist/denylist, with delivery logs and retry controls), scheduled and on-demand **Full Bulk LOUD Exports** (compressed JSON-LD / N-Triples snapshots stripped of internal sub-node slash IRIs), and `/activity/stream` feed monitoring.

## 12\. Bulk Operations & Interoperability

* **Content Negotiation & Versioned Permalinks:** Dereferencing any record URI (`/id/{uuidv7}`) with `Accept: text/html` serves the fast, read-only **Lightweight Public Reader** by default (with JSON-LD/Turtle download, IIIF viewer, Mermaid toggle, and citation widget) and lazy-loads the collaborative React \+ Yjs editor only when a user clicks **Edit**. Requests specifying `application/ld+json` (with the Linked Art profile parameter, `profile="https://linked.art/ns/v1/linked-art.json"`) or `text/turtle` return raw data serializations, automatically stripping all internal sub-node slash IRIs so blank/nested nodes remain anonymous externally. Supports immutable versioned permalinks (`/id/{uuidv7}?version=N`) and **Memento (`Accept-Datetime`)** negotiation returning exact historical revisions for reproducible scholarly citations.  
* **ActivityStreams 2.0 Change Feed, IIIF Change Discovery API & Outbound Webhooks:** Exposes an ordered `/activity/stream` endpoint (`Create`, `Update`, `Delete`, `Move` for merges) backed by `record_revisions` and aligned explicitly with the **IIIF Change Discovery API** (ActivityStreams 2.0 profile) so external discovery portals and cultural heritage harvesters can consume incremental updates out of the box. **Outbound Signed Webhooks** serve as the push-based counterpart to pull-based `/activity/stream`, configured in the Administration Control Plane and dispatched from `outbox_events` with HMAC signatures, retries, and SSRF egress filtering so downstream websites, search portals, or Slack/Teams channels react immediately to publishes, merges, splits, and Tier 2 human escalations.  
* **Batch Operations & Interactive Batch Staging Wizard:** CLI and UI tools for bulk JSON-LD import, CSV-to-Linked-Art mapping, and undoable bulk find-and-replace across record sets (e.g., replacing a deprecated concept URI across 1,000 objects as a single batch transaction, also triggered when deprecating terms in the Vocabulary Manager). Includes an **Interactive Batch Staging Wizard**: a dry-run staging UI for CSV and JSON-LD uploads providing column-to-UI-Profile mapping, bulk SHACL validation preview, duplicate detection, and a reversible batch ID prior to committing changes into 10M+ live records. Scheduled and on-demand **Full Bulk LOUD Exports** (compressed JSON-LD / N-Triples stripped of internal sub-node slash IRIs) and versioned sidecar dataset refreshes are orchestrated from the Administration Control Plane (Section 10). External reference vocabularies are ingested via the same bulk bootstrap pipeline into local Linked Art sidecar datasets and QLever sidecar graphs. Value Set definitions and slot bindings import and export as declarative YAML/JSON files. Initial multi-million-record migrations use a dedicated bulk bootstrap pipeline (PostgreSQL COPY \+ offline QLever IndexBuilderMain from bulk N-Triples export) rather than streaming through the incremental outbox.

## 13\. Testing & Quality Strategy

* **Golden Round-Trip Corpus:** The Linked Art example records (plus institutional samples covering every profiled class and unprofiled extensions) load \-\> hydrate into a Y.Doc \-\> project \-\> strip, and must reproduce the input JSON-LD byte-for-byte after canonicalization, including array order.  
* **CRDT Convergence Property Tests:** Randomized concurrent operation sequences across multiple simulated clients (keyed-map inserts, `_order` moves, Y.Text edits, offline replay against bumped `draft_epoch`) must converge to identical projections.  
* **Sync Worker Idempotency & Consistency:** Replaying any outbox range (including duplicates and crash mid-batch) must yield the same QLever state; fixtures pin canonical N-Triples serialization and diff output; the sampled PostgreSQL-vs-QLever audit runs in CI against a small index.  
* **Validation Fixtures & Latency Budgets:** Per-class JSON-Schema and SHACL fixtures (valid, `sh:Warning`, `sh:Violation`), with CI asserting the per-record validation latency budget that batch staging and agent loops depend on.  
* **Existing Gates:** `eslint-plugin-i18next` no-literal-string lint, `LangMap` schema checks, pseudo-locale rendering, and `axe-core` \+ Playwright accessibility and keyboard-only smoke tests (Sections 6.7 and 6.9).

### Open Questions & Spikes

1. **`/sparql/vector` SPARQL `SERVICE` wrapper vs. application-layer fusion:** Undecided, but informed by an existing implementation: the LUX middle tier's `sparql_service` package is a tested SPARQL `SERVICE` endpoint that QLever federates to, with a `vec:` predicate vocabulary, a parser for QLever's pushed-down `VALUES` block, graph-first and vector-first modes, and documented pitfalls (no SERVICE timeout in QLever, the `service-max-value-rows` silent cutoff, unshared duplicate SERVICE calls). The leading option is to port that contract to `pgvector`; the alternative remains RRF fusion in FastAPI with `pgvector` hits injected as `VALUES`, retaining SERVICE only as a YASGUI convenience. Decide in Phase 3 after Spike S1.  
2. **QLever text-index freshness for autocomplete:** Autocomplete and graph-aware search stay in QLever. Spike: confirm that `ql:contains-word` prefix search covers literals inserted via SPARQL Update (word-lookup triples for updated literals landed upstream recently) so newly published stubs autocomplete before the next rebuild; otherwise overlay recently published entities from `entity_labels` until the blue/green rebuild catches up.  
3. **`pycrdt-websocket` under load:** Validate awareness fan-out, room eviction, and reconnect behaviour with 30 simulated editors before locking; fallback is a Yjs-wire-compatible sidecar behind the same room-manager interface.  
4. **SHACL latency budget:** Measure `pyshacl` (or a compiled evaluator) against the project-authored shapes per class to set the per-record budget assumed by the Batch Staging Wizard and agent self-correction loops.
