## Step 0.9

1. **BCE dates in `TimeSpan`s.** Linked Art bounds are `xsd:dateTime`, whose value space includes
   negative (BCE) years such as `-0500-01-01T00:00:00Z`; no corpus record has one yet, but
   antiquities need them. Two parts of the planned validation stack cannot handle them. rdflib,
   under pyshacl, cannot represent a datetime before year 1, so `sh:datatype xsd:dateTime`
   reports a valid BCE bound as a violation and `sh:lessThanOrEquals` raises `TypeError`, which
   aborts the whole validation (`docs/spikes/S4-shacl.md`, finding 6). And JSON Schema's
   `format: date-time` is RFC 3339, which allows only four-digit years, so the vendored schema
   rejects BCE bounds once Step 1.9 turns format checking on. The S4 report recommends that Step
   1.9 move both `TimeSpan` checks (`LAE-SHACL-009`, `LAE-SHACL-010`) into its Python rule
   `LAE-RULE-001`, comparing ISO 8601 values with signed years. Please confirm that BCE dates must
   be supported, so that Step 1.9 also accepts signed years in the `date-time` format check
   (for example with a custom format checker) rather than inheriting the RFC 3339 limit.
   **Resolved (orchestrator under the owner's delegation, 2026-11-22; reversible):** BCE dates must be supported (antiquities). Step 1.9 accepts signed years in `date-time` with a custom format checker, compares `TimeSpan` bounds in the Python rule `LAE-RULE-001`, and keeps `xsd:dateTime` datatype and ordering checks out of SHACL. The schema's RFC 3339 limit is listed for upstream in `docs/upstream/README.md`. **Confirmed by the owner, 2026-11-22.**

## Step 0.8

1. **ADR-0018 was accepted by the reviewer, not by the owner.** Spike S3 is GO. The draft
   projection rules fail 17 of 244 corpus files when taken literally, and lose one client's work
   when two clients add the first value of the same property at once. The rules that pass are
   R1–R19 in `docs/spikes/S3-projection.md`. They refine the wording of locked register entries
   B2 and B3; `docs/decisions/0018-projection-rule-refinements-from-s3.md` records the changes,
   and the independent larger-model reviewer (Claude Fable 5.2) set it to Accepted under the
   owner's delegation and updated B2 and B3 to cite it. The one change of substance to confirm:
   **an array is no longer a `Y.Map` of its own.** Its items are entries in the map of the object
   that has the property, keyed by `[property, item key]` (item key = internal node IRI or target
   URI, as before). Everything else in B2 and B3 stands. Step 1.4 proceeds on this basis; say so
   if you want a different layout.
   **Resolved (reviewer, 2026-11-22):** accepted as above. The owner may override.
2. **Concurrent first insert into a property with no values: closed.** The first version of the
   spike lost one client's entry when two clients each created the array, and proposed
   pre-creating containers for profiled properties only. With rule R6 there is nothing to create,
   so every first insert is kept for every property, profiled or not, at any depth (tested with
   two and three Python replicas and with a JavaScript Yjs client against a Python client on all
   245 test documents). No decision is needed.
3. **Single-valued properties stay last-writer-wins. Is that what you want for nodes?** If two
   clients each create the value of a single-valued property at the same moment (each adds
   `timespan` to an activity that has none, or each creates `produced_by` on a new object), the
   record converges on one client's whole value and the other's is replaced, including anything
   added inside it. It is never a mixture. This follows from "single-valued" and from spec §4.2
   ("scalar fields use LWW"), and the window is the network round-trip of a live session, so the
   rules keep it (R14). The alternative is to keep both values and project the property as a
   two-element array, which the validator would then report for a person to resolve. That costs
   a merge step in the UI and is not in any phase guide. Please confirm that last-writer-wins is
   acceptable, in particular for a person and an agent filling in `produced_by` on a new record
   at the same time (Phase 3).
4. **Records that repeat a reference in one array are preserved, not deduplicated.**
   `tests/corpus/institutional/yuag-lin-176060.json` and `yuag-lin-176699.json` have
   `aat:300027221` twice in `classified_as`. The lossless principle (spec §1; decision C5,
   "never dropped") means both occurrences must survive a round-trip, and the reviewer confirmed
   that they do: rule R7 keys the second occurrence `<id> #2`, both project at their original
   positions (`test_duplicate_reference_is_preserved_with_suffixed_key`), and both files are in
   the 244 of 244. Editing operations never create a duplicate (adding a reference that is
   already present is a no-op). Still open, and not blocking: should the QA sweeper report an
   imported duplicate as a finding?
5. **`Text` positions differ between the libraries.** `pycrdt` counts UTF-8 bytes and Yjs counts
   UTF-16 code units, and `pycrdt` does not reject an offset inside a character. Rule R19 makes
   the operations API count code points and convert. No decision is needed; this is recorded
   because Phase 3 MCP tools that edit text ranges inherit it.
6. **Not verified:** a live browser session over `y-websocket`. The cross-language check ran Yjs
   13.6.33 under Node against `pycrdt` state offline (`docs/spikes/S3-projection.md` §4.4).

## Step 1.3

1. **Embedded nodes that carry their own `id`: decided, ADR-0021.** As first written, Step 1.3
   reduced every object with a foreign `id` to `{"id": uri}`, so an embedded `Name`, `Identifier`,
   `Production`, `TimeSpan`, `Dimension` or statement that an institution had given an IRI was
   not indexed beyond the link. The reviewer changed this: such a node is emitted, in RDF only,
   under the derived node IRI `<record_uri>/node/<uuidv5(original id)>` with a `la:equivalent`
   triple to its original id; `records.data` keeps the original id; references are unchanged.
   Of the 205 corpus objects with a foreign `id` and more than `type` / `_label`, 3 are embedded
   `Name`s and are now indexed; 202 are references and still emit only the link.
   **Resolved (critical-step reviewer under the owner's delegation, 2026-11-22; reversible):**
   ADR-0021. Rob Sanderson may override, in particular the two class lists and the choice of
   `la:equivalent` as the linking predicate.
2. **Inline meta-types on concept references are not indexed from records. Phase 2 must harvest
   them.** `{"id": aat:300435424, "type": "Type", "classified_as": [{"id": aat:300418049}]}`
   emits `<node> crm:P2_has_type <aat:300435424>` and nothing about the concept: the concept owns
   its meta-type (183 such references in the corpus, and the same for `notation` on a `Language`
   or `Currency`, 18). So the triple `<aat:300435424> crm:P2_has_type <aat:300418049>` is in
   QLever only if the concept's own record or a sidecar graph says it. Rule-backed Value Set
   membership (Phase 2 Step 2.1, `rule.metatype_uris`) must therefore harvest inline meta-types
   from published records, as LUX's `reference_manager.walk_for_refs` does, into
   `entity_labels.metatype_uris` (or into the sidecar graphs), and must not rely on the default
   graph alone. A note is in the Step 2.1 guide text. No decision needed unless the owner
   prefers the sidecar graphs to `entity_labels` as the place to put them.
3. **Expansion rejects what pyld would silently change.** Not a question; for the record. pyld
   drops a triple whose IRI contains a forbidden character or any Unicode white space (U+00A0,
   U+2028, …), resolves a relative `id` or an undefined `type` against
   `http://example.org/base/`, and writes `INF` for an overflowing number. `expand_to_ntriples`
   raises `InvalidIRIError` / `InvalidLiteralError` in each case, and for an `xsd:dateTime` that
   is not a full date-time (`"1642"`, `"1642-01-01"`), and `ExpansionError` for an `@context` on
   any node below the root, so a publish (Step 1.10) must be ready to report these as validation
   failures. Rejecting, not repairing, is deliberate: a repaired `id` would no longer be the one
   in `records.data`; repair belongs in import. Signed BCE years are accepted. No corpus record
   is rejected.
4. **QLever decodes `\uXXXX` in an update before it tokenizes, even after an escaped
   backslash.** Found by the review's run against Homebrew QLever 0.6.0: a literal whose text
   contains a backslash followed by `u0041` made `INSERT DATA` fail with HTTP 400, and one with
   `u0022` would have stored a different literal than the index build does. Canonical lines now
   write a `u`/`U` that follows a backslash as `\u0075`/`\u0055`, which N-Triples and SPARQL
   read alike (verified: index build and update give the same literal back). The vendored
   `lae.sparql.terms.string_literal` still has the upstream behaviour: user text containing a
   backslash followed by `u` and four hex digits gives a query QLever rejects or reads
   differently (it cannot end the string, so it is not an injection). Phase 2 Step 2.2, which
   builds queries from user input with it, should apply the same escape, and the fix should go
   upstream to `lux/qlever-middletier`. No decision needed.

## Step 1.9

1. **How is an EDTF string marked in a `TimeSpan`?** The guide asks for a rule on "EDTF syntax in
   `identified_by` of a `TimeSpan`" (`LAE-RULE-002`), but nothing says which of a `TimeSpan`'s
   names is EDTF, and its ordinary names are free-text display labels ("ca. 1642", "1503-1506").
   The rule therefore checks only a `Name` or `Identifier` classified as
   `http://id.loc.gov/datatypes/edtf` (the Library of Congress EDTF datatype; AAT has no concept
   for EDTF), and reports invalid syntax as a warning. No corpus record has such a name, and
   until Step 1.18's `EdtfWidget` writes that classification the rule never fires. Please
   confirm the marker, or name another (ADR-0025, item 4). "Valid EDTF" means what edtf.js
   4.12.0 `parse()` accepts (the parser the editor will use), which is not quite the Library of
   Congress text: it also takes a century (`19`), a decade (`198`) and `02-29` in any year, and
   refuses a qualified season (`2001-21~`). Say if the specification should win instead; then
   client and server will disagree on those strings.
2. **OWNER DECISION NEEDED: records whose embedded nodes have their own ids cannot be
   published.** Two accepted decisions meet here. ADR-0021 says an embedded node that arrives
   with an `id` of its own (institutional data mints IRIs for a `Name`, an `Identifier`, a
   `TimeSpan`, a `Dimension`) is part of the record: it is indexed, and `records.data` keeps
   that `id` so the round trip is lossless. Decision C1 says the vendored Linked Art JSON
   Schema is the first gate, and that schema does not allow an `id` on `Name`, `Identifier`,
   `TimeSpan` or `Dimension` (`additionalProperties`; it does allow one on a `Production`).
   Internal node IRIs (`<record>/node/<uuidv7>`) are stripped before the schema runs; an id
   from elsewhere is not, because it is part of the record. So this, from
   `tests/corpus/linkedart/object-3.json`,

   ```json
   "identified_by": [{"id": "https://linked.art/example/Name/0", "type": "Name", "content": "Hacha"}]
   ```

   gives `LAE-SCHEMA-anyOf` at `/identified_by/0` with `params.cause` =
   `{"code": "LAE-SCHEMA-additionalProperties", "path": "/identified_by/0"}` (on a `TimeSpan`
   or a `Dimension` the code is `LAE-SCHEMA-additionalProperties` directly); without the `id`
   the same `Name` is valid. `validate` stops at schema violations, so `POST /api/validate`
   reports the record as not publishable and Step 1.10 will refuse it; `lae bootstrap load`
   applies the same schema and reports it as schema-invalid instead of loading it. Three corpus
   files are affected (`object-3.json`, `object-nightwatch-43.json`, `person-rembrandt-4.json`,
   all in `KNOWN_FAILURES.md`). So ADR-0021's case, a record whose `Name`s, `Identifier`s,
   `TimeSpan`s or `Dimension`s carry institutional IRIs, is indexed correctly by expansion but
   can neither be loaded nor published. The choices:
   (a) keep the gate as it is: such data has to drop those ids before it comes in, and
   ADR-0021 then matters only for the classes the schema lets carry an `id`;
   (b) before the schema runs, also strip the `id` of every node that expansion treats as
   embedded (`lae.rdf.expand._is_embedded`), in `validate_schema` and in bulk load, which
   loosens the gate relative to the upstream schema by exactly that property;
   (c) change the schema upstream to allow `id` on these classes and re-vendor.
   Nothing was changed in Step 1.9 or its review: (b) and (c) alter what "passes the Linked
   Art schema" means, which is the owner's to decide. SHACL and the rules already handle such
   nodes (their diagnostics point at the right JSON path;
   `test_paths_through_embedded_nodes_with_their_own_ids`).
3. **`POST /api/records/{id}/draft/validate` has no draft source yet.** Step 1.8 was not on main,

   (`lae.api.validation`) from `app.state.draft_snapshot_source`, and answers 503
