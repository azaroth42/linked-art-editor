## Step 0.9

1. **BCE dates in `TimeSpan`s.** Linked Art bounds are `xsd:dateTime`, whose value space includes
   negative (BCE) years such as `-0500-01-01T00:00:00Z`; no corpus record has one yet, but
   antiquities need them. Two parts of the planned validation stack cannot handle them. rdflib,
   under pyshacl, cannot represent a datetime before year 1, so `sh:datatype xsd:dateTime`
   reports a valid BCE bound as a violation and `sh:lessThanOrEquals` raises `TypeError`, which
   aborts the whole validation (`docs/spikes/S4-shacl.md`, finding 6). And JSON Schema's
   `format: date-time` is RFC 3339, which allows only four-digit years, so the vendored schema
   rejects BCE bounds once Step 1.9 turns format checking on. The S4 report recommends that Step
   1.9 move both `TimeSpan` checks (`LAE-SHACL-009`, `LAE-SHACL-010`) into its Python rule
   `LAE-RULE-001`, comparing ISO 8601 values with signed years. Please confirm that BCE dates must
   be supported, so that Step 1.9 also accepts signed years in the `date-time` format check
   (for example with a custom format checker) rather than inheriting the RFC 3339 limit.
   **Resolved (orchestrator under the owner's delegation, 2026-11-22; reversible):** BCE dates must be supported (antiquities). Step 1.9 accepts signed years in `date-time` with a custom format checker, compares `TimeSpan` bounds in the Python rule `LAE-RULE-001`, and keeps `xsd:dateTime` datatype and ordering checks out of SHACL. The schema's RFC 3339 limit is listed for upstream in `docs/upstream/README.md`.

## Step 0.12

1. **One Value Set per `(class, path)`, or several?** Spec §7.2 binds Gender, Occupation, and
   Nationality to the same `(Person, classified_as)`, and spec §6.1 partitions one `classified_as`
   array into several cards (Type of Work, Style, Shape). Phase 2 Step 2.1, however, makes
   `slot_vocabulary_bindings` unique on `(entity_class, property_path)`, which allows only one
   Value Set per path. The Step 0.12 schema and validator follow the spec: several bindings may
   share a `(class, path)`, and uniqueness is on `(class, path, value_set)`. Please confirm, so
   that Step 2.1 can make its unique constraint `(entity_class, property_path, vocabulary_id)`.
   Step 2.2 is affected too: its rule flags every value at the path that is outside one bound
   Value Set, so under a strict Gender binding every Occupation would be a violation. A rule that
   accepts a value claimed by any Value Set bound at that path, and leaves unclaimed values to the
   Other Classifications bucket (decision C5), would match the spec.
   **Resolved (orchestrator, 2026-11-22):** the spec is authoritative here and the Phase 2 guide was wrong. Step 2.1 now makes bindings unique on `(entity_class, property_path, vocabulary_id)`, and Step 2.2 checks a value only against the bindings that claim it (by membership or metatype), leaving unclaimed values to Other Classifications. Register entry C4 updated. The owner may override.

## Step 0.8

1. **ADR-0018 was accepted by the reviewer, not by the owner.** Spike S3 is GO. The draft
   projection rules fail 17 of 244 corpus files when taken literally, and lose one client's work
   when two clients add the first value of the same property at once. The rules that pass are
   R1–R19 in `docs/spikes/S3-projection.md`. They refine the wording of locked register entries
   B2 and B3; `docs/decisions/0018-projection-rule-refinements-from-s3.md` records the changes,
   and the independent larger-model reviewer (Claude Fable 5.2) set it to Accepted under the
   owner's delegation and updated B2 and B3 to cite it. The one change of substance to confirm:
   **an array is no longer a `Y.Map` of its own.** Its items are entries in the map of the object
   that has the property, keyed by `[property, item key]` (item key = internal node IRI or target
   URI, as before). Everything else in B2 and B3 stands. Step 1.4 proceeds on this basis; say so
   if you want a different layout.
   **Resolved (reviewer, 2026-11-22):** accepted as above. The owner may override.
2. **Concurrent first insert into a property with no values: closed.** The first version of the
   spike lost one client's entry when two clients each created the array, and proposed
   pre-creating containers for profiled properties only. With rule R6 there is nothing to create,
   so every first insert is kept for every property, profiled or not, at any depth (tested with
   two and three Python replicas and with a JavaScript Yjs client against a Python client on all
   245 test documents). No decision is needed.
3. **Single-valued properties stay last-writer-wins. Is that what you want for nodes?** If two
   clients each create the value of a single-valued property at the same moment (each adds
   `timespan` to an activity that has none, or each creates `produced_by` on a new object), the
   record converges on one client's whole value and the other's is replaced, including anything
   added inside it. It is never a mixture. This follows from "single-valued" and from spec §4.2
   ("scalar fields use LWW"), and the window is the network round-trip of a live session, so the
   rules keep it (R14). The alternative is to keep both values and project the property as a
   two-element array, which the validator would then report for a person to resolve. That costs
   a merge step in the UI and is not in any phase guide. Please confirm that last-writer-wins is
   acceptable, in particular for a person and an agent filling in `produced_by` on a new record
   at the same time (Phase 3).
4. **Records that repeat a reference in one array are preserved, not deduplicated.**
   `tests/corpus/institutional/yuag-lin-176060.json` and `yuag-lin-176699.json` have
   `aat:300027221` twice in `classified_as`. The lossless principle (spec §1; decision C5,
   "never dropped") means both occurrences must survive a round-trip, and the reviewer confirmed
   that they do: rule R7 keys the second occurrence `<id> #2`, both project at their original
   positions (`test_duplicate_reference_is_preserved_with_suffixed_key`), and both files are in
   the 244 of 244. Editing operations never create a duplicate (adding a reference that is
   already present is a no-op). Still open, and not blocking: should the QA sweeper report an
   imported duplicate as a finding?
5. **`Text` positions differ between the libraries.** `pycrdt` counts UTF-8 bytes and Yjs counts
   UTF-16 code units, and `pycrdt` does not reject an offset inside a character. Rule R19 makes
   the operations API count code points and convert. No decision is needed; this is recorded
   because Phase 3 MCP tools that edit text ranges inherit it.
6. **Not verified:** a live browser session over `y-websocket`. The cross-language check ran Yjs
   13.6.33 under Node against `pycrdt` state offline (`docs/spikes/S3-projection.md` §4.4).

## Step 0.6

Spike S1 (`docs/spikes/S1-qlever.md`) is a **NO-GO for text freshness** and a GO for updates,
persistence, `SERVICE`, and rebuilds. Decision F9 needs a human to acknowledge the NO-GO.

1. **NO-GO: text search does not see literals inserted by SPARQL Update.** Measured on the pinned
   Homebrew QLever 0.6.0 (`6c5861a`): after `INSERT DATA` of `rdfs:label "zebra-crossing-xyz"`,
   neither prefix search (`ql:contains-word "zebra*"`) nor whole-word search (`ql:has-word
   "zebra"`) finds the new literal until the index is rebuilt; the control literal in the base
   index is found by both. A source build of `lux/qlever-dev` master (`ba7b74c`) finds it with
   `ql:has-word` (upstream #3794, after 0.6.0) but still not with `ql:contains-word` prefixes.
   **Fallback applied, as `docs/implementation_phases.md` names it:** Phase 1 Step 1.13 unions the
   QLever autocomplete results with the `entity_labels` overlay (`updated_at` after the index
   watermark, `default_label ILIKE q || '%'`), so newly published entities appear until the next
   rebuild. Please acknowledge.
   **Resolved (orchestrator under the owner's delegation, 2026-11-22; reversible):** NO-GO acknowledged; the `entity_labels` overlay is mandatory in Step 1.13 (guide updated).
2. **Which QLever binary to pin (follows Step 0.3 question 3).** Everything else in S1 behaves the
   same on both binaries, so the Homebrew 0.6.0 pin can stay. A binary at or after upstream
   `d417fa76` would make whole-word `ql:has-word` fresh (the overlay would still be needed for
   prefixes); it builds natively on this Mac in about 3 minutes with one compiler flag (spike
   report section 8). Decide whether to keep 0.6.0 until a newer Homebrew release, or pin a source
   build.
   **Resolved (orchestrator under the owner's delegation, 2026-11-22; reversible):** keep the Homebrew QLever 0.6.0 pin (`6c5861a`) for development and CI because it is reproducible; the overlay is needed for prefix search on either binary. Revisit when Homebrew ships a release at or after `d417fa76`, or if index-build time matters before then (master builds about 2–3× faster). CI jobs that need QLever install it the same way (Homebrew on a macOS runner) unless a native Linux package of the same version is available.
3. **QLever's built-in rebuild cannot be used while text search is.** `cmd=rebuild-index` (and
   `--rebuild-index-strategy automatic`) folds the delta into a new index in 2 s at 11M triples,
   but drops the text index: `ql:contains-word` returns nothing afterwards, on both binaries, and
   QLever logs a warning saying so. Phase 2 Step 2.18 therefore keeps the external blue/green build
   with `qlever-index` (ADR-0002). No decision needed unless you want to revisit ADR-0002.
   **Resolved (orchestrator under the owner's delegation, 2026-11-22; reversible):** noted in Phase 2 Step 2.18; ADR-0002 stands.

## Step 0.11

Spike S6 (`docs/spikes/S6-bootstrap.md`) is a **GO**: 1M records bootstrap in 10.0 min, projected

1. **The GO line was set by the spike.** The guide gives no threshold, so S6 used "the projected
   10M bootstrap finishes inside an 8-hour overnight window on one machine like the development
   Mac, and no stage needs more memory than it has". Not verified: a dedicated or production-like

   stock settings). Confirm the window, or give the one that applies.
   **Resolved (orchestrator under the owner's delegation, 2026-11-22; reversible):** the 8-hour single-machine window is accepted as the bulk-bootstrap target.
2. **Carry a pyld patch?** Two expansion tunings were measured; both give byte-identical triples.
   The first, returning `"tag": "static"` from `lae.rdf.context.document_loader`, uses pyld's

   pyld's canonicalization of context objects by replacing `pyld.context_resolver.canonicalize`
   (a further +42 %, 2.1× in total at 1M records). Decide whether Step 1.3 may carry that patch
   (with a corpus-wide equality test against unpatched pyld and the pyld version pinned exactly),
   whether it should be offered upstream to pyld instead, or neither.
   **Resolved (orchestrator under the owner's delegation, 2026-11-22; reversible):** adopt the public-contract `"tag": "static"` loader change (Step 1.12 guide updated); do not carry the pyld monkeypatch now (maintenance risk for a +42 % bulk-only gain). Revisit, or offer it upstream, if bulk loads exceed the window.
